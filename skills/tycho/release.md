# 交付可审阅的代码与发布包

收到 Tycho 任务后，在 brief 指定的来源里完成工作，用机器自己的 Git 身份交付代码，把需要登记的非代码产物放到本轮交付目录。只读轮次只在最后一条消息报告结论，不改代码、不提交、不推送、不打包，也不往 `artifacts/` 放文件。

## 1. 在 brief 指定的工作目录开工

在执行机器上读 brief 的“代码在哪”和交付要求。有 Git 检出时，在当前工作目录核对：

```sh
pwd
git status --short
git rev-parse HEAD
```

- **仓库来源**：机器已准备好本任务的克隆，后续可写轮次沿用它。核对 `origin` 和任务要求的分支；不要假设目录叫 `repo/`，不要重置或重新克隆以丢掉上一轮的工作。可写轮次按 brief 先 fetch、合入需要的远端更新；不要 rebase 已推出去的提交。
- **工作目录来源**：代码就在 brief 指定的机器文件夹。按任务和仓库规则决定是否提交、使用哪条分支；保留别人的未提交工作，不擅自改变目录或来源。
- **没有代码来源**：按 brief 交报告或文件，不凭空寻找一个仓库。

来源与路径以本轮 brief 为准，详见[代码来源](../../docs/design/code-sources.md)。

## 2. 检查并交付代码

在可写轮次，按任务和仓库要求完成修改与检查；记录检查命令、结果和对应的最终提交。Tycho 测试从 `npm test` 入口运行，选测用 `npm test -- tests/<文件>.test.ts`。检查后再改代码或合入更新，就重新运行受影响的检查；需要发布包时，在冻结提交上完成打包。

仓库来源用这台机器已获准的 Git、`gh` 或 `glab` 身份推分支、开 PR/MR。目标按任务要求，未指定时用默认分支；已有 PR 就更新原 PR。不要强推或把凭据交给服务。推送、开 PR 失败时，在报告中写明卡在哪一步和脱敏后的原话，不把未推送说成已交付；仓库审阅需要机器核实已推分支的头与所报提交一致。

回执格式以本轮 brief 为准。**仓库来源**：`commit` 写当前工作目录的 HEAD，推上去了才写 `branch`。**工作目录来源**：提交了才写 `commit`，用了哪条本地分支就写 `branch`，不以推送成功为条件；没有提交时，不把旧 HEAD 冒充本次提交。两种来源的 PR/MR 都只写至多一项 `pr`，其 `ref` 是平台给出的完整网址。工作目录的改动留在原目录，服务不搬代码。

## 3. 只在任务要求时制作发布包

在 Tycho 仓库的最终提交上运行：

```sh
node scripts/pack.ts --out <brief 指定的本轮 artifacts 绝对路径>
```

成功时命令打印 `tycho-<版本>.tar.gz` 的路径。打包会重建控制台，缺前端依赖时按锁文件安装；包内已包含运行所需文件，服务端没有额外构建步骤。

不要手改 `package.json` 的第三段版本：源码只写主次版本，打包按 HEAD 提交数编号。交付记录写清冻结的 commit、包名、SHA-256 和检查结果。代码再改或包被替换，原来的审阅与发布授权不再覆盖它；同版本的不同内容不能当作重装。

已冻结、验证的包继续使用原提交和摘要。单纯更正文档不要求重打该包，也不要求重跑全套测试；本次检查按文档改动的实际范围执行。

## 4. 把非代码产物交给服务登记

在执行机器上，把本任务要求的报告、发布包等普通文件放到 brief 指定的本轮 `artifacts/`，按 brief 填回执。不要从当前工作目录猜交付路径：folder 来源的工作目录可能完全不在本轮目录里。遵守文件名和大小限制，不放子目录或链接。

审阅绑定或主人验收时，服务从本轮机器取回文件、核对摘要并登记。审阅与上线使用账本登记的产物身份；任务页预览报告不会自动登记或验收。取回失败时查看原因，不能把“机器上有文件”当作已登记。代码通过已推提交和 PR 交付，不放代码归档来替代它们。

## 5. 等当前产物审阅与验收，再按授权合 PR

需要独立审阅的任务，以当前验收标准、来源、提交和登记文件摘要绑定审阅。返工或替换产物后重新审阅；不要沿用旧结论。主人或项目已授权的入口验收后，才可请求“并入主线”。没有 PR 就没有可合的 PR；工作目录来源没有搬到主机再合入的一步。

收到正式合入子任务时，只用任务绑定的被审提交执行平台命令：

```sh
gh pr merge <PR 完整网址> --match-head-commit <被审提交>
# GitLab 使用：glab mr merge <MR 完整网址> --sha <被审提交>
```

沿用仓库默认合并方式，不加 `--admin`，不绕过检查、审阅或分支保护，不强推、不改 PR 提交。平台拒绝就停止，照原话报告。成功后按合入任务回执报告基准分支上的合入提交和合并方式。服务不替执行者调用托管平台，详见[合入实现](../../service/land.ts)。

## 6. 交付后由批准的发布入口上线

执行者交回经过检查的代码与登记产物，不自行停止正式服务。主人在控制台确认指定包，或明确运行 `tycho update --from <发布包>` 后，由独立升级进程切换版本并核对。审阅、验收、合 PR 和上线是各自的关卡，不能互相代替。

核对通过才算上线完成；仍在启动或恢复清点时如实报告待核实。自动回退只在已证明兼容、确认候选及总控已停止时换回程序，保留当前账本。schema 不兼容时不能直接启动旧版；人工恢复升级前副本前先核对新增写入和外部副作用，不能悄悄丢掉它们。发布与回退细则见[自我迭代](../../docs/design/self-iteration.md)。
