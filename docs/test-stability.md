# 修随机失败的测试、缩短慢的测试文件

读者是接到这两类活的执行者，以及审阅这类改动的人。结论先说：随机失败在拥有那份状态或那个进程的地方找根因，让用例等真实发生的事；一律不用重试、调大时限、加等待来盖住。慢的文件先去掉白等，再共用只读准备，最后才拆文件。

全量怎么跑、怎么排队见 [AGENTS.md](../AGENTS.md) 的“怎么改”一节。同一个文件里的用例按顺序跑，文件之间并行，所以全量的墙上时间约等于最慢那个文件的时间。

## 两类活都不能用的办法

- 重试或自动重跑。
- 调大超时或时限、加 `sleep`、把 `rmSync` 的 `maxRetries` 加大来压 `EPERM`。
- 放宽或删除断言、删用例、合并用例而丢掉断言、`skip`、`todo`。
- 在产品代码里为测试开特例，或改产品默认值来迁就测试。

时限本身就是被测行为时（例如“到时限认不出”），用注入的时钟推进时间，或让测试替身控制时限从“准备完成”那一刻起算，不把数字调大。

## 修随机失败

1. **先在负载下复现**，记下失败输出。复现不出来，也要写清观察到的时序窗口在哪、为什么会失败。
2. **找根因，在拥有者处修。** 常见根因：
   - 测试按固定时长等待后断言中间状态。
   - 时限（`limitMs`、`deadline`）在负载下比准备工作还短。
   - 进程或句柄还没真正退出就删目录（Windows 上是 `EPERM`、`EBUSY`）。
   - 进程退出后才去读它的启动时刻。
   - 几个测试文件共用固定的名字、端口、目录或环境变量。
3. **修法**：等真正的事件或状态（轮询状态直到出现，或由被测代码通知）；用注入的时钟（`t.mock.timers`，或模块接受的 `now`、`limitMs` 参数）代替墙上时间；收尾时先等拥有者确认进程已退出，再删目录。产品代码有真问题（比如停服务时没等子进程退出就返回）就修产品代码，并补一条先失败后通过的测试。
4. **验证**：目标文件在负载下连续通过 10 次，不加负载也通过，`npm run typecheck` 通过。

   ```
   for i in $(seq 10); do node --import ./tests/guard.ts --test tests/<文件>.test.ts || break; done
   ```

### 怎么加负载

```
node scripts/load.ts 8 300
```

起一个进程、8 个忙线程，300 秒后自己退出。脚本把线程数封顶在 8、时长封顶在 300 秒：机器上还有别人在用，需要更久就分几次起。放后台跑；要提前结束，只按它打印的 pid 结束这一个进程。

## 缩短一个测试文件的耗时

目标是单独跑这个文件在 150 秒以内，每个用例防的失败方式不变，也不变得更不稳定。按下面的顺序做，前一步够了就不做后一步。

1. **去掉白等。** 先单独跑一遍，记下每个用例的耗时：

   ```
   node --import ./tests/guard.ts --test --test-reporter=spec tests/<文件>.test.ts
   ```

   对最慢的几个用例查清时间花在哪：固定等待、等某个时限或轮询间隔自然到期、等进程退出的兜底超时、反复起真进程。能改成等真实事件的就改。被测代码已经接受的时间参数（轮询间隔、宽限期、时限）在测试里可以取小值，条件是断言的仍是同一件事，而且不依赖“小值在负载下也来得及”；断言依赖时序时，改用注入时钟或事件。
2. **共用准备。** 多个用例重复做同一份昂贵准备（编译、建仓库、打包），而结果只读不改的，在文件里准备一次复用。会被用例改动的不共用。
3. **拆文件。** 用例本身要起真进程、确实慢，做完前两步仍超过 150 秒，就按主题拆成几个 `*.test.ts`：原文件名留给第一部分，新文件叫 `<原名>-<主题>.test.ts`，每个文件开头写它防的失败方式。共用的夹具放进新的 `tests/<原名>-fixture.ts`，不往 `tests/helpers.ts` 里加。

验证：改动前后各单独跑一遍，报告每个文件的总耗时和最慢的 5 个用例；改过的文件连续跑 5 次全部通过；`npm run typecheck` 通过。机器上同时有别的测试在跑时耗时会波动，前后两次尽量挨着跑，并在报告里写明。

## 审阅这类改动时查什么

1. 有没有变相的掩盖：上面不能用的办法，包括把一个时间常数改大却说成“对齐产品上界”、把失败路径变成 `skip` 的条件。
2. 修随机失败的改动是真的消除了时序窗口，还是只把窗口变小。
3. 产品代码的改动有没有改变产品行为（去掉时限、把查询并发化、改进程身份的报告格式），有没有引入新问题（原来有上限的等待现在可能永远等）。
4. 共用的准备有没有让用例之间共享会被改写的状态。
5. 拆文件的提交：原文件里的每个用例和每条断言都还在（按用例名和 `assert` 行对比拆分前后）；夹具有没有重复定义；各文件之间有没有固定的名字、端口、目录互相冲突（它们会并行跑）。
