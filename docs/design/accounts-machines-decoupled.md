# 账号和机器解耦：账号说"能用什么"，机器说"在哪儿干"

读者：主人和实现者。状态：**已确认；第 1、2、3 步、内部编号和机器上登录好的执行器自动采用已落地（内部编号账本版本 26；账号默认名、删除清项目清单和空池项目可见是账本版本 30；自动采用和删掉不加回是账本版本 39）**（2026-11-09 主人确认；起因是主人指出账号与机器页里两者是耦合的）。本文按终态写，不做过渡兼容（主人 11-09："永远指向终态开发"）。

## 结论

1. **账号不再列机器。** 删掉账号上的"能在哪些机器上用"清单。账号只回答"我能用什么"：执行器、tycho 替你保管的登录、各档内容、权限和并发上限。
2. **tycho 保管的登录自动送到每台机器。** 填了登录的账号，在任何一台"在线、装了这个执行器"的机器上都能跑；每一轮由 tycho 经凭据通道把登录送到那台机器上那一轮的进程（这条通道今天已经有了），机器上不用预先登录，也不用你去"同步"。
3. **机器自己的登录归机器，不再伪装成账号。** 机器接入后会上报它装了哪些执行器、登录了没有（已有）。它自己已经登录的执行器，就是"这台机器上的一份登录"：主机在处理这份报告时就写下一份，带好默认档位，直接可以被派活，账号页和机器页都列出来；你不用为它建账号，也不用再给它填一遍。今天的 `local-codex` 就是这种，迁移时并到 DEV-WORKSTATION 下面。
4. **项目只说"允许用哪些账号和哪些机器登录"，机器由派发挑。** 派发在"项目允许的登录 × 在线且装了执行器的机器"里挑：只读的活还要过机器的只读探针（已有），审阅还要换执行器（已有；别的都审不了时降级，见 roles-and-tiers.md §4 ②）。项目上的"允许的机器"清单保留，因为它表达的是"这个项目的活只能在哪些地方跑"（代码、数据、网络在哪），默认空 = 哪儿都行。

一句话：**登录是"谁的身份"，机器是"在哪儿"，两者在派发那一刻才组合。**

## 为什么

- 账号上的机器清单是 SSH 时代"执行目标"留下的：那时登录装在某台机器上，账号离不开机器。凭据由 tycho 保管之后（账本版本 8 起），带凭据的账号本来就能和任意机器组合（[accounts-and-machines.md](accounts-and-machines.md) §绑定 最后一段），清单只剩限制作用，还得你在两处各配一遍。
- 机器自己的登录今天要登记成一个"凭据留空、只列这台机器"的账号，这是同一件事的两份记录：机器已经报了"Codex 已登录"，你还得再建一个账号告诉 tycho。

## 哪些登录能"自动分发"，哪些不能

| 登录 | 能交给 tycho 保管、送到任意机器吗 | 依据 |
|---|---|---|
| Claude Code 订阅（`claude setup-token` 的长期令牌） | 能，已实现 | 实测令牌在空配置目录里能跑（accounts-and-machines.md §凭据 实测） |
| Claude / Codex 的 API 密钥 | 能 | 密钥不轮换，送到哪都一样 |
| Codex 的 ChatGPT 订阅登录 | **不能当成可搬运的凭据** | 它是会轮换的 OAuth 刷新令牌：同一份登录在两台机器上各自刷新，会互相把对方挤掉。这种登录只能是"机器自己的登录" |
| dsh 的 provider 密钥 | 能（随启动环境交给那一轮，2026-11-11 实测） | 存凭据的服务保持关闭（native-login.md 文末） |

所以"登录自动同步到所有机器"的终态是：**能搬运的登录 tycho 保管、每轮送达；不能搬运的登录留在它登录的那台机器上，作为那台机器的能力出现。** 不做"把一台机器的 `~/.codex/auth.json` 拷到别的机器"这种同步：轮换令牌会坏，而且等于把你的会话复制到所有机器。

## 对象长什么样（终态）

| 对象 | 字段 |
|---|---|
| **账号**（tycho 保管登录的身份） | 内部编号、可改的名字、执行器、登录（必填：账号就是"tycho 替你保管的一份登录"）、各档内容、权限、单次时限、同时最多几轮；运行时的额度状态 |
| **机器** | 名字、备注、平台、来源、临时标记；机器上报的执行器（装没装、版本、**机器自己登录了没有**、只读探针、它列出的可用模型）。机器自己已登录的执行器，主机按那份报告自动写一份“机器自己的登录”（可能已经在机器页改过），带适配器声明的默认档位（模型留空，用那台机器上执行器自己的默认），在机器页和账号页都能改，和账号的档位表单是同一个组件 |
| **项目** | 允许的登录（账号，或"某台机器自己的某个执行器登录"；只定能不能用，不带顺序）、允许的机器（空 = 都行） |

派发时的一个候选 = （一份登录，一台机器）：

- 账号登录：任何允许的、在线的、装了这个执行器的机器。
- 机器自己的登录：只有它所在的那台机器。

额度状态跟着"登录"走：账号的记在账号上，机器自己的记在那台机器的那个执行器上（同一个订阅登录在两台机器上是两份额度窗口这一点，由执行器自己报，tycho 不推断）。

## 分步

1. **已落地。** 机器自己的登录成为机器上的能力（机器页能填它的档位，派发能用它），迁移把凭据留空的账号并过去。
2. **已落地。** 删账号上的机器清单，派发按（登录，机器）挑；项目允许清单改成"登录"。
3. **已落地。** 控制台拆页。账号卡片上不列机器；账号的“测试连接”由 Runner 的 `check` 挑一台在线、装了执行器的机器问一次，没有就照实说没问。关于某个登录的通知（模型增减、令牌失效、登录被拒）按 `shared/logins.ts` 的 `loginPage` 指路：账号去账号页，机器自己的登录去机器页，正文里的页名和链接出自同一处。

每一步做完都能单独用；第 1、2 步之间不留"两种都认"的过渡：两步一起合入，迁移一次到终态。

### 第 1、2 步落地后的样子

- **登录的编号。** 账号与机器自己的登录都用账本生成、从不重用的内部编号（`ulid`）。账号名字在现存账号中唯一，可以随时改；机器登录的显示名是"机器名/执行器"（例如 `DEV-WORKSTATION/codex`），它的编号绑定这次机器登记的 `machine.uid`。账号名和机器名不许带 `/`，两种显示名不会相撞。页面和消息里说"账号 X"或"机器 M 上的 E 登录"（`shared/logins.ts`）。
- **账本（版本 18）。** 新表 `machine_login`（机器、执行器、各档、权限、单次时限、同时最多几轮），机器删掉时一起删；`account` 去掉 `machines_json`；项目的 `logins_json`、任务和 Run 的 `login_id`、额度状态表 `login_state` 对两种登录一视同仁。Run 快照记 `login`（机器登录的机器在 `login.machine` 里，不能从编号推断种类）；没有 `login` 的旧快照只当历史读，一轮还没发出去就碰到它，这一轮撤回重派，不按旧快照启动。
- **账号必须有凭据。** 账号的登录按执行器声明的方式取得（见 [native-login.md](native-login.md)），换执行器要同时换一份凭据，凭据只能换、不能清。只有能每轮交凭据的执行器能建账号（适配器声明了 `credential`）：Claude 的登录、Codex 的 API 密钥、dsh 的线路密钥（[native-login.md](native-login.md) 文末）。
- **机器自己的登录什么时候能用。** 机器报告某执行器装好了、这一版在这个程序里能用、而且没说没登录，主机在处理这份报告时就写一份：默认档位由该执行器的适配器声明（`ownLoginTiers`，用它的 `tierForm.render` 写成文本），Claude 和 Codex 是决策档强度高、执行档强度中，模型留空（用机器上执行器自己的默认）；dsh 的决策档和执行档都是空文本（它的 patch 整块替换 `config`，只写强度会丢 provider 和 model，空文本就是用机器上的配置）。自动采用只写决策档和执行档，操作档不写、按同一份登录的执行档内容顶替；空文本也算已填，派发照同一条档位规则就能用它。它立刻可用，不再需要主人先填档位：执行器没有在某一轮里拒过它（见下），而且机器的话允许它在那里跑。“能不能在那台机器上跑”只在 `service/readonly.ts` 的 `ownLoginHere` 一处判定：机器还没报告、或报告里没有这个执行器，等它的报告；报告了装了、没说用不了（版本低于适配器要的、或机器自己报了 `unusable` 都不算能用）、也没说没登录，就能用——`logged_in` 为空表示执行器没有问登录的命令（dsh 就是这样），按它的话算。自动采用走的就是这一个判断：机器报告的那份这时就写下来，报告说没装、用不了、或没登录就不写；已经有一份的行从不被默认值改。同一份报告重复到达只写一份（在账本的同一个事务里先查再写），审计写 `machine_login.create`，actor 是服务自己，理由写明“机器报告已登录，自动采用”。写失败只记日志，不拒收报告。**主人删掉的那份不会自己回来：** 在控制台删除一份机器自己的登录时，同一个事务里记下“这台机器登记（`machine.uid`）+ 这个执行器被主人拒用”，自动采用跳过它；清掉这条记录的只有在 tycho 里对这台机器这个执行器完成一次登录（`service/sign-ins.ts` 的登录到 `done`），或主人在机器页、账号页显式提交一次这份登录的设置（`PUT /api/machines/:uid/logins/:executor`，有就更新、没有就建）。机器删除时一起删；同名重新接入是新登记，不继承。它没有配置目录这一项：用的就是机器上那份登录。
- **登录被拒。** 两种登录同一个分类：一轮里执行器报 `auth`，这一轮按认证失败结算、任务排回队列，这份登录不再接新活（`loginRefused` 一处判定）。恢复看来源：账号等换令牌；机器自己的登录等那台机器之后报告"已登录"（探针时刻晚于失效时刻）；"现在就试"只结束额度歇息。
- **历史只看这一轮所在的机器。** 读原始输出、取产物、绑定审阅，只核对这一轮绑定的机器还是不是那台（同一个节点身份）、连不连得上，不看它当时用的登录还在不在：迁移并掉的账号跑完的那些轮次照样能读、能取、能审。派发和启动仍只接受带 `login` 的新快照。
- **派发。** 候选 = 项目允许的登录 ×（账号：项目允许的、在线、装了执行器的机器；机器自己的登录：只有它那台），按该档位的全局派发顺序（`dispatch.order.<档位>`，`loginOrder(tier)` 一处算）排；项目清单只定能不能用，不带顺序。任务上的总控优先名单（`task.prefer_json`）先试，审阅任务再先试没审过同一份产物的执行器，最后才是全部候选；哪一组挑中记在 `run.create` 的 `placed_by`。只读探针、审阅换执行器（及其降级）、档位、额度、并发上限、临时机器只接名额项目，各自仍只在一处判定，对两种登录同样适用。
- **总控的工具。** `list_logins`（取代 `list_accounts`）、`set_project_logins`、`create_project` 的 `logins`、`create_task` / `update_task` 的 `login_id`；`add_machine` 当时不再带账号清单（它后来整个删掉了：机器只经客户端接入，nodes.md §11 第 6 步）。旧参数名一律当未知参数拒收。
- **控制台（只做到能用）。** 账号卡片去掉机器勾选，新建账号按执行器声明的方式登录，凭据只能换；账号页在账号列表下面另有一节列出所有机器自己的登录，每行用机器页同一个表单改档位和上限、删除、额度歇着时“现在就试”；每台机器下面也列“这台机器自己的登录”。项目页的允许清单可以选账号和机器登录。

### 机器登录的自动采用（账本 38 → 39）

主人不必为机器上已经登录好的执行器再登记一次。新表 `machine_login_refusal`（`machine_uid`、`executor`、`created_at`）只记“主人在这次登记里删过这份登录”：自动采用先查它；主人在机器页或账号页显式保存、或在 tycho 里对这台机器这个执行器登录完成时清掉；机器删除时随机器一起删。旧的 `machine_login` 行一行不动，升级也不回填拒用记录。

- 报告的处理在 `service/nodes.ts` 的 `signedIn`（每份报告都经过它）：采用不采用直接问 `service/readonly.ts` 的 `ownLoginHere`（派发用的是同一个判断，不各写一份），建行只在账本 `adoptMachineLogin` 一处，在一个事务里先查再写。
- `PUT /api/machines/:uid/logins/:executor` 改为“有就更新、没有就建”，回答的 `created` 说明是哪种；`PUT /api/logins/:id` 不变。
- 控制台账号页列出机器自己的登录，编辑用机器页同一个 `LoginEditor onMachine` 和同一组接口；机器页的编辑能力全部保留。

### 迁移规则的细节（实现时定的）

- 凭据留空的账号列的机器为空（"哪台都行"），按当时账本里所有没离开的机器各并一份；列着的机器已经不在账本里的跳过。
- 两个凭据留空的账号并到同一台机器的同一个执行器上，留先建的那个账号的档位和限制，后面的只把引用改过去。
- 项目允许清单里，并出来的机器登录只留项目允许的机器上的那些（项目机器清单为空就都留）。
- 没结束的任务：钉的账号正好并成一份机器登录，改钉过去；并成多份或零份，取消钉住，时间线记 `login.migrate`，写明原来钉的账号和理由。
- 还没结束的 Run 的 `login_id` 改成它所在机器的那份机器登录；已结束的任务和 Run 保留旧编号（历史）。
- 总控绑在被并掉的账号上的，绑定原样留着（时间线记一条），于是总控按已有的"绑定的账号不在"停摆，理由写明"在账号和机器解耦的迁移中被并掉了，请在设置里重新绑定一个带令牌的账号"，排着的消息不被取走。不能把它清空：清空读起来是"主人选了不绑"，总控会改用这台电脑自己的登录接着跑。
- 每个被并掉的账号在时间线留一条 `login.migrate`：原账号名和并成的登录。

## 内部编号（账本 25 → 26）

主人改账号名字后，项目清单、任务的钉住、正在执行的轮次、额度状态和总控绑定都继续指向原来的登录。删除后再用同一个名字新建，是另一份登录，不继承任何引用或状态。机器删掉后同名接入也一样；同一份机器登录改档位和上限时编号保持不变，删除这份登录后重设则生成新编号。

- `account.id` 是内部编号，`account.name` 是唯一的当前名字；改名只由账本的 `renameAccount(id, name)` 判定和写入，不重验或重写档位内容。默认名也只由账本一处定：新建时不给名字，就在写这一行的事务里起成“<执行器> 账号”（执行器报告的组织编号不是名字，Claude 的登录令牌读不到邮箱，见 native-login.md 文末），撞上现存名字就加序号，新建不因重名被拦。`machine_login.id` 是内部编号，`machine_uid` 绑定机器的本次登记。名字不参与凭据文件路径，凭据仍由 `credential_ref` 定位。
- 项目 `logins_json`、任务与 Run 的 `login_id`、`login_state.id`、`router_context.login_id`、设置 `router.account` 和 `knowledge.logins` 都只存内部编号。Run 和总控上下文额外记 `login_name`，只表示启动时的名字；改名不重写过去的实际输入和历史名字。
- 控制台读接口给 `id` 和 `name`，新建用 `POST /api/accounts`（`name` 可不填，回答里的 `account.name` 是最终名字），更新用 `PUT /api/accounts/:id`（含 `name`，仍拒绝重名）。旧名字或已删除的编号都不能当作更新目标。项目和设置写编号，显示名字。删账号或被删机器自己的登录时，同一事务里把它的编号从项目的 `logins_json` 里去掉，每个受影响的项目记一条 `project.update`（写明去掉的是哪份登录、按名字），`DELETE /api/accounts/:id` 和 `DELETE /api/logins/:id` 的回答（以及删除前的确认预览）都列出受影响的项目 id、名字和各自删后还剩几个可用登录。已配置的机器登录通过 `PUT /api/logins/:id`、`DELETE /api/logins/:id` 和 `POST /api/logins/:id/retry` 操作；`PUT /api/machines/:machine.uid/logins/:executor` 有就更新、没有就建（回答的 `created` 说明是哪种，也用于修好一台机器上报了、主人删过的登录）。旧页面持有的登录编号或机器登记号失效就拒绝，不按名字接到新对象。
- 总控仍用名字说话：`list_logins` 的 `id` 和工具参数 `login_id` 的值都是当前名字；工具在受理当下查名字、解析编号，不存在就拒绝。给总控的内部事件也把登录引用换成名字，审计载荷仍存编号。HTTP 和工具对历史 Run 的额度信息共用一处展示换算，优先用 Run 的 `login_name`、再用当前名字，不改历史 `error_json`。账本不保留“名字或编号都行”的读法。引用已经不在了的句子（总控绑定的账号、运行中进程用的账号、自检那一条）用账本里它被删时的名字（`account.delete` 审计的 `account.name`，更早的折叠记录本身就是名字），找不到名字才说“已删除的账号”；内部编号不进任何文案。
- 主机总控没有绑定账号时，使用本机执行器登录；主机尚未作为机器配置这份登录时，上下文的 `login_id` 为 null，`login_name` 留本机显示名，不生成基于主机名的引用。本机接入时在账本记这次机器登记号（`host_machine_uid`），只用仍有效的这次登记定位本机。迁移旧账本时，最后一次本机接入记录的名字必须对应唯一的有效机器登记，而且之后没有删除或重新接入，才补上登记号；有旧本机接入记录但无法确认时，`host_machine_uid` 记 null，自检和机器页说明重新接入一次可恢复绑定；从未本机接入的主机不记这个设置、不告警，不用 hostname 猜。
- 升级到 30 的同一个事务顺带清掉现存清单里已经悬空的编号，每个受影响的项目记一条 `project.update`（原名和原因；原名按 `account.delete` 审计的 `account.name`、`machine_login.delete` 的 `login_name` 或 `login.name` 反查，查不到写“已删除的登录”）。项目此刻的有效登录池为空（“只用所选”且所选都没了，或根本没有登录）时，由账本的 `projectsWithoutLogins` 一处判定：`/api/overview` 的 `no_login` 给出项目 id、名字和原因，自检给一条“注意”指到那个项目的设置页。

迁移在一个事务里生成编号并转换所有引用，包括待发送、待提醒通知里的登录引用。已经不存在的登录从清单中删除，任务取消钉住，未结束 Run 和总控上下文的引用置 null、原名留下单独显示，孤立的额度状态删除；已结束 Run 保留登录身份：同一个已删除的旧登录分配同一个独立历史编号、原名存 `login_name`，不创建可派发的登录，也不会被同名新对象接上；设置里的悬空项也清掉。每个受影响对象都有带原名和清理原因的审计，项目用 `project.update`，任务、Run 和设置各自记录，名字不会留在引用里等同名新对象接上。悬空 `router.account` 清空后是无绑定、用本机登录；悬空 `knowledge.logins` 全清后按空清单使用所有登录，审计保留清理的原名。旧的实际输入快照和已经写下的历史审计保持原字节，不用于查当前身份。上面版本 18 的迁移细节只描述当时的变换，版本 26 的编号规则取代其中按名字保留引用的部分。
