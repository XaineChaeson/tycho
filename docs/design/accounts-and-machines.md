# 账号、机器、绑定：tycho 的配置模型

读者：主人，用来决定要不要这样改；通过后是实现的依据。状态：已确认，分步实现中。账号和机器的关系后来又改过一次（账本版本 18）：账号不再列机器，机器上已经登录好的执行器是"机器自己的登录"，项目允许的是"登录"——以 [accounts-machines-decoupled.md](accounts-machines-decoupled.md) 为准，本文相应处已改成那个样子。

## 结论

把“执行目标”拆成三样，总控和执行者从同一份账号里取：

| | 回答什么 | 里面有什么 |
|---|---|---|
| **登录** | 谁来想 | 两种：**账号**（tycho 保管的一份登录：执行器种类、登录凭据，必填）和**机器自己的登录**（机器上已经登录好的某个执行器）。两种都带各档位的内容、权限、并发上限；运行时的额度状态跟着登录 |
| **机器** | 在哪儿跑 | 一台机器：名字、备注、平台，以及它上面装了哪些执行器。机器自己跑 `tycho node` 主动连回主机，账本按节点身份登记；Worker 的 SSH 路径已删除（[nodes.md](nodes.md) §11 第 6 步） |
| **绑定** | 谁用哪个 | 总控 = 账号 + 档位；项目 = 允许的登录（不带顺序）+ 允许的机器 |

一轮执行 = 任务 × 挑出的（登录，机器）：账号配项目允许的、在线、装了执行器的任意一台机器，机器自己的登录只配它那台。“执行目标”这个概念取消。

已经落地的是第 1 步：账本版本 7 里是 `account`、`machine` 两张表和跟着账号的额度状态，控制台里是“账号与机器”一页，派发、工具、接口都按账号和机器说话（现状见 [phase1-design.md](phase1-design.md) §3、§4）。凭据还在机器上、档位还是机器上的文件路径，是后面几步的事。

账号带着凭据走：tycho 保管，每轮启动时交给那一轮，机器上不用预先登录；建账号必须填凭据。机器上已经登录好的执行器不建账号，它是**那台机器自己的登录**，只属于那台机器、那个用户，只在那台机器上跑（[nodes.md](nodes.md) §1.2）。

开实例不归 tycho 管：tycho 只提供“接入一台、撤销一台”的接口（机器自己连回来），实例怎么开、怎么销毁是技能的事。

执行器和通道写成插件；账本、状态机和九条底线是固定的核心，不可替换。

## 为什么要改

现在的“执行目标”把四件不相干的事粘在一起：执行器、机器列表、登录目录、档位。

- 换一台机器和换一个账号，改的是同一个对象。
- 两个 Claude 账号很难同时用：登录是装在机器上的，一台机器一份。
- 档位是“机器上某个文件的路径”，新机器上没有这个文件，这个档位就用不了。
- 总控另有三项设置，同一个账号要在两处各配一遍。
- 额度状态记在执行目标上，两个目标共用一个账号时，另一个要白跑一轮才知道。

## 账号

一个账号是一个能干活的身份。字段：

- **名字**，你起的。
- **执行器**：Claude Code、Codex、dsh。决定下面几项长什么样。
- **凭据**：见下一节。
- **档位**：每个档位的内容由执行器自己声明，tycho 随快照发到机器上。Claude 是一份 settings 的内容，Codex 是一组配置项，dsh 是一份 patch。机器上不需要预先放任何文件。控制台的表单默认只填三样：档位名、模型、推理强度（dsh 的档位还要 provider）；推理强度的取值和“模型+强度→文本”都由执行器自己声明，其余设置在这一行的“高级”里按原文保留，改模型不会动它们。旧账号里指向机器上文件的档位显示为“用机器上的文件（旧方式）”，点“改成由 tycho 设置”换成内容形式。
- **权限**、**单次时限**、**同时最多几轮**。

额度状态（歇到几点、用量）跟着账号。第十三步的挑选逻辑原样搬过来，从“按执行目标”改成“按账号”。

模型名只出现在这份数据里。代码和 brief 仍然只说执行器和档位，不传 `--model`：tycho 发的是档位内容。

### 模型列表

档位里的模型和强度不是空白框：账号的登录执行器自己报告它能用哪些模型，控制台按这份列表给下拉框（执行器标了隐藏的不列）；列表里没有的模型——一个执行器仍接受的别名，或者一个刚被下架的——可以手填并保留，那一行会标出来说它不在列表里。强度跟着所选模型走：模型自己说接受哪些强度就列哪些，没说就退回执行器声明的强度表。列表还没读到就是原来的自由输入。

怎么问、怎么读由适配器声明（`listModels`）。谁去问看是哪种登录：账号的由服务带着令牌去问；机器自己的登录由那台机器的客户端按声明的命令去问，在机器上解析后随执行器报告上报，主机只显示、不存账本（[nodes.md](nodes.md) §1.2 “可用模型”）。下面的“规则”说的是账号的列表。

| 执行器 | 怎么问 | 强度从哪儿来 |
|---|---|---|
| Claude Code | 账号有令牌时，用令牌请求 `GET https://api.anthropic.com/v1/models?limit=100`；令牌只在请求头里，不进日志、错误信息、通知和账本。没有令牌时读 `claude --help` 写明的别名和强度，能解析多少算多少，解析不了就空着 | 返回的 `capabilities.effort` 里 `supported: true` 的那些 |
| Codex | 机器的客户端在那台机器上跑 `codex debug models` | 每个模型自己的 `supported_reasoning_levels`（各模型不同，不能按一张全局表写） |
| dsh | 读 `dsh --profile headless --dump-config`（一轮启动的那个 profile；不带 profile 启动器不回答）里线路自己写下的 `models:`，加上 `agent-default-model` 写着的那一个默认模型；随包的 profile 不写清单，所以通常只有默认模型这一个，别的由主人手填。要查自己 `/models` 的线路在这里加（`http` 查询就是为它留的），tycho 不认识任何具体网关 | 线路写下的那些 |

规则：

- 读到的东西记在 `login_state`（账本版本 18 之前叫 `account_state`）的 `models_json` 和读到的时刻（`models_at`），和额度状态一样是“用出来的状态”，不是配置，不参与“配置有没有变”的比较，随登录一起删。
- 查询时机：保存账号、换登录令牌、点“测试连接”时各一次，另外按配置项 `models.refreshMs`（默认 6 小时）定时问一次：定时器定在最早到期的那个账号上（上次读到或上次定时去问，再过这么久），没有另一套固定的检查周期；改了这一项马上按新值重排。问不到的账号也是隔这么久再问，不连着重试。机器自己的登录不在这一轮里：它的列表跟着机器每次上报执行器走。查询等机器回答的期限和“测试连接”是同一个。保存和令牌那两次不等结果，答案随后到；测试连接等它，因为主人正看着。
- 查询失败保留上次结果，页面上写着最后成功读到的时刻；一次查询不阻塞派发，一个账号问不到不影响别的账号，同一条查询同时只发一次。
- 列表里出现以前没有的模型、或者档位在用的模型从列表里消失，经 Outbox 通知一次（按账号 + 模型 id 去重，只发一次）；不自动改档位，换不换主人决定。第一次读到只填列表，不叫“新模型”。

实录：Codex 的模型目录录在 `tests/fixtures/codex/0.162.0/models.json`（codex-cli 0.162.0；每个模型项只留了 `slug`、`display_name`、`supported_reasoning_levels`、`default_reasoning_level`、`visibility`，删掉的是模型自带的整篇指令模板，模型的数量、顺序和取值都原样）。Claude 的 `GET /v1/models` 回答和 `claude --help` 在 `tests/fixtures/claude/models/` 里：`recorded.json`、`help.recorded.txt` 是 2026-11-07 用真实账号录的实录；`models.json`、`help.txt` 是按公布的字段形状写的构造，只用来钉住实录里没有的不整齐情况，README 里写明了。dsh 的 `--dump-config` 没有实录，解析的形状是猜的（见 `adapters/dsh.ts`）。

### 凭据

原则：**tycho 保管凭据，证明你是账号的持有者**——账号就是这份凭据，机器上不用预先登录；没有凭据的账号不存在，令牌只能换、不能清。机器自己的登录是另一种来源，不是账号：它只属于那台机器和那个用户，只在那台机器上跑（[nodes.md](nodes.md) §1.2）。这样同一台机器上两个 Claude 账号可以同时跑（各自带凭据），互不相干，没有“切换”这回事。今天 Claude、Codex（API 密钥）和 dsh（线路密钥）都能建账号（适配器声明了 `credential`）。

| 执行器 | 怎么得到 | 每轮怎么用 |
|---|---|---|
| Claude Code（订阅） | 在控制台按执行器声明的方式登录（见 [native-login.md](native-login.md)） | 经凭据通道放进这一轮进程的启动环境（`CLAUDE_CODE_OAUTH_TOKEN`），见下 |
| Claude Code（API） | API 密钥 | 给这一轮进程的 `ANTHROPIC_API_KEY` |
| Codex（API） | API 密钥 | 这一轮的环境 `CODEX_API_KEY`（实测压过机器自己的登录，见 [native-login.md](native-login.md) 文末） |
| Codex（ChatGPT 订阅） | 在一台机器上用设备码登录，是那台机器自己的登录 | 不交：机器上本来就有 |
| dsh | 一条线路加它的密钥：线路由 tycho 写成 patch，密钥随启动环境交给这一轮 | 启动环境（自定义线路 `TYCHO_DSH_API_KEY`，官方线路 `DEEPSEEK_API_KEY`）；三个凭据服务保持关闭，见 [native-login.md](native-login.md) 文末 |

规则：

- 存在 `<数据目录>/secrets/accounts/<编号>`，只有运行服务的用户可读，和企业微信 Secret 同一套做法：不进账本，不进备份，任何接口、`change`、日志都不带它，页面只显示“已设置”。
- 控制台里只能换，不能读。过期或失效时账号显示“要重新登录”或“要重新填”，走第一阶段设计里已有的“登录失效”处理（[phase1-design.md](phase1-design.md) §4、§6；额度用完不属于这一类，它会自己恢复）。
- 发到机器：经节点通道的**专用凭据通道**交给这一轮——机器上的客户端起这一轮时从凭据接口取，看管进程把它放进 Worker 启动环境里适配器声明的那个变量（Claude Code 的 `CLAUDE_CODE_OAUTH_TOKEN`）。这样 Worker 跑的子命令会继承它，同机同用户也能读到：机器是边界。不写进命令行（别的用户看得到），不落盘，不进快照和日志（[nodes.md](nodes.md) §9）。Windows 上 claude.exe 2.1.303 不读文件描述符，所以不再有那条路（实测见 [../spike/claude-credential-way.md](../spike/claude-credential-way.md)）。（历史：节点通道落地之前，令牌经 SSH 的标准输入进启动脚本；SSH 那条路已经删了。）
- 总控同样从账号取，环境里设令牌，不再依赖这台电脑上的登录。
- 同一条通道还交一样东西：任务派生机器时的一次性接入材料（[nodes.md](nodes.md) §1.3）。它不是账号的凭据，是给新机器加入用的：这一轮启动时当场签发、每份接一台、只用一次，是凭据接口回答里的 `materials`，到 Worker 的环境变量 `TYCHO_JOIN_MATERIALS` 为止。账本只存哈希，不进命令行、快照和 `change`。和账号凭据一样进启动环境，所以 Worker 的子进程会继承它、同机同用户能读到；它进不进这一轮的输出（主机会读回来显示），靠技能不去打印它。兜底是有效期、一份只接一台、上限在兑换时把关。一轮只签发一次。
- 账号必须有凭据：建账号时按执行器声明的方式取得，之后只能换、不能清。想用机器上已经登录好的执行器，不建账号，它就是那台机器自己的登录（[accounts-machines-decoupled.md](accounts-machines-decoupled.md)）。

这部分已实现（Claude Code 令牌）：

- 接口 `PUT /api/accounts/:id/credential` 换令牌；账号的读接口有一个 `credential` 字段（`set`／`rejected`）。任何接口都读不出令牌。
- 下发：机器上的客户端起这一轮时从 `POST /api/node/runs/:id/credential` 取令牌，交给看管进程，看管进程把它放进启动环境里的那个变量（`CLAUDE_CODE_OAUTH_TOKEN`）；起这一轮的命令里只有变量名，没有令牌（[nodes.md](nodes.md) §9）。最初实测的那条路是令牌进 SSH 的标准输入，SSH 那条路已经删了（nodes.md §11 第 6 步）。快照只记令牌的编号（`credential_ref`），不记值：发启动前对一次编号，主人刚换掉就走现有的“撤回重新挑”，不是报错。
- 会不会被采用：适配器还能声明一条不耗额度的问法（`credentialCheck`）。机器的客户端上报执行器时，用一段占位值设好那个变量跑一次（Claude 是 `claude auth status`，只看它说用的是哪份登录），把“会采用 / 不会采用 + 原话”随报告报回来。主机按这份报告挑机器：报了不会采用、或者报告里没有这一项的机器，不接这个执行器的账号的活；还有机器没报告就只是等。机器自己的登录不交令牌，不受这一项影响。
- 失效：适配器报 `auth` 时，Run 结算成退出类别 `auth`，任务排回队列（不算失败、不算重试次数），这份登录不再接新活，经 Outbox 通知一次。账号记下失效的是哪个令牌（`credential_rejected_ref`），换一个令牌才恢复；机器自己的登录记下失效的时刻（`auth_failed_at`），那台机器之后报告“已登录”（探针时刻晚于失效时刻）才恢复。是不是“不再接新活”只由 `loginRefused` 一处判定，挑登录、派发前核对和页面共用。没有时钟、不自动重试。

实测（2026-11-06，令牌有效期 1 年；本机 2.1.317，集群实例 2.1.312）：

- 空配置目录加令牌：`auth status` 报 `oauth_token`，`claude -p` 跑完一轮。本机和实例都通过。
- 令牌和机器自己的登录同时存在时，令牌优先。所以不用另建配置目录，机器上的 `settings.json` 照常生效。
- 令牌放在启动环境里能跑一轮；Worker 用 Bash 工具看到的环境里也有它，子命令会继承。文件描述符那条路在 Linux 上也能跑，但 Windows 上 claude.exe 2.1.303 根本不读它（`auth status` 和不给令牌时一模一样，会悄悄用机器自己的登录），所以 2026-11-11 起只有环境变量这一种交法（实测见 [../spike/claude-credential-way.md](../spike/claude-credential-way.md)）。后果：一轮执行在跑的时候，它能读到自己的令牌，有风险的任务可以把它带走。
- 跑完之后配置目录里搜不到令牌，没有落盘。
- 执行者跑在 root 身份的机器上时，`bypassPermissions` 要 `IS_SANDBOX=1` 才放行。集群实例上这个开关现在写在 `~/.claude/settings.json` 里。以后它不该靠机器上预先放的文件：账号的权限设置要能带上它。

这改掉了之前的两条约定：“凭据不进执行环境”和“不把本机的 Claude 凭据拷到集群”。要说清楚后果：一轮执行在跑的时候，它能读到自己的令牌，有风险的任务可以把它带走。这和现状差别不大，现在 Worker 也读得到机器上 `~/.claude` 里的凭据；差别是令牌会到达你所有的机器，而不只是登录过的那些。令牌可以单独作废，泄露了重新生成一个，不用改密码。

## 机器

机器是一个对象：名字、备注、平台、加入时间、最近一次往来、来源（手动 / 哪个任务的第几轮派生）、临时标记。可以增删。

**机器自己连回来。** 目标状态下，每台机器上跑一个 tycho 客户端（`tycho node`），由它主动连回主机；执行机器上不需要开入站端口，主机也不用 SSH 进去（设计见 [nodes.md](nodes.md)）。增删有两个入口，走同一份账本记录：

- 控制台的机器页：在那台机器上跑一条加入命令，屏幕上出现六位数，主人在控制台输这个数放行——和设备登录同一套，六位数只用来指认请求，换回来的是**节点令牌**，不是控制台 Cookie。
- 总控的工具：`invite_machine`（新增：申请一条接入名额，材料按设置的有效期（默认 15 分钟）、用一次、只在主人授权的范围内签发）、`list_machines`（已有，加上连接状态和来源）、`remove_machine`（已有，语义变成"撤销这台机器"，令牌立即失效，等于删设备）。

**原来的 `add_machine` 删掉**：不再让总控把 SSH 地址抄进账本。六位数那条人工接入只有主人能放行；总控能做的是在名额内签发一次性材料让临时机器自己接入（见上面 `invite_machine` 那条），两条路都不需要它替主人点放行。

动态的场景这样走：你对总控说"开一台实例接这个活"，总控派一个任务，执行者用项目的技能开实例，技能把一次性接入材料注入实例，新机器自己连回来；用完反过来注销。tycho 不认识门户，也不存门户凭据。别人用云厂商或者一台固定的服务器，换一个技能，或者什么都不用。

这要两样东西：一台已有的机器跑那个开实例的任务（或者主机自己当一台机器），和技能能拿到它需要的凭据。后者是技能和你的事，tycho 不经手。

机器消失走现有规则：判定旧执行已不在，自动接续。撤销接入材料不等于撤销它换出的机器身份，两种操作分开；机器离线时页面上要区分"已撤销接入"和"已确认进程停止"。

## 绑定

- **总控**：一个账号加一个档位，替代现在的三项设置。执行器要声明“能当总控”才可选。今天只有 Claude Code 能当：ACP 实测（`docs/spike/acp-evaluation.md`）说明，Codex 去不掉内置工具，dsh 不给逐段文字，这是能力问题，不是配置问题。
- **项目**：允许的登录（不带顺序），加允许的机器。
- **任务**：要哪一档；可以点名账号，不点名就由服务挑。

这部分已实现（2026-11-06，账本版本 9）：

- 设置里 `router.configDir`、`router.tierFile` 换成 `router.account`、`router.tier`；`router.cli` 照旧，因为它是这台电脑上程序的位置，不是账号的一部分。两个都是选择项，不是输入项：账号列的是执行器声明“能当总控”的那些，档位列的是所选账号自己的档位。
- 账号的令牌进总控自己的环境（`CLAUDE_CODE_OAUTH_TOKEN`）；配置照旧是这台电脑上的（账号只替换身份，[merged-design.md](merged-design.md) §1.1；账本版本 32 起账号没有登录目录）。不绑账号就是这台电脑已有的登录和档位，行为不变。页面和自检说成“账号 X 的令牌”。绑了但账号不在、执行器不能当总控、档位用不了（引用的文件不在，或内容会被 CLI 丢掉）、CLI 不接受这个登录，都只停摆总控并说明去哪里改，服务、控制台和消息入账照常。
- 运行中把绑定的账号删掉，同样只停摆总控：当前回合收尾后停下进程，排队消息留着等“重启总控”，不需要谁去点它才发现。
- 总控自己的登录被拒（适配器报 `auth`）是账号的一次失效：`login_state.credential_rejected_ref` 记下它启动时用的那个编号，账号在页面上显示“要重新填”，`pickAccount` 也跳过它——总控和 Worker 共享同一份账号状态。令牌换掉之后这次失败不再算数。
- 自检和设置页的部署信息分开说两件事：总控进程启动时用的是哪份凭据，以及下次启动会用哪份。启动时用的那个编号跟着这次启动记下来（`RouterLaunch.credentialRef`，是编号不是令牌）；它和账本里现在的对不上，就说运行中那份查不了，并说明查到的是下次启动会用的那一份。
- CLI 自己写回来的诊断（stderr、失败结果）在进入日志、状态、接口和通知之前先把令牌隐去。
- 会话的归属记到账号：之后再换账号就会开新会话，不会一直续接旧账号的对话。现在由执行器上下文记登录编号，只按登录判断换不换（[project-sessions.md](project-sessions.md) §1）。

**账号**和机器可以任意组合，只要那台机器在线、装了对应的执行器、在项目允许的机器里；**机器自己的登录**只在它那台机器上，换机器就不成立（[nodes.md](nodes.md) §1.2）。账号的“测试连接”查的就是这个（换到节点之后，就是问那台机器现在活不活、它报的执行器登录状态，见 [nodes.md](nodes.md) §11 第 5 步）。

## 插件

借 dsh 的三样：一项能力由接口、实现、使用方一起设计；插件声明自己的配置项，控制台按声明生成表单；注册可撤销，改配置不重启。

不借的：

- **没有特权内核**。tycho 的产品是“交代的事不丢、不重复、状态如实”，账本和九条底线不能换。
- **Cordis 依赖**。服务端零依赖，几个扩展点用一个小登记表就够。接口按“有名字的服务、声明依赖、能卸载”写，以后要外部插件时可以平移。
- **多层补丁叠配置**。一个主人一套部署，配置在账本里。

```ts
interface Plugin<C> {
  id: string;
  kind: 'executor' | 'channel';
  config: FieldSpec[];                // 控制台按它生成表单，和设置页同一套字段类型
  start(config: C, host: Host): Disposable; // 改配置就停掉重来
}
```

- **执行器**：现有适配器的四件事，加声明：凭据长什么样、怎么交给进程、档位长什么样、能不能当总控、怎么问登录状态。接 dsh 用 `dsh --profile headless --json`。
- **通道**：控制台、企业微信。

技能和知识不算插件：技能已经是随任务下发的文件，以后的知识记忆再看。机器不是插件，是对象。没有真实的第二种实现之前不加抽象。

需求已经成立——主人本人就是第二个作者，"在使用中给自己加能力"不是假想需求——但排期服从第一次可用闭环：先自迭代闭环和节点各步，外部插件目录排在第三阶段（[self-iteration.md](self-iteration.md) §5、§7）。真开的时候也只开"只加不改"的类型，先 `executor`、`channel`；控制台页面用 sandbox iframe；故障隔离用子进程，但同进程或同源的代码不是沙箱，只装信得过的。开发者规则里那张"想加某种新行为，挂在哪里"的表照旧要补。

## 迁移

账本升一个版本，每个执行目标拆成一个账号和若干台机器，内容相同的合并。总控的三项设置变成一个账号。

- 没有凭据的旧账号（用的是机器上已有的登录），由账本版本 18 并成它列的机器上的"机器自己的登录"（规则见 [accounts-machines-decoupled.md](accounts-machines-decoupled.md) §迁移规则的细节）。
- 档位旧值是“机器上的文件路径”，迁移时不读远端文件，保留为“引用机器上的文件”这种形式。后来档位只认内容（2026-11-10）：这种旧值不再是档位，那份登录不提供这一档，直到主人填上内容；账本读登录时把它读成“已失效的档位”，账号页、机器页、自检和钉住它的任务的停下理由都照这一份说原来写的是什么、去哪重填，带着它的登录不显示“可用”。
- 旧任务指向拆出来的账号和机器；旧 Run 的快照记着当时的配置，继续按它结算。
- 节点通道最初落地时，机器增加节点身份字段（平台、令牌哈希、来源、最近一次往来、临时标记），旧机器记录暂时保留为"还没有连回来"。最终删除 SSH（账本版本 24）时，删掉 `ssh_config` 列及未经客户端接入的机器；`host` 保留，表示客户端报告的主机名。旧 Run 快照里留下的 `ssh_config` 是历史，读的时候不认它（[nodes.md](nodes.md) §5.4、§11 第 6 步）。
- 升级前副本照旧。

这部分已实现：一步从版本 6 升到 7，升级前副本照旧，迁移测试对着 `tests/fixtures/ledger/schema-v6.sql` 建旧账本跑。版本 8 升到 9 是把档位值里的旧字符串包成 `ref`，版本 9 升到 10 是总控绑定那一步：`tunables` 里的 `router.configDir`、`router.tierFile` 变成一个名叫 `router` 的账号（名字被占了就 `router@2`），设置改成指向它，档位按 `{ kind: "ref", value: "<旧路径>" }` 记；两项都没设过就什么都不做，也不造账号。名字是空的、升级前没有 `tunables` 行，都是“没设过”。迁移测试对着 `tests/fixtures/ledger/schema-v9.sql` 建旧账本跑。

## 分步实现

每步单独能用：

1. **已完成**（2026-11-06，账本版本 7）：账号与机器的数据模型、迁移，页面只做到不退步。额度状态搬到账号上。
2. **已完成**（2026-11-06，账本版本 8）：凭据的保管、填写、下发到一轮执行，失效处理。只做了 Claude Code 令牌；Codex 和 dsh 的凭据留给它们各自的实测。当时下发走 SSH 标准输入；现在经节点通道的专用凭据通道交给这一轮，SSH 那条路已删除（[nodes.md](nodes.md) §9、§11 第 6 步）。
3. **已完成**（2026-11-06，账本版本 10）：总控绑定到账号，令牌和档位从账号取（当时还有登录目录，账本版本 32 删掉）；不绑就是这台电脑自己的登录。档位的内容写成 `<数据目录>/router/` 下的设置文件再交给 `--settings`（令牌不进这个文件）。
4. **已完成**（2026-11-06，账本版本 9）：档位内容随快照下发。档位的值分成“内容”（执行器自己的那份配置文本，随这一轮的快照到机器上）和“引用”（机器上已有的文件或名字，迁移包出来的旧形式；2026-11-10 起不再是档位，只认内容）；Claude 写 `runs/<run>/snapshot/tier.json`，dsh 写 `tier.patch.yml`，Codex 展开成 `-c` 参数不落文件。执行器自己的命令读不了的档位在下发前被挡住。同一天接着做完：控制台的档位表单只填模型和推理强度（dsh 还有 provider），取值和写法都取自适配器的 `tierForm` 声明，模型是自由输入、建议项来自账本里已经用过的模型；表单管不到的设置在这一行的“高级”里原样保留，改模型不会动它们；没有模型的档位在那一行被拒；新建账号开在固定两行上（决策档 `decide`、执行档 `execute`，见 [roles-and-tiers.md](roles-and-tiers.md) §2），一行留空就是这个账号不提供那一档；旧版本自起的档位名原样留着，行上标“系统不再用这个名字”，给一个改成决策档 / 执行档的动作。总控选档位的地方只列绑定账号真正持有的那两个名字，按页面名显示。接着做完（账本版本 11）：档位的模型和强度改成由登录的执行器报告——适配器的 `listModels` 声明怎么问、怎么读，服务在保存、改令牌、测试连接和定时（`models.refreshMs`，默认 6 小时）各问一次，读到的东西记在账号的 `account_state`，问不到就还用上次读到的；控制台按这份列表给下拉框，模型不在列表里就标出来并允许手填，新模型和消失的模型经 Outbox 各通知一次。见上面“模型列表”。
5. 插件登记表，现有的执行器和通道搬上去，加 dsh。
6. 总控的机器工具：**改现有的三个**——删掉 `add_machine`（不再让总控把 SSH 地址抄进账本），`list_machines` 加上连接状态和来源，`remove_machine` 改成"撤销这台机器"；新增 `invite_machine`（申请一次性接入材料）。开实例的技能不在本仓库。
7. 控制台改造按新模型重写设置、账号和机器、项目几页。
8. 机器改成自己连回来（[nodes.md](nodes.md) §11）：账本里机器的 SSH 字段换成节点身份，控制台换成"一条命令 + 六位数放行"；**删 SSH 放在这条队列的最后**。

顺序上，自我迭代第一步（沿用现在的 SSH 路径）跑通之后才开始节点各步，删 SSH 是节点各步的最后一步（[nodes.md](nodes.md) §2）。

## 仍不知道的

- **两个 Claude 账号同机并行是否互不影响。** 令牌单独能工作已实测（见下），但只有一个令牌，没有测过两个同时跑。
- **Codex 用 ChatGPT 订阅时能否这样用。** `codex login --with-access-token` 能从标准输入读令牌，但要往机器上的 `CODEX_HOME` 写登录文件，而且令牌会自动刷新，多台机器同时用一份可能互相顶掉。要实测。做不到就为每个账号每台机器保留“用机器自己的登录”。
- **dsh 的凭据形式（2026-11-11 实测后：账号的密钥随启动环境交付，三个服务保持关闭，见 [native-login.md](native-login.md) 文末；下面是当时的记录）。** provider 密钥是 `apiKeyEnv` 指定一个环境变量名，值由 credentials 服务取：默认 `<DSH_HOME>/.credentials.yaml`（`~/.dsh/.credentials.yaml`），优先级是它、进程环境、调用目录的 `.env`、`$DSH_HOME/.env`。headless 档默认把 `credentials`、`authorization`、`deepseek-account` 三个服务关掉（“一次性任务用启动时的凭据，不用交互式那份存储”），要用 `--patch` 的 `disabled: false` 打开；本机就是打开 credentials 后靠 `apiKeyEnv` 取到密钥跑通的。账号线路（`deepseek-account`）的凭据也由同一个服务管，`~/.dsh/.credentials.yaml` 里有它的记录，但 headless 下怎么启动、能不能用，没有实测。
- dsh 的 headless 输出已录入仓库：`--json` 是一行一个 JSON 事件，`session` 开头、`final` 结尾，中间是 `status`（`step_end` 带用量）、`text`、`thinking`、`tool_call`、`tool_result`；成功一轮、续接、缺凭据、被中断和用法错误各有一份实录（`tests/fixtures/dsh/`）。
- dsh 每次启动都会重写 `<DSH_HOME>/profiles/headless/cordis.yml`，所以 `$DSH_HOME` 必须可写；`--patch` 只收文件路径、相对路径按进程的工作目录算、一条 patch 里 `config` 是整块替换，都已实测（当时的记录没有落盘，依据是 `tests/fixtures/` 里的实录和适配器的契约测试）；Codex 的 `-c` 覆盖面同样。
- **三个执行器报告模型的方式，只有 Codex 有实录。** `codex debug models` 已录入（0.162.0，见 §账号的模型列表）；dsh 的 `--profile headless --dump-config` 有一份节选实录（`tests/fixtures/dsh/0.2.2-rc.1/dump-config-headless.yml`：随包的 profile 不写 `models:`，只写默认模型）；线路自己把 `models:` 写成哪种形状仍然没有实录，解析按 YAML 列表的常见写法猜，遇到真形状要对实录改；Claude 的 `GET /v1/models` 和 `claude --help` 是按公布的字段形状写的，也没有实录。三处都可能要按真实输出修，`tests/fixtures/*/README.md` 里写明了哪份是实录、哪份不是。
