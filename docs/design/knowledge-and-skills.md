# 知识与技能：经验进入下一次工作

读者：主人和实现者。状态：**已确认，分步实现中；第 1、2、3 步已落地，形状见 §8 之后的“第 1 步落地”“第 2 步落地”“第 3 步落地”**（11-09 补充的组织、归属、记忆、维护和"先生效、后审阅"均经主人确认）（2026-11-09 主人确认；协调者稿与 Codex 稿互审后的定稿，分歧裁决见文末）。按终态写，不做过渡兼容。

## 结论

目标是**让经过把关的经验进入下一次工作的实际输入**，而不是建一个自动堆文字的知识库；主人掌握最终修改权，但不被每一条打扰。

1. **tycho 账本是主人的工作方法和经验的唯一正本。** 主人散落在别处的方法和经验（个人指令文件、各会话的笔记、自己写的技能、总控的"长期裁定"）一次性迁进来，迁完以后要么删除，要么是 tycho 生成的只读文件。**外部维护的不迁：** 项目仓库里的、执行器在机器上装的、tycho 平台自带的，各有各的正本；tycho 不为它们建立第二份可编辑的正本（§1.2）。
2. **两种对象：知识回答"据什么判断"，技能回答"怎样完成"。** 两者都有作用域：全局，或者一组项目；还可以再按职能收窄。知识另有加载方式：常驻或按需。每次修改产生一个不可变的修订。**不建层级、不设领域：** 一条条目放在哪，只由归属、适用范围、加载方式、类型四个属性决定（§1.1）。
3. **只有一个进口：带证据的提议；默认先生效、主人事后审阅。** 提议来自执行者回执里的可选字段、总控、tycho 之外的会话（经知识 MCP）和主人自己。没有证据就提交不了。每份提议一进来，立即派一次独立的把关任务（只读、换一个执行器）去重、合并、核对证据和范围，通过就生效，标"未审阅"，主人有空时在控制台看、改或退役。只有两种仍要主人先点头：全局而且常驻的；改动或退役主人写过、审过的条目（§3）。
4. **出口全部从正本生成，每个出口都先按范围和职能选条目，再按加载方式决定给全文还是给目录：**
   - **tycho 派出的每一轮：** 只用这一轮的快照。常驻条目全文进 brief，按需条目和技能的正文作为快照里的文件随这一轮送达；超出大小上限就不开这一轮，并说明是哪些内容超了，不悄悄截断。机器上执行器自己的配置（全局指令、MCP、技能、记忆）照常生效，快照照实列出；只有 tycho 的知识出口（tycho 写的全局知识入口、主人装的知识 MCP）这一轮不读，因为同样的条目已按钉住的修订在快照里（§4.1）。
   - **总控：** 每一回合带上不限职能的全局常驻条目全文和其余条目的目录，正文经工具读取。
   - **tycho 之外的会话：** 不限职能的全局常驻条目由机器客户端写进执行器自己会加载的全局指令入口（位置和接法由适配器声明）；其余经知识 MCP 读取。
5. **生效的条目要维护，历史可以增长。** 一份提议可以同时合并、拆分、抽象、提升或退役多条现有条目，一次发布、一个事务生效。整理由事件触发（反例、接近大小上限、项目阶段结束），由一次只读的分析任务出候选，按 §3 发布。不做后台自动改写，不按年龄或频率自动退役，不做健康看板（§5）。
6. **记忆不另设对象。** 业界说的"记忆"是几件不同的事，在 tycho 里各有归属：发生过什么是账本里的 Run、回执和时间线；学到了什么是知识与技能；这一轮的上下文归执行器；同一任务的接续靠会话续接和任务历史。执行器自带的持久记忆归执行器，派出的轮次照常读写它（审阅、知识把关和整理这些要独立视角的轮次除外），快照标明；它不是 tycho 的知识，跨任务的经验要进账本只有经提议、把关这一条路（§1.3）。

任务页的「任务反馈」提供经验维护的线索：值得复用、太慢、结论错误，连同任务及来源轮次的修订进入既有变更记录。总控通过 `get_task` 读取后，可以沿下述证据提议流程处理。反馈本身不构成知识，不绕过独立把关或主人确认门。

## 1. 对象

| 字段 | 说明 |
|---|---|
| 类型 | 知识或技能，发布后不能互换 |
| 标题、什么时候用 | 什么时候用，就是技能检索的主要入口；知识写触发情境 |
| 正文 | 知识写结论、依据和边界；技能写在哪里做、以谁的身份做、按什么顺序、怎样算成功、失败后留下什么 |
| 作用域 | 全局，或者一组项目（一个或多个，显式列出）；职能列表可选，空表示不限。"全局"必须显式写明，不能根据措辞推断 |
| 加载方式（只有知识有） | 常驻：全文给到；按需：只给标题和触发情境，正文另取（§4 各出口怎么取）。技能一律是"目录给到、正文另取"。加载方式是修订的一部分：改它就是一次新修订 |
| 修订 | 不可变，引用一律精确到修订号 |
| 证据 | 支撑这一修订的证据，见 §2 |
| 发布记录 | 谁提议、哪次把关、谁点头（如果要）、什么时候；审阅状态：未审阅 / 已审阅（主人看过或主人自己写的） |
| 状态 | 可用 / 已退役（附理由和替代它的条目） |

运行状态不进知识库：实例地址、待合分支、账号歇到几点这类内容，从现有对象里查。技能是 Markdown 说明，不是插件，不带 hooks、权限或后台执行；需要脚本时，引用项目仓库里随代码一起管理的脚本。

### 1.1 组织：四个属性，不建层级

| 属性 | 回答什么 | 取值 | 谁用它 |
|---|---|---|---|
| 归属 | 正文在哪改 | 账本 / 外部维护（§1.2） | 决定改动走哪条路 |
| 适用范围 | 哪些工作该用它 | 全局 / 一组项目，加可选职能 | 派发时挑条目 |
| 加载方式 | 什么时候进上下文 | 常驻 / 按需 | 生成快照与 brief |
| 类型 | 判断依据还是做事方法 | 知识 / 技能 | 正文模板与审核标准 |

为什么不建层级：

- **会出问题的是每一轮带了多少，不是库里有多少。** 同时生效的指令越多越容易被漏掉，和目标主题相近的干扰内容最伤（附录）。所以要管住的是"常驻"那部分；"一组项目"让只适用于两三个项目的经验不必升成全局；"按需"让参考类的内容不占常驻。
- **没有证据支持在这个规模上树化。** 分层摘要的实验收益出现在长对话、大语料的问答上，而且检索时不必沿着树逐层走；对几十到几百条、几个项目的规模，没有找到"该树化"的阈值，层级在这里的边际价值没有被证明。将来真要跨条目归纳，可以另加一个能随时重建的摘要索引，不改正本的组织。
- **不设"领域"。** 领域最主要的用途（跨几个项目、但不是全局）由"一组项目"覆盖；按主题过滤还要让任务也声明主题，多出一个实体，目前没有使用方。真实任务里出现"同一项目内不同主题互相干扰"时再加。
- **不设"准则"一级。** 约束力强的规则就是"全局 + 常驻"；一条准则也可能只适用于一个项目，所以它不是一个层级。

### 1.2 外部维护的知识和技能

执行者实际读到的东西，不只来自 tycho 账本。归属只分两种：**账本接受正文修改的**，和**外部维护的**。后者 tycho 不建立第二份可编辑的正本，也不认任何具体的分发渠道；缓存、快照里的不可变留档不算第二份正本。

外部维护的内容怎样到达一轮，常见的有下面几种（举例，不是穷尽）：

| 到达方式 | 例子 | tycho 做什么 |
|---|---|---|
| 随项目代码到达 | 仓库里的指令文件、技能目录、文档 | 什么都不做：由执行器按自己的规则加载。快照里的代码提交号记下了被提交、被打包的那部分；仓库外的链接目标、外部引用、运行时生成的内容不在其中 |
| 机器上的执行器环境 | 用户级技能、插件、执行器自己的配置，不论从哪里装来 | 不管理、不屏蔽，也不据此派发：照常生效，账号只替换身份（定位见 [merged-design.md](merged-design.md) §1.1）。快照如实标出"这一轮还会读到机器上执行器自己的配置"；执行器能不耗额度报告的清单（全局指令文件、MCP 服务器、技能、插件），适配器声明怎么问、哪些问法会启动 MCP 服务器、因此不问（`unasked`），机器在上报执行器时报上来，派发时记进快照，注明是什么时候问到的；报告不了的就是未知，随登录带来的（例如 Claude 账号在网页上连的远端连接器）机器报不出来，也记未知；不把"没报告"当成"没有" |
| tycho 平台自带 | 给执行者的交付约定：产物放哪、派生的机器怎么报告销毁 | 随发布包走，由快照生成器按条件写进 brief；它是平台协议的一部分，跟着代码版本变，不经主人批准 |

- 同一份内容的两种身份不冲突：主人自己写、装在机器上的技能，正文若在账本里维护，它就是账本的，机器上那份是投影；正文若在别处维护，它就是外部的。决定归属的是"正文在哪改"，不是"放在哪"。
- 想改一份外部维护的技能，就去它的正本那里改。想要一份自己的改编版，就把它当作摘录提交成新的提议，从此归账本，不和原来那份同步。
- 不按"机器上装了什么技能"挑机器：可见的技能还取决于账号、工作目录、插件启用和会话状态，名字在不同执行器之间也不是同一个身份。真有任务离不开某个外部技能时，再看它要的是一份技能文档（那就随任务提供）、一个工具依赖、还是一项机器能力。

### 1.3 记忆

"记忆"在 agent 的文献和产品里指几件不同的事，tycho 不为它另设对象，而是逐一落到已有的归属：

| 说的是 | 在 tycho 里 |
|---|---|
| 这一轮的上下文（工作记忆） | 归执行器，tycho 不自研 |
| 发生过什么（情景记忆） | 账本：Run、回执、时间线、日志、证据，本来就是正本，也是知识提议的证据来源 |
| 学到了什么、怎么做（语义与程序性记忆） | 知识与技能 |
| 主人的偏好和交互约定（用户画像） | 主人定的全局知识，走同一个进口 |
| 同一件事做到一半（接续） | 执行器会话续接，加上任务修订、历史与回执进下一轮 brief |
| 将来要做什么 | 任务、预约、待送达的插话 |

保存了经历不等于能跨任务回忆起它。以后真出现"找上次类似的事"这类需求，先给现有的 Run、任务和证据加查询入口，再看检索够不够，不为此另建记忆对象。

**执行器自带的持久记忆**（执行器自己写、下次启动自己读的笔记）归执行器，和机器上它的其余配置一样透传：

- **派出的轮次照常读写它**，快照上标出这一轮会读写哪一种（没有、只在任务内、跨任务、说不清）。
- **要独立视角的轮次关掉它**：审阅，以及知识的把关和整理。执行器的记忆可能带着它在别的轮次里对同一件事的看法。用执行器自己提供、在实录上验证过的开关，快照上记下用的是哪种；关不掉或确认不了的，快照上标"这一轮可能读到执行器自己跨任务的记忆"。
- **它不是 tycho 的知识**：tycho 不读它、不迁它、不担保它对不对。跨任务的经验要成为 tycho 的知识，只有经提议、把关这一条路。
- 这些都由适配器声明（有没有这类记忆、范围多大、怎么关），tycho 不猜。
- **tycho 之外的会话**：执行器自己的笔记归执行器管，tycho 不承诺它是会话私有的；只有经提议、把关的内容才是 tycho 的知识。

**人格不另设对象。** 长期陪伴型 agent 常有一份"语气、立场、身份"文件，而且 agent 能自己改它。tycho 不需要：执行者一轮就结束，怎么做由职能、权限、brief 和知识决定；总控需要的是稳定的交互约定（用什么语言、先给结论、什么时候打扰主人、怎么报告不确定），这些是主人定的全局知识，走同一个进口；名字之类的展示属于设置。

## 2. 进口：带证据的提议

- **执行者**：回执里加一个可选字段 `learned`，填候选内容和证据。brief 写明"只在有可复用的结论时写"；没有空模板，也不要求每一轮都回答"学到了什么"。这个字段写坏，不影响这一轮业务交付的结算。
- **总控**：用工具提交。提交前要能答出三件事：下次在什么情形下会用到它；它改变的是哪一个判断或动作；有什么证据支持把它推广出去，边界在哪。
- **审阅打回不自动生成提议**：一处缺陷只证明这里错了，不等于该加一条长期规则。审阅意见保留，总控可以引用它来提。
- **外部会话和主人**：知识 MCP 的 `propose_learning`，或者控制台。外部客户端提交实际的摘录或附件；服务不会按请求里给的路径去打开主机上的文件，也不会去抓取链接。按"客户端身份 + 请求编号"去重。

**证据**统一记录这几样：来源（Run、任务、提交、外部对话、文件、命令输出、主人原话）、位置（带版本）、摘录、采集时间、摘要哈希、提交者。服务能核实的，比如 tycho 内部的对象，标"已核实"；核实不了的外部摘录，标"提交者提供，未核对原记录"。证据摘录随修订保存；凭据和无关的私人内容不进摘录。

提议提交审核后，内容冻结。冻结的是整份变更：涉及的每条输入的修订号和当时是否生效、每份输出的正文、作用域、加载方式与触发描述、证据、每条输入的去向。任何一项改了，都算新的候选，旧的把关结论和主人的点头不能沿用。

## 3. 把关与发布

主人 11-09 定：知识不该因为等主人而不生效，也不该拿每一条去打扰主人。所以默认是**把关通过即生效，主人事后审阅**；主人先点头只留给影响面最大、最容易出事的两种。

**把关任务**：每份提议一进来，服务立即为它建一个**分析**职能的任务（只读），不攒批。它和审阅同一个原则：不由写的人检查自己写的，执行器要换一个（复用审阅"排除写过产物的执行器"那一处判定）。它在快照里拿到这份提议、证据和相关的现有条目（服务按作用域和相似度挑出），做四件事：

- 去重：和现有条目说的是同一件事，就并进去（改成对现有条目的修订），或者驳回；
- 核对证据撑不撑得住它说的范围，写过头的收窄；
- 对涉及技能的变更，检查步骤能不能完成工作、会不会做错操作；
- 只改措辞、不改判断或动作的，驳回。

结论经回执交回：通过（原样或修改后的冻结变更）/ 驳回（附理由）。它不能写账本，发布由服务按下表执行。

**把关和整理任务不属于任何项目**：它们维护的是知识库，不是某个项目的代码。项目只记作来源。执行资源这样定：

- **用哪些登录**：设置项 `knowledge.logins`（一份登录列表，只定能不能用；先找谁按档位的全局派发顺序，roles-and-tiers.md §11），空表示主人的所有登录都可用；照常排除写这份提议的执行器。
- **在哪些机器上跑**：必须是这份变更涉及的每个项目都允许的机器（取交集；全局的不限），因为把关材料里有这些项目的内容，不能送到项目不允许的地方；还必须报告了只读可用。交集为空就停住，说清是哪几个项目的机器范围没有交集。
- **只读是结构保证**：知识任务不论挂哪个职能，权限一律只读，在建任务、换职能、建 Run 三处由同一个判定拒绝可写的配置，不依赖"分析"职能当前的设置。主人在控制台新建或修改的，主人自己就是把关，直接生效、标"已审阅"。

| 变更 | 把关通过后 |
|---|---|
| 一般情况：项目范围的、按需加载的、新增的、修订或退役 agent 写的条目 | 立即生效，标"未审阅"，进主人的待阅列表 |
| 全局而且常驻（新建、改为常驻、扩到全局、修订已是全局常驻的） | 等主人点头：它进入所有项目的每一轮 |
| 改动或退役主人写过、审过的条目 | 等主人点头：后台整理误删仍有效条目，正是同类产品出过的事（附录） |

- **事后审阅：** 待阅列表里，主人可以标"已审阅"、直接改（改完即"已审阅"）、退役，或者跟总控说一句让它提修订。不用审也照常生效。
- **打扰：** 只有"等主人点头"的那两种发企微卡片（只放摘要和"打开"入口，全文在控制台看）；其余只进控制台的待阅列表，不推送。
- **驳回的**保留在提议记录里，附把关任务的理由；同一内容再提，把那次驳回摆在新提议上。
- **不碰任务状态：** 只复用 Approval 的展示、白名单和 Outbox，不复用它让任务继续排队的语义，知识发布不改变任何任务的状态。
- **一次事务：** 不论自动生效还是主人点头，发布都在同一个事务里完成：核对冻结变更里每条输入的修订号和生效状态都没变 → 更新可用版本 → 记录审计 → 发通知。两个候选基于同一份旧修订时，先发布的生效，另一个必须重新处理差异；输入在等待期间被退役，也一样。

## 4. 出口

### 4.1 tycho 派出的每一轮

- **怎么选：** 派发时，按任务所在的项目和当时的职能选出可用的条目，在建 Run 的同一个事务里写进快照，快照记下每条的修订号和加载方式。
- **只用快照：** 这一轮 tycho 的知识和技能全部来自快照。按需条目和技能的正文作为快照里的文件随这一轮送达，brief 里的目录指向这些文件；执行者在机器上直接读文件，不在线查当前版本。
  - 机器上执行器自己的配置照常生效（§1.2），快照记下机器报告的清单。例外是 tycho 的知识出口（§4.3），它们不能成为这一轮的第二个入口：同样的条目已按钉住的修订在快照里，机器上的可能是另一个修订（例外的总述见 [merged-design.md](merged-design.md) §1.1）。
    - 全局知识入口：适配器声明怎样让执行器这一轮不读这一份文件，并在实录上验证；做不到的，快照上标"这一轮还会读到 tycho 写在机器上的全局知识入口"。
    - 知识 MCP：主人装在机器上的知识 MCP（名字固定是 `tycho-knowledge`，见 [../deploy.md](../deploy.md)），派出的轮次也看得见。适配器声明怎样在启动参数里按名字关掉一个 MCP 服务器（实录上验证），派出的轮次在实测过的版本上关掉它：Claude 从 2.1.303 起带 `--disallowedTools mcp__tycho-knowledge`，低于或版本不明就不带、记“可能用到”（和记忆开关的 `since` 同一个写法）。关掉了的，这一轮读不到快照以外的条目，也提不了绕开回执的提议（这一轮的提议只走回执的 `learned`）。适配器没有按名字关 MCP 的办法（dsh 还没实测）、主人装成了别的名字、或者机器的版本低于实测，就关不掉：快照的 `machine_inputs` 标“这一轮可能用到机器上的知识 MCP”。
  - 记录分三种，不混：确定送达的修订（快照）；执行器有可靠记录可证的读取；其余读没读是未知。不把未知记成"没读"。
- **brief 的顺序：**
  1. 任务目标、验收和权限；
  2. 常驻知识：先全局，再项目（同一组里先列不限职能的，再列匹配职能的）；
  3. 按需知识的目录（标题和触发情境），与技能目录，以及任务点名的技能全文；
  4. tycho 平台的交付约定（§1.2）；
  5. 历史和回执规范。

  先后顺序不代表后面的覆盖前面的。知识不能悄悄修改验收要求；要改验收，就改任务修订。
- **审阅轮：** 审阅仍走它自己的生成路径，不经知识入口夹带作者的报告或还没批准的复盘。
- **大小上限：** 都登记成设置项，按 UTF-8 字节，算的是最终生成的输入，不是哪个作用域里存了多少。超了就不开这一轮，说明是哪些内容超了，不截断。

  | 上限 | 默认值 |
  |---|---|
  | brief 里的常驻知识正文、两份目录和任务点名的技能全文 | 24 KiB |
  | 快照里的知识与技能文件合计 | 512 KiB |
  | 单条正文 | 32 KiB |
  | 单份提议的证据摘录 | 256 KiB |

- **重开会话：** 一轮适用的修订集合或它们的加载方式变了，下一轮就重开执行器会话（工作目录保留），这样已经退役的规则不会在旧会话里继续生效。

### 4.2 总控

- **带着什么：** 每个项目有自己的总控（[project-sessions.md](project-sessions.md) §3），它只带全局和本项目里不限职能的条目：常驻条目的全文在一个执行器上下文开始时随恢复材料送一次（并留档），按需条目给目录，目录变了才随下一回合再送；常驻正文被修订、退役或不再适用，就在下一条消息前换上下文。限了职能的条目、别的项目的条目不进总控的输入。
- **按需读取：** 用 `get_working_context` 和 `read_library` 读正文，读回的内容带修订号。
- **只能提议：** 总控只能提议，不能发布。`note_decision` / `list_decisions` 已删除（账本版本 20）：每条旧裁定转成一份带原始记录作证据的提议（来源“迁移的长期裁定”），分类交给正常的把关——任务内的决定被驳回、留在把关记录里，长期有效的生效；旧表和它的读法一起删掉，不留旁路（[project-sessions.md](project-sessions.md) 第 1 步实现记录）。

### 4.3 tycho 之外的会话（Claude、Codex、dsh）

- **全局常驻条目可以通过外部会话入口加载。** 在设置里打开「将全局常驻知识写给 Tycho 之外的会话」后，机器客户端和主机按执行器声明的原生入口发布。新服务默认关闭，已使用的账本升级后保有原设置。关闭只撤下本知识发布集合的文件；其他发布方、旧版归属不明的投影和用户文件保留。执行器何时采纳这份文件由原生加载规则决定。
  - 内容是一段接入说明，加上**不限职能的全局常驻条目**；限了职能的、按需的、项目的都不进这份文件，走 MCP。有大小上限。
  - 文件头写明"由 tycho 生成，勿改；正本在 tycho"，并注明修订和生成时间。
  - 在机器页看写入结果。节点同时报告原生入口中是否仍有 Tycho 文件和该文件的修订号。普通轮次在详情里显示重复、版本不一致或状态未知。
  - 正式审阅与知识把关使用固定的 Tycho 知识快照和新会话。调度先核对是否能隔离同名知识 MCP，再按执行器适配器的实测能力排除入口。无法按轮排除时，外部入口须已关闭，机器报告无投影，看管进程也在启动前复核。Codex 没有配置该 MCP 时，看管进程会用本轮工作目录再核对一遍。机器上的项目指令、普通技能和其他原生配置继续按各执行器规则加载。
- **其余条目：按需读取。** 知识 MCP 只提供四个工具：
  - `get_working_context`：某个项目、某个职能的当前知识和技能目录（常驻条目给全文，其余给目录）；
  - `search_library`：在明确的范围内查找；
  - `read_library`：读指定的修订；
  - `propose_learning`：只提交，不发布。

  读取和提交是两种授权。MCP 的令牌在控制台签发和吊销，只能从本机或节点通道访问，拿不到总控的工具，也拿不到本机令牌接口。知识读取授权不包含原始任务、轮次或消息的读取。MCP 提议返回受理结果，不立即回显摘录是否命中这些原始记录；服务仍核验证据供独立把关。未获知识读取授权的客户端也不收到旧条目的匹配内容。提案发布后的知识读取照原有授权进行，不新增客户端配置。
- **必须如实承认的边界：** tycho 能证明工具返回了什么，但不能保证一个不归它派发的会话一定会去读、会遵守。所以全局常驻条目走启动时加载的入口，其余靠接入说明和 MCP。服务不可用时，明确说"知识服务不可用"；没查到时，明确说"在这个范围内没找到"。不悄悄退回去读旧的 memory。

## 5. 维护：整合、退役、抽象、提升

> 本节 2026-11-09 补充。起因：主人问"只增不减会不会无限膨胀，要不要定期抽象、合并项目知识、把跨项目的提炼升级"。依据是两份调研（论文与产品记忆系统；Hermes Agent 与 OpenClaw），结论和出处见文末"附：维护的依据"。

### 5.1 结论

1. **限制的是"生效的条目"，不是历史。** 修订、退役记录和证据可以一直增长，它们不进任何一轮的输入。要管的是当前可用的条目，以及每一轮实际生成的输入（§4.1 的上限管住后者）。
2. **整理是一种提议，不是后台改写。** 一份提议可以同时涉及多条现有条目：合并、拆分、抽象、提升、退役，一次发布、一个事务生效（§2 冻结整份变更，§3 发布时核对）。没有任何进程能绕过 §3 的把关直接改正本，包括整理本身。
3. **整理由事件触发，由一次有边界的分析任务出候选。** 不常驻一个"记忆 agent"，不定期把整库重写成摘要。

### 5.2 一份提议能做什么

| 操作 | 什么时候用 | 发布后 |
|---|---|---|
| 修订 | 同一结论的内容或边界变了 | 新修订生效，旧修订留作历史 |
| 合并 | 几条实际在指导同一个判断，合起来能完整写出各自的条件 | 新条目生效，被完整取代的输入条目同时退役，退役理由指向新条目 |
| 拆分 | 一条里混着几个独立机制、不同作用域或不同流程 | 拆出的条目生效，原条目退役并指向它们 |
| 抽象 | 几条经验背后是同一个机制，但各自还有独有的细节 | 新增高一层的条目；只有独有内容被完整覆盖的底层条目才退役，其余保留 |
| 提升 | 已有条目要扩大到别的项目或全局 | 作用域扩大，按 §5.4 的五问补证据，按 §3 发布（扩到全局而且常驻要主人点头） |
| 退役 | 错了、被取代了、没有消费者了，或者应该由系统直接保证 | 停止生效，保留理由和去向 |

规则：

- **钉住输入。** 提议列出它涉及的每条现有条目的修订号，并说明每条输入的去向（保留 / 修订 / 被哪条取代 / 退役）。被引用为"取代者"的现有条目也是输入（去向通常是保留），一样钉住。这些都在 §2 的冻结范围里，发布时按 §3 核对。
- **展示损失。** 审批页逐条列出：哪些条件、例外或动作被删掉了，挪到了哪里；以及按 §4.1 的同一种算法，每个受影响的"项目 × 职能"组合实际生成的输入各增减多少。只比长短不算数：去掉重复的文字和去掉唯一的适用条件，字数都会变少，后果完全不同。
- **一个决定一份提议。** "这三条由这一条取代"是一份；不相干的整理分开提，不打包成"清理一批"。
- **只改措辞、不改判断或动作的，不提。**

### 5.3 什么时候整理、谁来整理

整理候选由一次**分析**职能的任务产出，用的全是现有的任务、职能和进口，不新增对象，也不给 Worker 加工具：

- **输入随快照送达：** 要整理的条目修订和必要的证据作为这一轮快照里的文件送到，和 §4.1 的按需正文同一种方式。
- **候选经回执交回：** 执行者在回执里交一份多条目变更（§5.2 的形状），由服务按 §3 发布；它不能写账本。整理任务本身就是一次独立把关，它交回的变更不再另派把关任务。
- 一次只处理一个主题或一组相关条目，允许结论是"没有值得改的"。

新提议的去重与合并已经由 §3 的把关任务顺带做了。此外的触发（都由服务或总控建任务，不是定时全库扫描；同一组条目已有没结束的整理任务，就并进去，不另建）：

| 触发 | 谁建任务 | 整理的范围 |
|---|---|---|
| 出现反例或冲突（执行者、审阅指出某修订不成立） | 总控 | 那条和与它同主题的条目 |
| 某个"项目 × 职能"组合实际生成的输入接近 §4.1 的上限（设置项，默认 75%） | 服务 | 进入这个组合的条目；优先找重复和放错作用域、放错加载方式的 |
| 项目阶段结束、方向改变、接口或环境换了 | 总控或主人 | 依赖这些前提的条目；同时找值得提升的 |

不设固定周期，不按"多久没被读过"触发：读没读多数时候是未知（§4.1）。§4.1 原有的"超了就不开这一轮"保留：整理触发在上限之前，正常情况下走不到拒开。

### 5.4 跨项目提升的五问

提升提议必须回答：

1. **共同机制是什么。** 去掉项目名后，哪个判断或动作仍然成立。
2. **证据是否独立。** 来自不同环境、不同约束的几次，还是同一次事故被转述了几遍。
3. **反例。** 至少写出一个不该用这条的情境。
4. **在目标范围验证过吗。** 用没参与提炼的案例看它是否帮到决策、有没有引出坏动作；没验证就写"没验证"。
5. **加载方式。** 扩大到全局不等于每一轮都带：要改为常驻，单独说明它相对按需读的收益，因为常驻的全局条目占的是所有项目每一轮的输入。

主人亲口定的偏好可以直接是全局的，不走这五问；反过来，一条项目经验重复再多次，也可能只适用于那个环境。

### 5.5 发现过时与矛盾

发现入口不变：执行者用了某修订后发现不成立；审阅发现某条与现状不符；提议者提交时要列出相关现有条目，说明是重复、替代还是冲突（服务给出候选）。

- **同一结论变了：** 修订原来那一条。
- **结论错了或者没用了：** 退役，历史证据保留。
- **适用条件不同：** 把边界写清楚，或者拆成不同作用域的两条。
- **全局和项目冲突：** 不隐式地让项目优先，由主人明确修订。
- **一次重现不了：** 只记下反例，不自动退役。
- **退役的不能被悄悄学回来：** 新提议的证据与某条已退役条目的证据重合，或内容与它实质相同时，服务把那条退役条目和理由摆在提议上和把关材料里，提议者必须说明退役理由为什么不再成立；说明不了，把关驳回。被主人退役的条目这样回来，算"改动主人审过的条目"，等主人点头。
- **同一类错误反复出现，而条目一直在：** 先问这条是否真的送进了那一轮（快照可查），再问它该不该由代码、工具或环境直接保证。是后者就修系统，然后退役这条提醒，而不是再加一条同义的。

### 5.6 怎么知道整理有用

快照已经记下每一轮带了哪些修订。在此之上只看这几样，都从现有记录里算，不另建看板：

- 生效集合的大小，按作用域；
- 同一条目被反例指到的次数，以及同类错误是否复发；
- 主人对同一类问题的纠正和干预次数；
- 把关的驳回率；主人事后审阅时改动或退役的比例（自动生效的条目被主人推翻得多，说明把关太松）；主人点头那两类的等待时长。

"被引用了几次""执行者说有帮助"只用来排序，不作为提升或保留的证据。

### 5.7 不做的事

| 不做 | 理由 |
|---|---|
| 定期把全库重写成更短的摘要 | 整体重写会丢掉边界和细节，ACE 的实验里成绩掉到不用记忆的水平之下 |
| 按年龄或使用频率自动退役 | 低频不等于没用：安全和事故类的经验恰恰很少触发 |
| 按语义相似度自动合并 | 相似的两条可能条件相反，或者一条讲原因、一条讲操作 |
| 不经独立把关就改正本，也不保护主人写过的条目（Hermes 的 Curator 对 agent 自建的技能、OpenClaw 的 dreaming 对长期记忆文件，都是同一个进程既判断又改写） | tycho 也是先生效、后审阅，但写的人和把关的人分开，主人写过审过的、全局常驻的仍等主人；回滚能救回内容，救不回其间已经用错它的那些轮 |
| 把自评"有用"当作提升证据 | 自报和任务成功都不能归因到某一条 |
| 每次审阅打回都加一条长期规则 | 已在 §2 定过：缺陷可能该由代码、接口或环境修 |
| 现在就上知识图谱、向量库或专门的记忆框架 | 当前规模没证明它们的边际价值；先用账本加任务跑通整理闭环 |
| 容量吃紧时自动删旧条目腾地方 | Hermes 就出过这种事：后台整理悄悄删掉了仍有效的记忆条目，后来改成无人值守的删改必须暂存 |

## 6. 迁移（一次性，显式操作）

迁移是一个通用的显式操作：主人指定一批来源（个人指令文件、会话笔记目录、技能目录、总控的长期裁定），tycho 按下面五步把其中归主人的内容变成账本条目。哪些来源、在哪台机器上，由主人在控制台选，不写死在机制里。

本机这一次的来源是 dotfile 的原则、各会话的 memory、数据目录 `skills.dir` 下的技能文件、总控的长期裁定。仓库 `skills/` 下的两份按 §1.2 分流：`spawn-machine.md` 是平台的交付约定，并进快照生成器；`release.md` 是 tycho 这个项目自己的做法，留在 tycho 仓库里，随代码包到达。

1. **采集。** 主人在控制台选择来源，在来源所在的机器上读取，保存清单、原文摘要和必要的摘录。
2. **整理成候选。** 把当前有效的结论、历史纠正、临时现场和重复内容分开。"进度/现状"类的不迁。找不到原始证据的，标"待补证据"，不批量发布。
3. **发布。** 同一主题只保留一个当前结论。迁入的是主人自己的原则和偏好，由主人在控制台过一遍后批量发布，标"已审阅"；原文件里写着的"已批准"不能顶替这一步。
4. **验证真的用上了。** 在机器上每个装了的执行器的真实会话里，和一轮 tycho 执行里，验证读取、使用、引用和提议这几条路都通。
5. **切换。** 已经迁完的范围一次撤掉旧的：删掉旧的知识正文；个人指令文件改由 tycho 生成（§4.3）；删除 `readSkills` 和 `skills.dir`。写进全局知识："值得跨任务保留的，经 tycho 提议；执行器自己的笔记不承担长期知识。"

正式切换前要复核来源文件的摘要；整理期间来源又被改过的，停下来核对差异。删除来源文件、改变 dotfile 正本之前，先把完整清单交给主人看。同一条内容不能同时由旧文件和 tycho 接受修改，不做双向同步。

## 7. 第一批数据

第一批是 TY总控 11-06→11-09 的 12 条经验，已经带着证据整理在 [../knowledge-seed/ty-lessons-2026-11-09.md](../knowledge-seed/ty-lessons-2026-11-09.md)。按本设计分流：

- 稳健的方法进知识：有的是全局的，例如 E1 承诺与检查、E2 差距分解、E7 方向变了就停掉在途片；有的只属于 QL 项目；

这 12 条也是第一次整理的练习：它们更需要去重、改掉过强的表述、拆开混在一起的条目，而不是再抽象成几条更空泛的原则。例如 E2、E4、E5 适合合成一份"提出并验证性能方案"的技能，但"归因""选型公平""数字可信"是三个判断，不能压成一句"先测量再优化"；E12 混着脚本发布、brief 校验、续跑探针几件事，要拆开，其中已经是待修缺陷的直接修系统。

5. **整理：** 提议的形状是"一组钉住修订和生效状态的输入，加输出与去向"（第 1 步的提议对象直接按这个形状建，不留单目标的读法）；审批页的损失与输入大小变化；整理任务的输入随快照、候选经回执；§5.3 的触发。用第 7 节那 12 条跑一次真实整理。

## 第 1 步落地：形状

第 1 步已落地（`knowledge-1` 分支），连同 §3 的"先生效、后审阅"、§5.2 的多条目变更和 §5.3 的整理任务一起建成终态形状，没有单目标的提议读法，也没有只能选一个项目的读法。§4.3 的执行器全局入口和 §1.3 的执行器记忆是第 2 步；技能是第 3 步，提交技能现在会被拒。

**账本**（版本 19，在 18 上加一版）：`knowledge`（条目：类型、现行修订号、可用或已退役及理由和取代它的条目）、`knowledge_revision`（不可变修订：标题、什么时候用、正文、作用域、加载方式、职能、来自哪份提议、由谁生效）、`knowledge_proposal`（一份变更：提交时的变更和把关通过后真正发布的变更、三个问题的回答、来源与提交者、请求编号、两份摘要、上一次同样内容的驳回、把关任务与它的结论、为什么要等主人、状态与决定、生效时间、审阅时间）、`knowledge_evidence`（每份提议的证据，随修订保存）、`knowledge_client`（知识 MCP 的客户端：名字、它跑在哪个执行器上、授权、令牌的哈希）；任务多一列 `knowledge_json`，标出它是把关任务还是整理任务，任务的项目可以为空（把关和整理任务不属于任何项目；SQLite 不能放宽一列，升级时任务表照原样重建、逐行拷贝；只有这一步在关掉外键检查的情况下跑，并前后核对引用，其它升级步骤照常开着）。修订的审阅状态读自它的提议，不另存一份。

- **一个进口，一种形状**（`service/knowledge.ts` 的 `propose`）：回执的 `learned`、总控和知识 MCP 的 `propose_learning`、控制台新建，交的都是一份变更——`inputs` 是涉及的现有条目，各自钉住现在的修订和生效状态并写明去向（保留 / 修订 / 被取代 / 退役），`outputs` 是要生效的条目（新建，或者修订某条输入），每份写明作用域（全局是 `project_ids: null`，否则是一组项目）和加载方式。每条输入都要有去处，什么都不改的不收。没有证据、凭据进了摘录、正文或证据超限，都收不下；按"客户端 + 请求编号"去重。
- **把关**（§3）：主人以外的每份提议在同一个事务里建一个"分析"职能的把关任务，不攒批，排除写它的执行器——执行者回执来的排除那一轮的执行器，总控提的排除能当总控的执行器，知识 MCP 提的排除签发令牌时写明的执行器；排除和审阅共用 `excludedExecutors` 一处判定，挑登录、钉登录、建 Run 都用它，没有合格的登录时任务停住并说清。把关任务的快照里带这份提议（变更、三个回答、证据、同样内容上一次被驳回的理由）和它涉及或相近的现有条目（按作用域相交、按字符相似度挑前几条），都是快照里的文件。结论写在回执的 `knowledge_verdict`：通过（原样，或者改过的整份变更）或驳回（附理由）；写坏是"交付不齐"，任务停住、提议原样等着。结论被采用后任务直接结束，不进待验收，也不再叫醒总控。
- **发布**：把关通过的，一般立即生效、标"未审阅"、进待阅列表，不推送；全局而且常驻的输出、改动或退役主人写过审过的条目，等主人点头，只有这两种发企微卡片。主人在控制台新建、修改等待中的提议、在待阅里直接改的，直接生效、标"已审阅"。发布在一个事务里核对每条输入的修订号和生效状态，动过就不发布、标"依据的修订已变"；生效时写修订、退役被取代或退役的输入、让钉住了这些条目的其它等待中提议变成"依据的修订已变"、记审计，不碰任何任务的状态（只有把关任务自己结束）。主人点头带着他看到的那份摘要（把关通过后的变更），两个通道同时点只提交一次。驳回的留在提议记录上；同样内容（不看钉的修订号）再提，新提议上带着那次驳回。
- **主人看什么**：待阅列表（已生效、未审阅）里可以标已审阅、直接改、退役；"等你点头"列表；每份提议的页面列出每条输入的去向、每份输出的全文和对它所修订那一条的差异、被删掉的句子（输入里有、所有输出里都没有的行），以及按 §4.1 同一种算法算出的每个受影响的"项目 × 职能"组合生成输入的增减（`changeImpact`）。
- **整理**（§5.3）：总控用 `curate_knowledge` 为出了反例或冲突的条目建整理任务；每次发布后服务检查每个"项目 × 职能"组合的生成输入，到了上限的一定比例（设置项 `knowledge.curateAtPercent`，默认 75%）就为进入它的条目建整理任务。同一组条目已有没结束的整理任务就并进去（还没开工的合并条目和原因，已经在跑的不动）。总控只给条目和原因，不给项目。整理任务的输入是快照里的条目和各自的证据，它交回的变更按上面的发布规则处理，不再另派把关。整理建不出来（比如分析职能被删了）只记一条审计，不让触发它的那次发布失败。
- **出口**（§4）：派发时按项目和职能选，`createRun` 在建 Run 的事务里核对选出的修订集合，变了就不发；常驻条目全文进 brief，按需条目在 brief 里只有目录、正文是快照里的文件；快照记修订号和加载方式，只算"确定送达"。brief 的顺序：目标与权限、（把关或整理任务的材料）、常驻知识、按需目录与技能目录、平台交付约定、资料与回执。四个上限按生成出来的内容算，超了不开这一轮；修订集合变了不续接会话。总控每回合带不限职能的全局常驻条目全文，其余给目录；`get_working_context` 同样。
- **知识 MCP**（`service/knowledge-mcp.ts`，`tycho knowledge-mcp`）：stdio，零依赖。主机本机经对内监听的 `/api/knowledge/mcp`（只认回环地址和知识令牌）；接入的机器加 `--node`，经 `/api/node/knowledge/mcp`（要机器令牌加 `X-Tycho-Knowledge-Token`）。令牌在控制台签发和吊销，签发时写明会话跑在哪个执行器上；账本只存哈希，令牌本身存 `secrets/knowledge/<编号>`。四个工具只有 `service/library.ts` 一份，总控用的也是它。

- **独立审阅后补的几道结构**（11-09，Codex 审阅打回的八条）：
  - 把关和整理任务的只读是结构保证：不论挂在哪个职能上，可写的职能在建任务、换职能、建 Run 三处由同一个判定（`knowledgeRoleRefusal`）拒绝，不靠"分析"职能当前的设置。
  - 被引用为取代者的现有条目必须作为输入钉住（去向通常是保留），缺了在统一解析入口拒收；它在等待期间变了，整份候选失效。
  - 退役的内容不悄悄回来：新提议和退役条目文字相近（字符二元组重合 ≥ 0.5）或证据重合（同一份摘录的哈希），把关材料里就带上那条和它的退役理由，提议没说明理由为何不再成立就驳回；`propose_learning` 的回答也列出这些条目。主人退役的（直接退役，或经主人写过、点头、审过的变更退役）这样回来，算"改动主人审过的条目"，等主人点头。条目记下是哪份变更退役了它（`retired_proposal_id`）。
  - 证据摘录拒收本系统的令牌：已知的字段格式（`TYCHO_…TOKEN` 一类环境变量、`X-Tycho-…-Token` 一类请求头），以及按账本里已有的哈希认出的知识 MCP 令牌和机器令牌。
  - 同一请求重试：先按"客户端 + 请求编号"查，已有的按冻结内容比较（只规整形状、不核对账本），返回原结果；只有首次提交才按现在的账本核对输入。冻结内容是变更、钉住的修订、三个问题的回答和证据，任何一项不同都是另一份提议，拒收。冻结摘要不含"当时是否生效"这一项，它仍钉在变更里，发布时核对。
  - 回执里的一项 `learned` 要么整份收下，要么什么都不留：它在一个保存点里写，后面的判定拒收时连同已写的提议、证据和审计一起撤回，只留一条拒收记录。
  - 快照的大小上限按最终送达的全部知识材料算：按需知识、技能和把关或整理材料一起，超限说明分来源列出各自多大。
  - 已生效的提议，影响展示按历史修订还原它发布那一刻前后真实生效的集合；还在等的提议标"当前影响预测"。

- **把关和整理任务不属于任何项目**（§3）：任务的项目为空，所以它不拿项目的代码目录、项目的技能，也不能派生机器、不能合入；它带的知识按"不属于任何项目"选，只有全局条目。任务页把它放在"知识"下面，写明它把关哪份提议或整理几条、从哪个项目来（提议是在哪个项目的任务里提的；外部会话、总控、控制台提的不来自项目）、材料涉及哪些项目。
  - **材料和涉及的项目是同一个答案**（`knowledgeMaterial`）：它给出这一轮要送的全部材料，和这些材料带着的项目，生成快照文件和挑机器都用它。把关的材料是提议（变更、三个回答、证据）、同样内容上一次被驳回时的最终形状、它涉及或相近的条目；涉及的项目是这些东西里出现的全部：输出写的项目、输入条目在钉住的修订和现在的修订各自的项目、上一次驳回那份变更里的这些、提议来自的项目、证据引用的执行轮次或任务所在的项目。整理同理：各条目的项目、条目背后那份提议来自的项目和它证据引用的项目。相近条目只从全局条目和这些项目的条目里挑，别的项目的条目再像也不给。
  - **提议不再等把关，把关任务就结束**：提议因依据的修订变了而失效、被主人改成新候选时，它的把关任务在同一个事务里放弃（理由"提议已经不在把关中：……"），不准备材料、不派发。已经派出去的那一轮不追回，它的结论在结算时照收、不发布。
  - **用哪些登录**：设置项 `knowledge.logins`（一份登录列表，只定能不能用；先找谁按档位的全局派发顺序，roles-and-tiers.md §11；保存时核对每个都是主人现有的登录、不重复），空表示主人所有的登录都能用；照常排除写这份提议的执行器（`excludedExecutors`）。挑登录的范围只由账本的 `loginPool` 给出，派发和控制台的排队计数共用；钉住只能在这个范围里收窄、不能扩大，由账本的 `loginRefusal` 一处判定，钉登录（总控的 `update_task`、控制台）、派发、建 Run 都问它。清单收窄后，钉在被去掉的登录上的任务停住："账号 g1 不在知识任务用的登录里（设置“知识任务用哪些登录”）：改钉别的登录，或者取消钉住"。项目任务的钉住仍按 main 的规则（总控只能钉项目允许的登录，主人的钉住照原样），这一处不改。
  - **在哪些机器上跑**：账本的 `machineRange` 一处判定，派发挑机器、账本建 Run、找回失联的一轮共用：涉及的每个项目都允许的机器取交集（项目没限定机器就不算一条限制，全都没限定就不限）；为某个项目派生的临时机器不接它；还必须报告了只读可用（和其它只读任务同一个判定）。交集为空时任务停住，理由写明是哪几个项目、各自允许哪些机器："没有能跑这个知识任务的机器：项目 乙项目（h2、h3）、丙项目（h1）允许的机器没有交集"。
  - **只读**：可写的职能在建任务、换职能、建 Run 三处由 `knowledgeRoleRefusal` 拒绝；排着队时主人把职能改成可写，派发在同一处停住它："知识任务要求只读，但挂的职能是可写的：“分析”"，不再留在队列里只记一行日志。
- **证据"已核实"**：来源是 tycho 里的执行轮次、任务或主人消息，编号存在，并且摘录逐字出现在那个对象的文字里；其余一律"提交者提供"。
- **相近条目**按作用域相交和字符二元组的相似度挑，最多五条，加上它涉及的输入，只从全局和涉及的项目里挑；只是为了把可能的重复摆到把关者面前，不是判断。
- **没写采集时间**的证据用提议建立的时刻，摘要按"没写"算，重发仍是同一份。
- **企微卡片**上只有"打开"一个按钮，点它只刷新卡片上的状态；卡片写明变更摘要、作用域和加载方式、为什么要等主人；链接是控制台的 `#/knowledge/proposals/<编号>`。只有 Outbox 的 `knowledge_proposal` 一类，进入"等你点头"时排。
- **第一批数据**按 §7 分流时，种子里写"只适用于……"的 E11、E12 进 QL 项目、按需，其余 10 条进全局、常驻；测试在自己的数据目录里走完"外部提交 → 把关 → 全局常驻的主人点头、项目按需的直接生效 → 新的一轮用上 → 用反例提修订 → 把关 → 主人点头"（`tests/knowledge-mcp.test.ts`）。§7 说的合并、拆分由整理任务做；"提出并验证一项性能方案"这类技能等第 3 步。主人真实安装里的提交由协调者上线后做。

## 第 2 步落地：执行器的全局入口与自带记忆

各执行器的事实和实测见 [../spike/global-entry.md](../spike/global-entry.md)，实录在 `tests/fixtures/global-entry/`。

- **适配器声明**（`adapters/types.ts` 的 `globalEntry`、`memory`，只写执行器自己的事实）：入口在执行器自己的目录里哪个文件（目录由哪个环境变量改、默认在主目录下哪里）；旁边有哪些文件、在什么条件下执行器改读那一份（`coveredBy`）；读不读还取决于机器上看不见的东西时，是什么（`unconfirmed`）；一轮怎样不读它、在哪一版上实测过、更早的为什么不承诺（`offInRound`，没有就不声明）；自带记忆的范围（无 / 只在任务内 / 跨任务 / 说不清）和关掉的开关（环境变量或参数，Worker 和总控都从这里取）。三个执行器：
  - Claude：`~/.claude/rules/tycho-knowledge.md`（`CLAUDE_CONFIG_DIR`），rules 目录里的文件各是一份用户级指令，tycho 不碰主人的 CLAUDE.md；一轮的设置文件带 `claudeMdExcludes` 就不读（只认最后一份 `--settings`，所以并进档位那一份），只在 2.1.303 上实测过；自动记忆按跨任务算，设 `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`。
  - Codex：`~/.codex/AGENTS.md`（`CODEX_HOME`），旁边的 `AGENTS.override.md` 有字时不读（空的、只有空白的不算）；一轮关不掉；`memories` 功能跨项目，要独立视角的轮次带 `--disable memories`，只在验证过它的 0.162.0 起带（更早的版本没有这个功能时整条命令报错，所以不带，标“可能读到”）。
  - dsh：`~/.dsh/AGENTS.md`（`DSH_HOME`）；默认 profile 下和 `~/.agents/AGENTS.md` 共用 65 536 字节的渲染预算，但 profile 能改上限或关掉指令插件，所以只报“已写入、读不读确认不了”；一轮关不掉；有没有跨任务的记忆确认不了。
- **写什么**（`service/knowledge-brief.ts` 的 `globalEntryContent`）：一段接入说明（其余条目经知识 MCP 读、值得保留的经 `propose_learning` 提、连不上就说“知识服务不可用”），加全局、常驻、不限职能的条目全文。没有这样的条目就不写；超过设置项 `knowledge.globalEntryLimitKb`（默认 24 KiB）也不写、不截断，并撤下旧的那份，原因写进机器页。内容由主机生成，带一个摘要。
- **谁写、什么时候写**（`node/global-entry.ts` 的 `applyEntry`，客户端和主机共用）：机器客户端在每次正常 poll 发出前核实已知执行器的入口，报告当前实际状态；这一步不重新查询执行器、账号或模型。报告的内容摘要不是主机现在的那份时，主机在 poll 回答里附上内容，客户端立即应用；重新扫描发现新执行器后也会补写。其他发布方撤下或增加投影、用户增删覆盖文件后，下一次正常 poll 会重新观察，不必等待默认十分钟的执行器扫描。断网和重试仍受正常连接周期约束。主机本机按设置项 `knowledge.globalEntryCheckMs`（默认 1 分钟）重新核实现场，给目录存在的执行器写（主机不问执行器，目录在就算装了）：新装的补写、被挪走的写回、覆盖文件增删后改报告；内容一样时文件不重写，但现场每次都看。
- **谁能修改**：生成文件还要区分全局知识发布集合。同一集合才能更新或撤下；另一集合关闭投影时也不删除它。文件保留修订、摘要、生成时间和来源展示，未知归属或旧格式保留并报告。具体格式、跨进程互斥及旧检查器的迁移边界统一见 [原生知识入口的发布归属](knowledge-publisher-ownership.md)。
- **报告**：每个执行器一行状态——已写入 / 写入了但执行器不会读（旁边有字的覆盖文件）/ 写入了、读不读确认不了（覆盖文件查不了，或者取决于 profile）/ 被别的东西占用（含末级是符号链接；硬链接着的自己那份改写时整份换掉，不原地改另一头）/ 没写进去（原因）/ 没有写（原因）。每个执行器各自收口，一个出错不影响别的。机器页上，每台机器卡片里的执行器表多一列“全局知识入口”（表头写明这份报告是什么时候写的），主机本机的在机器页开头一行。
- **测试碰不到主人的执行器目录**：统一出口（`service/home-paths.ts` 的 `executorDirOf`）先解析最终路径（链接、junction、大小写、`..`），在测试里落在主人真实的 `~/.claude`、`~/.codex`、`~/.dsh` 或主人终端里原来设的那几个目录里面就拒绝，不管路径是继承的变量给的还是默认的；`tests/guard.ts` 给每次测试运行换上自己的临时执行器目录，并把主人原来的值传下去一并拒绝。
- **派出的轮次**（`runner/snapshot.ts` 的 `instructionsOf`、`machineInputsOf`）：快照多一项 `machine_inputs`，记两件事：tycho 写在机器上的全局知识入口这一轮不读（和用的办法）、“可能读到”（排除项带上了，但机器报的版本低于实测过的、或者没报版本）或“还会读到”（和原因）；执行器跨任务的记忆这一轮关掉了（和办法）、只在任务内、没有，或“这一轮可能读到”（和原因）。版本取派发时那台机器报告的执行器版本，派发和快照用同一个判定；还没启动的一轮换到别的机器时，按那台机器的报告重算并写回快照（`machineInputsHere`）。Claude 的档位内容在快照里写成文件时并进排除项（档位原文仍按账本记在快照里）；档位是机器上的文件时加不进去，就标“还会读到”。Codex、dsh 一律标“还会读到”。任务页的“任务详情”照快照写出这两行。
- **之后的改动**（2026-11-11 落地，账本版本 32，[merged-design.md](merged-design.md) §1.1 的定位）：
  - 账号只替换身份：账号和总控上下文都没有配置目录了（迁移把填过的值记进审计再删列；还没启动的一轮（`launching`）快照里那个空字段一并去掉，免得和登录对不上；已经启动的是送出去的记录，不改）；总控只按登录判断换不换上下文。
  - 记忆照常读写，只在要独立视角的轮次（审阅、知识把关和整理）关（§1.3）；适配器的 `memory.off.since` 写明开关在哪一版上验证过，低于它或版本不明就不带开关，标“可能读到”。Codex 不再有最低版本。快照的 `memory` 照实写“照常读写 / 关掉了 / 可能读到 / 说不清”，启动时带不带开关由快照的这一项决定（`roundTurn`）。
  - 知识 MCP 按名字关（`shared/knowledge.ts` 的 `KNOWLEDGE_MCP`，适配器的 `mcpOff`，实录在 `tests/fixtures/executor-config/`）：Claude 从 2.1.303 起带 `--disallowedTools mcp__tycho-knowledge`（只在实测版本及以上；没配这个服务器也没事；服务器进程照样起，工具不进这一轮），低于 2.1.303 或版本不明就不带、记“可能用到”（和记忆开关的 `since` 同一个写法）；Codex 带 `-c mcp_servers.tycho-knowledge.enabled=false`，但没配它时这个参数会让 Codex 起不来，所以只在机器报告的 MCP 清单里有它时才带，清单里没有就记“没有”，没报告就记“可能用到”；dsh 没实测，记“可能用到”。快照记在 `machine_inputs.knowledge_mcp`。
  - 配置清单：适配器的 `config` 声明每种配置（全局指令、MCP、随登录来的远端连接器、技能、插件）怎么不耗额度地问、怎么读出名字，或者为什么不问（`unasked`：Claude 的 `mcp list` 会把服务器起起来做检查）。机器的客户端在上报执行器时问声明了命令的那几种，只把解析出的名字报上来（`NodeExecutorStatus.config`，读不出来就报原因，不报空清单；不加节点协议版本，旧客户端就是没报）；派发时记进快照的 `machine_inputs.config`，带机器问到的时间，没报的种类写“未知”和原因。现在问得出来的：Codex 的 MCP 服务器（`codex mcp list --json`）、Claude 的插件（`claude plugin list --json`）。
- **总控**：它的全局常驻条目随恢复材料送达（§4.2），所以给总控写的设置文件里也并进同一个排除项——档位内容就并进去，没有档位就写一份只带排除项的；档位是机器上的文件时加不进去。总控还带上适配器声明的记忆关闭开关。判定和 Worker 同一个（主机不问它起的 CLI 是哪一版，所以排除项带上了也只算“可能读到”），记在上下文的启动记录（`launch_json` 的 `machine_inputs`）里。
- **没做的**：§6 的迁移不做成自动的，主人把个人指令文件里的原则在控制台的知识页新建为全局常驻条目（第 1 步已有入口）；在真实交互会话里验证“确实读到”留给迁移的第 4 步；机器上的知识 MCP 不自动配置。

## 第 3 步落地：技能

技能和知识是同一张条目表、同一套提议、冻结、把关、发布和退役，只在三处不同：正文写什么、怎样到达一轮、把关查什么。账本升到版本 23（版本 22 是触发器第 3 步的按项目外部来源触发器），只多一列：任务点名了哪些技能（`task.skills_json`）。

- **对象**（`service/knowledge.ts`）：提议写 `kind: "skill"` 就是技能，一份变更只涉及一种，类型发布后不能互换（第 1 步就有的核对）。技能没有常驻：`loading` 不写或写 `on_demand`，写 `resident` 拒收并说明，不悄悄改成按需。正文模板是 `shared/knowledge.ts` 的 `SKILL_TEMPLATE`（在哪里做、以谁的身份、按什么顺序、怎样算成功、失败后留下什么），控制台新建技能时以它起头，工具说明和回执规范里写着它；不解析正文，答没答全由把关判断。“等主人点头”的两种照旧：技能永远不是全局常驻，所以只有“改动主人写过审过的”会让技能等主人。
- **把关**：技能提议的把关任务标题是“把关技能提议”，目标里写明要查步骤能不能完成工作、会不会做错操作；brief 的四件事第 3 条写明怎么查（模板答全了没有、命令和顺序对不对、不可逆的一步有没有先确认、失败时留下什么），做不到的改好再过、改不好就驳回。这段检查要求是 `runner/snapshot.ts` 的一份 `SKILL_CHECK`，整理任务的规则里也写着它：整理技能时那一轮就是它唯一的一次把关。把关能改内容，不能改类型：回执里的变更把技能改成知识（或反过来）是交付不齐，提议原样等着，类型在提议、它的页面和主人的修改里始终是同一个。其余（去重、证据范围、只改措辞的驳回）和知识同一条路。
- **一轮拿到什么**（`runner/snapshot.ts`、`service/knowledge-brief.ts`）：账本的 `applicable` 按项目和职能选出知识和技能（知识在前，各自先全局后项目、先不限职能后限职能），`createRun` 照旧核对整个集合，技能变了这一轮不发、修订集合变了不续接会话。brief 里在按需知识的目录之后是“## 技能”目录（标题、什么时候用、文件路径），正文是快照里的 `skills/<编号>@<修订>.md`；任务点名的技能全文进“## 这个任务点名的技能”，不再另给文件。快照的 `knowledge` 每项多 `kind: "skill"`，点名的多 `named: true`。四个上限照旧按生成出来的内容算：点名的全文算进说明的上限，技能文件算进快照的上限。
- **任务点名**（`service/ledger.ts` 的 `namedSkills`）：总控的 `create_task`、`update_task` 带 `skill_ids`。只能点名可用的、对这个任务的项目和职能生效的技能，同一个只记一次，最多 10 个；改职能时点名的技能也要对新职能生效，否则拒绝。改点名和改目标一样是一次新修订，任务在跑时要先中断。点名之后技能被退役或作用域改走了，下一轮不开、任务停住并说清是哪一个（“任务点名的技能 … 现在不适用于这一轮”），不悄悄少给。任务页的“任务详情”列出点名的技能，已退役的标出来。
- **总控和知识 MCP**：`get_working_context` 多一份 `skills`（目录，不给正文），`search_library` 能按 `kind` 只查一种，`read_library` 读技能和读知识一样，`propose_learning` 收 `kind`。总控每回合带的目录里多一段“[tycho 技能]”（全局和本项目、不限职能的），目录变了才随下一回合再送。执行器的全局入口（§4.3）只写知识，不写技能。
- **平台约定**（§1.2）：派生机器的说明原是 `skills/tycho/spawn-machine.md`，现在是快照生成器的一部分（`runner/conventions.ts`），任务申请过接入名额（`machine_invite` 里有它）时每一轮的 brief 里都有“## 派生机器（平台约定）”——后面的一轮可能要负责销毁和报告；文件已删。`skills/tycho/release.md` 是 tycho 这个项目自己的做法，留在仓库里随代码包到达，不迁。
- **迁移**（§6，`service/skill-import.ts`）：`readSkills` 和设置项 `skills.dir` 已删，派发不再读任何目录。主人以前放在数据目录 `skills/<项目名>/*.md` 下的文件，在控制台知识页的“迁入技能文件”里显式导入：先预览（每份文件会怎样，什么都不写；会被拒收的经提议入口同一套校验 `checkProposal` 当场说出原因，不算进“导入这 N 份”），再导入。每份文件成为那个项目的一份技能提议（来源“迁入的技能文件”，原文整份作证据，标题取 front matter 的 `name` 或第一个标题，什么时候用取 `description` 或第一行正文），照常经把关才生效。按“项目 + 文件名 + 内容摘要”去重：再导一次只进改过的；不在项目子目录里的、目录名不是任何项目的、空文件、链接（指向文件的和指向项目目录的）都列出原因不导入；超限或带凭据的照常拒收并写明；读不出来的文件、列不出来的项目目录各自一行“读取失败”和原因，其余照常导入；账本写不进去就整个停下，不往下做。以前把技能目录改到别处的，在导入框里填那个目录（只读主人这次指定的目录，接口只在主人登录后可用）。设置里留下的旧 `skills.dir` 值这一版不读，旧程序回退时还认它。
- **没做的**：§6 第 4 步“在真实会话里验证用上了”和第 5 步删除来源文件，留给主人真实安装里的迁移；技能不写进执行器的全局入口（它们是按需的，经 MCP 读）；没有按“机器上装了什么技能”挑机器（§1.2）。

## 项目移交时的知识

项目移交保留获准知识的原 ID、完整修订及提议证据，不重新发布成新的条目。现行头必须仅归本项目；旧版本曾为全局且其授权闭包完整时可保留原 scope，但不让它作为全局现行知识在目标生效。Console 写入沿原语义；Worker 来源须回到真实 Task／Run 项目，总控来源须有持久调用因果。项目接管后创建的新工作按迁来的当前头选择知识，旧轮保留原快照。

自动学习历史只携带所选提议精确依赖的已终结 gate 及原 Run、材料与报告，仍保持无项目字段，不继承在途执行权，不放宽项目总控读取服务级工作的权限。旧 scope 涉及其他项目、全局或共享当前头、未结束 gate 或来源不明时拒绝；项目当前归属不能替代复制许可。知识模块统一核定引用闭包，交接模块沿原协议安装；不建第二份报告正文或永久档案表。具体边界和维护权见[项目知识和文件交接](project-handoff-materials.md)。

## 附：维护的依据

2026-11-09 两份调研（Codex 联网完成，协调者抽查核实了带数字的引用）。只列支撑 §5 判断的那部分。

| 判断 | 依据 |
|---|---|
| 整理要局部、点名到条目，不整体重写 | [ACE](https://arxiv.org/abs/2510.04618)：一例整份重写把 18,282 tokens 压成 122，AppWorld 准确率从 66.7 掉到 57.1，低于不用记忆的 63.7（一个坍缩实例，说明风险，不证明所有整体重写都失败）；它的做法是带编号的条目加增量合并 |
| 整理会变成负担，要有范围、允许"没有要改的" | [Anthropic，2026-11-06](https://www.anthropic.com/research/components-of-agent-memory)：wiki 加搜索 61% 对只搜索 53%；但另一例 wiki 长到原文的 1.77 倍、"什么都没抽象"，还有 agent 连续 17 步只整理笔记不干活 |
| 抽象要回到原始证据，对照成功与失败 | [ExpeL](https://arxiv.org/abs/2308.10144)、[Agent Workflow Memory](https://arxiv.org/abs/2409.07429)（规则提炼与模型提炼成绩相当：更复杂的抽象不一定更好） |
| 改动先验证再接受 | [SELM](https://arxiv.org/abs/2610.24630)（候选库要在独立的选择集上变好才接受） |
| 退役是"标为被取代"，不删历史 | [Nygard 的 ADR](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions) |
| 复盘的产出可能是修系统，不一定是一条提醒 | [Google SRE Workbook：复盘文化](https://sre.google/workbook/postmortem-culture/) |
| 常驻层要小，流程放进按需读的技能 | [Claude Code memory](https://code.claude.com/docs/en/memory)、[skills](https://code.claude.com/docs/en/skills) |
| 记忆会被投毒，后台反复读会自我强化 | [MINJA](https://arxiv.org/abs/2503.03704)；OpenClaw [v2026.9.4](https://github.com/openclaw/openclaw/blob/main/CHANGELOG/2026.9.4.md) 为此加了"不同查询数"门槛 |
| 产品现状：自动整理、事后回滚 | Hermes [Curator](https://hermes-agent.nousresearch.com/docs/user-guide/features/curator)（对 agent 自建的技能：默认 14 天标过期、30 天归档，模型合并因成本默认关）；OpenClaw [Dreaming](https://docs.openclaw.ai/concepts/dreaming)（默认每天一次，深睡阶段可新增、合并、取代长期记忆条目，单次删超过 25% 被拒，无批准步骤）、[来源与遗忘](https://docs.openclaw.ai/concepts/memory-provenance)（指定存储里被遗忘的会话不再被自动摄入；不覆盖外部写入和旧副本）。这些是产品默认值，不是 tycho 的参数 |
| 容量压力会诱发误删 | Hermes [#105921](https://github.com/NousResearch/hermes-agent/issues/105921)：后台整理删掉仍有效的记忆条目，随后改为无人值守的删改必须暂存 |
| 跨项目提升要单独举证 | 两份调研的范围内没查到这类验证流程；共享库或被多个项目引用，不等于证明能迁移 |
