# 项目会话：每个项目有自己的总控，企微是前台

读者：主人和实现者。状态：**已确认**（2026-11-09 主人确认；协调者稿经 Codex 对抗审阅后修订）。按终态写，不做过渡兼容。

## 结论

1. **项目是总控上下文的边界。** 每个项目有自己的总控：只带全局和这个项目的知识，工具只作用于这个项目。tycho 不把别的项目的对话历史混进来；执行器自己环境里 tycho 管不到的部分，按知识设计的规则如实标出。
2. **一个项目是一串有顺序的会话段，只有当前段接收新消息。** 主人说"新话题"就开一段新的，旧段只读、留作历史。连续性不靠段里的对话历史，而靠账本（任务、问题、主人的原话、已提交的操作）和项目知识。
3. **没有常驻的用户级总控会话。** 全局配置和管理在控制台；不属于任何项目的通知由服务直接发；跨项目的自动协调本期不做。
4. **企微是按规则分流的前台，不是模型。** 它记住"当前项目"，把主人直接输入的消息送进这个项目的当前段；送不准时，先把消息记进账本、挂起，让主人选，不猜。它也是**主动找主人的通道**：需要主人的事立即推，阶段成果推一句，进度不推，另有每日简报（§2.1）。
5. **项目配置尽量少。** 建项目只要名字，代码来源可选（仓库地址，或某台机器上的文件夹）；新项目的登录默认"全部"，机器默认"不限"；档位和额度跟着登录走，不按项目重配。
6. **各项目的总控各自运行。** 一个项目的长回合不会让别的项目排队；共用的登录额度用完时，用它的项目一起等。

## 起因

主人 11-09："当前项目是要我逐个配置的吗？项目是独享上下文的吗？如果我有多个项目怎么办，总控会混乱吗？"之后又说："目前 Claude 的运作逻辑非常符合我的使用习惯：创建一个 project，这个 project 有个总会话会不停地派发任务给具体的会话去执行，完成后会退役。多个 project 是隔离的，不会互相污染。所以我有点犹豫需不需要一个用户级别的总控会话。""微信的会话可以是用户级别的，然后提供给我项目级别的入口即可。""项目的配置也尽可能简单易用。"

现状：Worker 已经按项目隔离，每个任务属于一个项目，快照只有这个项目的代码和知识。总控则是所有项目共用的一个长期会话：只有一个全局的消息队列，工具也没有项目范围。

## 1. 对象

| 对象 | 内容 |
|---|---|
| **项目** | 不变的编号、名字、代码来源（有序，第一项是默认；一项都不配就是不写代码的项目，见 [code-sources.md](code-sources.md)）、机器范围（空 = 不限）、允许派生机器（默认关）。登录方式两选一：**全部登录**，派发时按当时的登录池挑；**只用所选**，一张不带顺序的勾选清单，选零个就是不派发。先找谁不在这里：每个档位一份全局派发顺序，总控还能按任务写一份优先名单（roles-and-tiers.md §11） |
| **会话段**（新） | 属于一个项目，按顺序编号；每个项目同时只有一段是"当前"。一段里可以先后有多个**执行器上下文**：续接失败、总控换了登录或执行器、适用知识的正文变了，都会让这一段换一个新的执行器上下文。新上下文从账本重建（§3），主人看到的仍是同一段对话，只多一行系统说明。只有主人说"新话题"才开新段 |
| **执行器上下文**（新） | 属于一段：执行器会话标识、用哪个登录、凭据编号、启动参数、进程标记。每个上下文送出的恢复材料和知识修订留档，这就是总控的输入记录（"输入如实记录"那条底线） |
| **消息** | 归属：哪个项目的哪一段，或者"待归属"；归属依据：控制台所在页面、企微当前项目、主人选择、账本对象推导；渠道地址照旧另记。状态多一个**待归属**：这种消息不会被总控取走 |
| **企微前台状态** | 按机器人和聊天固定项目，优先于按发送人保存的临时当前项目；绑定或解绑清除该聊天的临时选择。 |

项目总控默认沿用服务设置，也可以在项目设置中选择自己的登录和档位；同一账号的额度仍随实际登录计算。

**为什么"换执行器上下文"不开新段：** 段是主人看到的对话，执行器上下文是技术实现。如果因为一条知识被修订、续接失败就切出新段，主人的对话会被系统动作切碎。所以段只由主人开；系统需要换上下文时，在同一段里从账本重建，并在对话里标一行"已按最新知识重建上下文"。

## 2. 消息怎么到项目

前台只认主人**直接输入**的几种固定说法和对象引用格式；转发、引用来的材料只当作资料，不会改变路由。

| 输入 | 归属 |
|---|---|
| 控制台项目页里的对话 | 这个项目的当前段（历史段只读） |
| 企微："进入 <项目名>" / "<项目名>：……" | 项目名唯一匹配，就切换当前项目并记住；匹配不唯一或不存在，就列出候选 |
| 企微：直接写出任务、轮次的编号 | 这个对象所属的项目（从账本推，不让模型猜） |
| 企微："项目" | 列出各项目和它们的状态：在跑的任务、待答的问题 |
| 企微："新话题" | 在当前项目开新段 |
| 企微：其余消息 | 进当前项目的当前段 |
| 还没有当前项目、显式项目和对象指向不同项目、一条消息涉及多个项目的对象 | 记为**待归属**，列出候选项目（按编号）让主人选；一个项目都没有时，给控制台"新建项目"的链接 |

- **待归属是账本里的状态，不是内存里的。** 原文、渠道去重键、发送人先落账。主人做选择时，确认归属、更新当前项目、让消息可以被取走，在同一个事务里完成。选择针对哪几条消息，要明确：只选这一条，或者"这几条待归属的都归这里"。
- **更正归属和总控取走消息互斥。** 总控取走之前，可以改归属；取走之后按原归属处理：已经提交的操作如实列出，不自动搬到别的项目重放。
- 白名单、去重、写库失败不回"已收到"，这些现有规则同样适用于前台命令和选择动作。
- **回复带【项目名】；不属于任何项目的通知带【系统】**，例如服务降级、备份失败、登录失效、机器加入。通知后面附控制台直达链接，链接只指向目标页面，不携带任何令牌。企微里点开，会在它自带的浏览器里打开控制台，第一次要用现有的一次性登录链接登录；没有配置对外地址时如实说明"手机打不开"。

## 2.1 主动触达

主人 11-09："不同 project 可能会有不同的进度，但是我不可能时刻盯着它们推进。如果有阻塞或者需要我判断的地方，抑或是有阶段性成果，我是需要能感知的……这是 IM 的价值，不仅仅是传达我的需求到 project，更是主动触达我的手段。"

**推不推、怎么推，由服务按账本事件的类型判定，不由总控临场判断**；总控只负责写一句摘要。总控回复写得不好，该找主人的事也不会漏。

| 级别 | 事件 | 怎么推 |
|---|---|---|
| **等你** | 待答的问题；要主人放行的；任务停住且只有主人能处理（登录失效、没有可用的登录或机器、决策档又被打回）；知识等主人点头 | 立即推，卡片带按钮，能在企微里直接处理。没回应，按设置项的间隔再提醒，次数有上限（设置项） |
| **成果** | 一项工作整体完成、等验收；已合入；已上线 | 立即推一条：一句摘要加链接。同一项目在设置项的时间窗内的多条合成一条 |
| **进度** | 开始、重试、一轮结束、审阅通过 | 不推；在控制台看，或在企微发"项目"查 |

- **每日简报：** 每天在设置的时间推一条，按项目列"等你的、完成的、在跑的、卡住的"。没变化的项目不列，全都没变化就不发。时间和开关是设置项。
- **回复直接处理：** 点卡片按钮，或者按卡片上写的格式回复（带问题编号），就送到那个问题所属的项目，不改变当前项目。
- 每条都带【项目名】或【系统】和直达链接（§2）。
- 现有的"总控回复里只把卡住或已就绪的推给主人"那条规则，由这张表取代，不保留第二套判定。

## 3. 项目总控怎么运行

**约束归谁：**

| 约束 | 范围 |
|---|---|
| 数据目录锁、服务进程归属 | 整个服务唯一 |
| 当前段、消息取用、驱动进程、工具接纳 | 每个项目唯一：同一项目一次处理一个回合（一条主人或触发器的消息，或连续取走的一组内部事件），同一时刻只有一个驱动进程 |
| 单活跃 Run、修订绑定、原子结算、答复校验 | 不变，仍由账本按原有对象保证，与会话怎么拆无关 |
| 写库失败后停止副作用、降级、恢复清点 | 整个服务统一：降级时所有项目的总控都停止接纳工具；恢复时按每个项目各自的在途回合核实，不用某一个项目的空闲状态代替全部 |
| 停服、升级排空、回退前核实残留 | 覆盖所有还没确认结束的执行器上下文的进程标记 |

**运行：**

- **空闲就退出，有消息再起。** 进程空闲超过设置项（默认 30 分钟），在途工具调用收尾、核实进程已经不在之后退出；下一条消息到来时，按这一段当前的执行器上下文续接。
- **换执行器上下文**（续接失败、换登录、适用知识的正文变了、项目的代码来源变了）：在下一条消息开始前处理，不打断正在进行的回合。先停止旧上下文接纳工具，等在途调用收尾，核实旧进程不在了，再起新的。
- **开新段**（主人说"新话题"）：同样的切换步骤。已经排队的消息跟着当前段走，进入新段。
- **歧义先做后说**（2026-11-11 主人认可，参照 Claude Code Projects）：主人的话有几种读法时，能撤回的步骤（建任务、派分析或验证、退回重做、预约）总控按最可能的读法先做，回复里写明怎么理解的；只有改变目标或范围的取舍、分不出哪种读法更可能时才 `ask_user`。提问会立即推给主人并让任务停下，问一件本可以先做的事等于让项目白等。收不回来的步骤（验收、上线、不经审阅验收）本来就有结构上的关卡，不靠这条。
- **内部事件**（Run 结束、问题被答复、预约到时）按账本对象推出所属项目，送进那个项目的当前段，不看企微的当前项目。已自动回到队列的结算（额度用完、执行丢失、没机器接下、只读轮不采用后重派）和插话回执只记账、不投递：下一轮由服务自己接上，总控要看就用 `list_tasks` / `get_task`。排队中紧挨着的内部事件合成一个回合，最多 10 条，遇到主人或触发器的消息就停。

**适用知识：** 总控的输入是全局和本项目的知识里、不限职能的那些条目：常驻的全文，其余的给目录（知识设计 §4.2）。只有目录变化（新增按需条目）时，下一回合刷新目录，不换上下文。已经进入上下文的正文被修订、退役或不再适用时，必须换上下文，失效的规则不能留在旧上下文里。

**恢复材料**（新执行器上下文第一条消息前送出，并留档）：

- 本项目适用知识的常驻全文和其余条目的目录；
- 没结束的任务及其状态、当前产物登记、在跑的 Run，以及通过已提交操作关联的主人原话（`owner_requests`）：建了任务不等于原话里的限制已经解除。原话只从本项目的主人渠道按现有因果关联回读，不复制保存；按时间保留后来的明确变更。整项超出材料预算时用 `get_task` 读取；
- 待答的问题、还没送达的插话；
- 待核实（`unverified`）的消息，以及它们已经提交的操作；
- 还没闭合的主人要求：没有关联任何任务或操作的主人原话，**全部**列出，不只列最近几条；超过输入上限时给一个可分页的读取入口，不默默丢掉早的。

原文、对象编号、修订号和登记编号是事实依据，摘要只做索引。

**共用的登录：** 额度、冷却、认证状态以实际登录为准，不按项目存副本。

- 额度用完：用这个登录的项目总控停止取消息，等它恢复；消息留在账本里。
- 认证失败：总控停摆，找主人。
- 已经送出的失败回合按待核实处理，额度恢复后也不自动重放。
- 总控进程不计入登录的 Worker 并发上限。真需要限制总控的并发时，再加一个全局设置，不做逐项目的预算表。

## 4. 工具的作用域

由服务端在接下这条消息时绑定，链条是"进程令牌 → 当前回合 → 已接纳的消息 → 项目"，在读请求体之前完成。总控改不了，模型传来的项目参数一概不信。

- **一处判定：** 查询、动态参数候选、编号引用，共用同一个"这个对象属于哪个项目"的判定。**先判定，再做任何外部动作**：例如建审阅任务，在取回被审产物之前就先确认它属于本项目。
- **知识读取：** 返回全局和本项目的条目；知道别的项目条目的编号也读不到。
- **知识维护：** 总控只能为本项目提交知识维护请求（例如整理），由服务建知识任务（这类任务不属于任何项目，见知识设计 §3）。

| 处理 | 工具 |
|---|---|
| 保留，只作用于本项目 | `create_task`、`update_task`、`list_tasks`、`get_task`、`get_run_log`、`interrupt_task`、`accept_task`、`rework_task`、`resume_task`、`abandon_task`、`ask_user`、`schedule_wake`、`invite_machine`；按项目授权的 `integrate_task`、`release_task`（见文末“总控可以自己做的事”） |
| 保留只读，只返回本项目需要的 | `list_roles`、本项目配置、`list_logins` 与 `list_machines`（只列本项目能用的资源和必要状态） |
| 移到控制台 | `create_project`、`set_project_logins`、`add_machine`、`remove_machine` |
| 删除 | `note_decision`、`list_decisions`（并入知识，按知识设计迁移，不留旁路） |

总控提示词里要求用这些被移走工具的段落一起改掉：需要时告诉主人去控制台的哪一页，并附链接。

## 5. 项目配置

| 内容 | 要不要填 | 默认 |
|---|---|---|
| 名字（可改） | 要 | 无 |
| 代码来源 | 代码项目要 | 不填就是非代码项目（执行器在空的任务目录里干活）；仓库地址或某台机器上的文件夹，可多项、第一项是默认（[code-sources.md](code-sources.md)） |
| 登录 | 不用 | 新项目：全部登录 |
| 机器 | 不用 | 不限 |
| 允许派生机器 | 不用 | 关 |
| 暂停 | 不用 | 不暂停；暂停立刻生效，不随保存走（见文末“按项目暂停”） |
| 归档 | 不用 | 不归档；收起来不用了，立刻生效，不随保存走（见文末“项目的生命周期”） |
| 总控可以自己做 | 不用 | 验收开，并入主线、上线关（见文末“总控可以自己做的事”） |
| 项目知识 | 有独有约定时再加 | 没有；全局知识照常适用 |

- 控制台"新建项目"只露出名字和代码来源，其余收在"高级"里。
- **有效登录池只有一个推导出口：** 全部或所选，再减去不可用的。挑登录、钉住任务、派生机器、建 Run 都用它。任务钉住的登录只能在当前有效池里收窄：项目把登录改窄之后，钉在被去掉的登录上的任务停住，并说明原因；建 Run 的事务里再核对一次。已经在跑的 Run 不受影响。

## 6. 迁移（一次性，通用规则）

- **项目：** 所有现有项目一律迁成"只用所选"，清单保持原样，原来是空清单的仍然不派发。只有新建的项目才默认"全部登录"。
- **旧总控会话：** 原来的全局会话和它的消息保留为只读的"旧全局记录"，不当成任何项目的第一段，也不续接它的执行器上下文。每个项目第一次收到消息时，从新的执行器上下文开始，按 §3 从账本恢复。能从账本对象（任务编号等）确定所属项目的旧消息，在项目页里可以看到链接；确定不了的就留在旧全局记录里，不假装已经按项目隔离。
- **待核实的旧消息：** 按原规则处理，不搬到项目里重放。
- 删除"全局只能有一个打开的总控会话"的约束、单值的总控登录记录和单会话的读法，不保留单会话路径。
- 本机这一次：唯一的项目 tycho 现在列着三个登录，迁成"只用所选"、清单不变；旧会话成为旧全局记录。

## 项目总控登录

项目设置可以沿用服务默认，或选一个支持总控的账号或本机登录，再选该登录的档位。服务默认替已有项目提供统一的起点。显式绑定的登录换号、换凭据或修改档位后，正在回答的消息先结清，下一条按新绑定启动。换账号、换凭据或换执行器会从项目账本重建上下文。一个项目的账号问题显示在它的对话页，其他项目继续处理。旧项目升级后沿用服务默认。

## 7. 本期不做

| 不做 | 理由 |
|---|---|
| 常驻的用户级总控会话 | 全局配置、状态汇总、系统通知都不需要一个模型会话；它会积累一份混杂的上下文 |
| 用模型判断一条企微消息属于哪个项目 | 歧义识别和意图分类都不可靠；送错项目可能建错任务、改错东西 |
| 跨项目的自动协调：项目总控之间互相发消息、跨项目任务依赖 | 本期不做，由主人分别对各项目说。终态设计里承诺的跨项目依赖同步改为"后续单独设计"，不当作已经被覆盖 |
| 按项目另计同一账号的额度 | 由提供方及实际登录决定的读数继续随账号走 |
| 历史段继续接收消息 | 没有使用方；只读比维护两个入口简单 |
| 把控制台嵌进企业微信工作台 | 用消息里的直达链接代替；能不能嵌入取决于各部署的域名和管理员权限，不是这里的通用前提 |

## 8. 分步

1. 会话段与执行器上下文、消息归属与待归属、各项目并行运行与服务级屏障、空闲退出与续接、换上下文与恢复材料、工具作用域、有效登录池；**控制台的"新建项目"接口和简化表单在同一步交付**，然后才删除 `create_project`，中间不能出现建不了项目的空档；迁移。

3. 控制台：项目页里的对话（当前段可写、历史段只读、"新话题"）、"全部登录 / 只用所选"的设置。

## 第 1 步的实现记录

设计没写死、实现时定下的细节，按“谁依赖它”留在这里：

- **账本（版本 20）。** 会话段 `router_segment`（每个项目同时一段 `current`，唯一索引保证）；执行器上下文 `router_context`（每个项目同时一个 `open`，唯一索引保证）。上下文的 `live_at` 是“它的进程可能还在跑”：起进程前写上，只有按标记扫描确认没有残留才清掉；停服、升级回退和启动清点扫描所有 `live_at` 不空或还开着的上下文的标记。消息的段在被取走时才定，所以“新话题”之前排着的消息自然进新段。
- **一次只放回一种消息：续接被拒。** 条件只认结构上看得见的：续接的进程没出现初始化、没接纳任何工具、没被打断，并且是它自己结束的（退出，或自己给出失败的结果行）。这时这一回合没有任何操作被执行，消息放回队列（`message.requeue`），换新上下文后再送。线路坏了、进程不出声、初始化超时都是一般的通信故障，和其余没完成的回合一样按原规则待核实。
- **恢复材料的上限**是设置项 `router.materialKb`（默认 64 KiB），管整份材料。各部分按顺序放（常驻工作方法、没结束的任务、待核实的请求、未闭合的要求、按需目录），放不下的部分在材料末尾写明用哪个工具从哪条之后接着读（`get_working_context`、`list_tasks`、`list_unverified_requests`、`list_open_requests`）。待核实的请求直接按账本查询分页，不从最近若干条消息里筛。“未闭合”= 主人在这个项目里说的、回合结束了、没有关联任何任务或操作（不算消息自身的生命周期和回复）。
- **空闲退出**是设置项 `router.idleMs`（默认 30 分钟）。服务启动和“重启总控”只检查能不能启动（把停摆原因先说出来），不预先起进程；进程在项目有消息时才起。
- **总控的登录身份和额度。** 总控用的登录在账本里总有一个稳定的身份：绑定账号时是那个账号；不绑定时是“主机这台机器上 Claude 的登录”，编号和机器自己的登录同一个格式——主机已经作为节点接入时用它接入的机器名，否则用它的主机名（就是它接入时默认会用的名字），这样主机作为节点跑 Worker 时共用同一份 `login_state`。额度用完记在这个登录上，和 Worker 走同一段歇息计算（`quota.restMs`、`quota.maxRestMs`、执行器报的恢复时刻），重启服务也还在；用这个登录的所有项目停止取消息直到恢复。撞上的那一回合按待核实处理，不重放。
- **登录池。** `loginPool` 是唯一出口；只发清单就是选“只用所选”。项目接口另收 `login_mode`（`all` / `selected`），两边都能切：切到“全部登录”时清单原样留着、不参与派发，切回“只用所选”就按它派；所选为空就是不派发，页面照实写。控制台的项目编辑只在主人改了登录方式或清单时才发这两项（发清单时一定带上登录方式），保存别的字段不动登录方式。钉住的登录已经不存在时仍按原来的“没有可用的登录”停住。
- **待归属的入口。** 不带项目的 `POST /api/messages` 记为待归属；控制台“对话”页列出待归属的消息、按条或整批归到一个项目（`POST /api/messages/assign`）。企微入站从第 2 步起走前台（见下一节）。
- **知识工具的作用域。** `get_working_context` 不再收项目参数；`search_library` 的范围只有 `global` / `project`；`read_library`、`curate_knowledge`、`propose_learning` 的输入条目必须是全局或本项目的；提议的作用域只能是全局或本项目。别的项目的条目按“没有这个条目”回答。
- **`note_decision` / `list_decisions` 已删除，旧裁定转成知识提议。** 替代是 `propose_learning`（知识第 1 步已提供）。迁移时每条旧裁定变成一份提议：来源“迁移的长期裁定”，证据就是那条原始记录（证据来源“账本里的旧记录”，只有迁移能交，服务能核实），作用域按它关联的任务推出项目、推不出就是全局，加载方式常驻（它原来就是总控每次都读的）。之后走知识第 1 步正常的把关：任务内的决定会被驳回，长期规则生效，全局常驻的照规则等主人点头；不按措辞擅自分类。转成提议在账本打开时做，每条一个事务，做完的从待转清单里去掉；`decision` 表和它的读法都删了。
- **服务级屏障覆盖工具。** 降级或恢复清点期间，工具接纳一律拒绝；请求体读完、动作执行前再查一次。
- **清点枚举失败就是清点失败。** 读不出哪些上下文可能还在跑时，启动清点失败、总控停摆并显示原因，不起新的总控；停服也照实报告。
- **切段竞态。** 起进程前最后一次等待之后重新读当前段和上下文；开上下文的事务里拒绝已经结束的段；取消息时只取进上下文所属的那一段。
- **迁移（§6）。** 旧会话行搬进 `router_context`（无段、无项目、已关闭，原因“旧全局记录”），开着的或最新的那一行保留进程标记待扫描；单值登录记录并进那一行后删除。旧消息的项目只从账本对象推：回合的变更所涉任务都属于同一个项目，或内部事件里的任务所属项目；推不出的留空。还没被取走的主人消息记为待归属，内部事件归到任务所属项目或只记账。

## 第 2 步的实现记录

- **账本（仍是版本 20）。** 第 1 步和第 2 步一起上线，版本 20 从没单独发出过，所以第 2 步的表并进版本 20 的同一步迁移，不另起版本：`front_desk`（按“机器人 + 聊天 + 发送人”唯一，存项目编号）、`push`（等你的事和成果，见下）、消息多一列 `candidates_json`（前台送不准时给主人的候选和原因）。归属依据多一种 `current`（企微当前项目）；写出项目名（“<项目名>：”）和做选择都记 `owner`，写出任务、轮次编号记 `object`。
- **前台只在账本里判断**（`service/front-desk.ts`，账本的 `frontReceive`、`frontChoose`）。一条企微消息的去重、白名单、解析、写入、改当前项目、要发的回答在同一个事务里；写库失败照旧回“暂时无法记录”。转发、引用的资料和不是文字的消息一律不解析，按普通消息进当前项目，没有当前项目就待归属。固定说法：
  - “进入 <项目名>”。名字按大小写不敏感的全等比；“进入”后面紧跟的字不是任何项目名（比如“进入下一步”）就是普通消息，隔了空格才算命令，那时找不到就列出现有项目。重名时列出编号，用“进入 <项目编号>”进。
  - “<项目名>：……”。冒号前的全部字恰好是一个项目名才算，名字多长都按全名查账本，不设长度上限；不是任何项目名就是普通消息（“注意：……”不受影响）。这条消息进那个项目并切换当前项目。
  - 写出的 26 位编号：账本里是任务或轮次就按它所属的项目送，不改当前项目。
  - “项目”列出全部项目和在跑、待答的数目；“新话题”在当前项目开新段。
  - 名字和对象指向不同项目、对象分属几个项目、重名，或没有当前项目：待归属，候选按项目创建顺序记在消息上。
- **待归属的选择。** 服务经出站发一张卡片（重启后照样发、照样能按）：每个候选一个按钮（最多 5 个），旁边总有“到控制台归属”，正文列出编号的候选和两种回复格式：“归 <码> <序号或项目名>”只归这一条，“全归 <码> <序号或项目名>”把这个聊天里这个人待归属的都归过去。码是消息编号的末 4 位，在这个聊天里对不上唯一一条就如实说。按钮和回复走同一个 `frontChoose`：确认归属、改当前项目、放行在一个事务里，全部或全不。已归属但没被取走的可以再改；被取走的拒绝，回答写明被哪个项目取走和已提交的操作，不搬。一个项目都没有时回一句控制台“新建项目”的链接，建好后用“归 <码> <项目名>”。控制台的归属不改企微的当前项目：控制台不是那个聊天。
- **答复带编号。** 问题卡片上写“答 <码> <序号或答复>”（码是问题编号的末 4 位），只答单题的问题，序号对上选项就取那个选项；多题的回“到控制台回答”。答复直接落在那个问题上（和按钮同一个 `answerApproval`），不进当前项目的总控，不改当前项目。
- **标记和链接**只在 `service/present.ts` 一处渲染，出站初发、按卡片后替换的卡片（答过、关了、放行结果、归属结果……）、绕过出站的直发（降级、备份失败、机器加入）都经它：每条企微消息前面是【项目名】或【系统】（`shared/labels.ts` 的 `projectMark`），后面是控制台页面的链接（`#/projects/…`、`#/task/…`、`#/work/…` 等），只有页面地址、不带令牌；没配对外地址时写“控制台：还没有配置对外地址，手机上打不开”。超长截断截正文，标记和链接留着。卡片的标题带标记，点卡片本身（按钮以外）打开对应页面；没配对外地址时卡片正文末尾写同一句。
- **三级推送只有一张表**：`service/pushes.ts` 的 `PUSH_LEVELS`，按出站行的类型定级，入队时就判，原来按任务状态判断“总控回复要不要推”的规则删了。
  - 等你：问题、规则停住的任务（`held`：结算、丢失上限、派发找不到登录等把任务停住；总控或主人自己挂起、改定义引起的停住不算；恢复备份停住的在恢复清点页一起确认，不逐条推）、账号令牌失效、机器自己的登录失效、登录没有机器、清不掉的残留、等主人点头的知识。立即推，账本里记一行；之后每隔 `push.remindMs` 看一次，还在等（按各自的账本事实判断，比如问题还开着、任务还停在同一个原因上；判断只在账本 `pushStillWaiting` 一处，入队时问一次，发出前再问一次，中间处理掉的就不发）就再提醒，最多 `push.remindMax` 次，处理了就不再提醒。提醒是一句文字（带“再次提醒 n/上限”），按钮还在原卡片上。“没有机器”账本答不出还在不在，只推一次；机器加入请求在内存里、会过期，照旧直接推卡片、不提醒。
  - 成果：一项工作做完等验收、已合入、已并入、已上线。项目在 `push.resultWindowMs` 内没推过成果就立即推；窗口内再来的攒着，窗口过了合成一条“这段时间有 N 项成果”。工作完成在结算的同一个事务里登记成果，用服务自己的话（“<工作标题> 做完了，等你验收”），由推送路径发出，不等总控：总控找不到、登录失效、额度歇着，成果照样推。总控对那条结算事件的回复第一段只能替换还没发出的那一句（窗口里攒着的，或还在出站里没试过的），发出了就不再动，也不会因此多出一条。上线只在升级命令核对通过、并且结果写于这个服务实例启动（`service.json` 的 `started_at`）之后时推一次：核对可能在启动还在等总控检查时就完成。
  - 进度（开始、重试、一轮结束、审阅通过）和总控对其余内部事件的回复都不推。
- **每日简报**（`push.daily`、`push.dailyAt`）：每分钟看一次，过了当天的时刻、还没为这个时刻发过就发；服务那时不在，启动后补一次。第一次只记基线不发。按项目列等你（等你决定、待验收）、完成（上次以来完成的）、在跑、卡住；和上次相比没变化、也没有新完成的项目不列，全没变化不发。
- **推送的默认值**只在 settings.ts 的声明里；账本在没有服务设置时（测试、命令行读账本）也从那里取。
- **旧裁定看得见。** 迁移时被提议入口拒收的旧裁定留在待转清单里，知识页列出它们的原文、项目和拒收原因（`GET /api/knowledge` 的 `legacy`）。选列表而不是【系统】通知：没配企微时通知根本不入队，列表总在。

## 按项目暂停、总控上下文按长度换（2026-11-11，参照 Claude Code Projects）

主人 11-11 认可的两条，和“歧义先做后说”（§3）一起落地。账本版本 29 加两列：`project.paused_at`、`router_context.context_tokens`。

**按项目暂停。** 以前只有全局的“暂停派发”，想让一个项目停手只能全停。现在项目设置里有“暂停这个项目 / 恢复”，点了立刻生效，不随页面的保存走（`POST /api/projects/:id/pause`，账本 `setProjectPaused`，审计 `project.pause` / `project.resume`）。暂停期间：

| 什么 | 怎样 |
|---|---|
| 派发 | 不给这个项目的任务建新 Run：账本的派发队列（`queuedTasks`）不列它们，`createRun` 在同一事务里拒绝“项目已暂停”。任务状态不变，恢复后照常排。 |
| 失联的一轮 | 不判定、不接续，原样等恢复；任务页写“项目已暂停，恢复后接续”。 |
| 在跑的一轮 | 跑完为止，照常结算。要立刻停，用任务页现有的中断。 |
| 总控 | 不取这个项目的消息（`takeNextTurn`、`hasReceivedMessage`、`projectsWaiting` 同一个条件）；正在处理的回合做完。空闲退出照旧。 |
| 消息 | 照常入账、排着；企微发进来时当场回一句“项目已暂停：这条消息记下了，恢复后处理”；“项目”命令列表里标“已暂停”。 |
| 触发器 | 到点的、入站来源投来的都拒收（原因 `project_paused`，计数，不算触发器自己的问题，不推送），游标照常往前走：恢复后不会一下子涌进一堆旧的触发消息。入站请求回 503，调用方恢复后重试能进。 |
| 一次性的定时触发器 | 暂停期间到点的那一次被跳过，恢复后不补；规则页的拒收里看得到。要补就恢复后改一个新时刻。预约（`schedule_wake`）不一样：到点任务回到排队，恢复后照常派。 |
| 派生的临时机器 | 照旧在线、空闲，名额对应的任务结束时才排空；暂停不排空它们。 |
| 任务页 | 排着的任务不显示按登录算的等待原因（那不是它在等的）；失联的一轮写“项目已暂停，恢复后接续”。 |
| 知识的把关和整理任务 | 不属于任何项目，不受影响。 |

判定只有一处：账本里那一个“项目在不在暂停”的条件，各个取活的查询共用它。

**总控上下文按长度换。** 以前只在续接失败、上次没起来、换了登录、知识正文变了时换执行器上下文；上下文变长只能靠执行器自己压缩，或者等主人说“新话题”。现在总控每次调用时执行器报告的上下文大小（Claude 的 assistant 行 `message.usage` 里 input、cache_creation、cache_read 之和，实录 `tests/fixtures/claude/2.1.312-linux/tools.ndjson`）在回合结束时记到上下文上；下一条消息之前，超过设置项 `router.contextTokens`（默认 100000，0 是不按长度换）就和“知识正文变了”走同一段：关掉旧的（原因“上下文超过设定的长度”），从账本重建新的。这个进程自己新开的上下文只跑过开头那一回合就超了，说明设置值不大于恢复材料和常驻知识的起始大小，重建也一样大：这时不换，日志里说一次。记在账本里，所以进程空闲退出、服务重启之后也不会续接一个太长的会话。账本是权威，重建比有损压缩可靠；“新话题”仍留给主人主动切题。

## 总控可以自己做的事（2026-11-11）

主人实际的用法是长期授权：修完、测完、审完就直接合入、推送、部署，做完报告。以前验收总控能做，并入和上线只有控制台按钮。现在每个项目在设置页有一节“总控可以自己做”，三个开关：验收、并入主线、上线（声明只在 `shared/grants.ts` 一处，控制台照着画）。账本版本 31 加一列 `project.grants_json`；已有项目迁移后是默认值。

**授权是权限上限，不是本次操作指令。** 总控默认在需要审阅的任务交回后发起审阅，在项目授权且前提满足时验收、并入或上线；主人明确要求等待、由他发起或不要执行时，默认推进停在该处。后来的明确变更按新的安排做，不把旧原话当永久锁。这是总控理解要求的约定，不是从自然语言解析出的服务端权限锁。

**授权只去掉“问”，不放松关。** 判定只在账本 `requireGrant`：调用者是总控时，项目没打开这一步就拒绝（“告诉主人等他在任务页做”）。并入主线（主人在控制台和总控都一样）要求任务已验收，判定只有账本 `requireLandable` 一处；上线同样要求任务已验收。验收那一步本来就过审阅关（`acceptTask`），上线照旧过上线关（`releaseGate`），这两道关对总控和主人一样。主人在控制台做哪一步都不看授权。

| 开关 | 总控的工具 | 前提 | 动手的是谁 |
|---|---|---|---|
| 验收 | `accept_task` | 审阅关 | 服务（取回产物） |
| 并入主线 | `integrate_task` | 已验收（主人在控制台并入也一样） | 那一轮回执里恰好有一个 PR：服务建一个“验证”职能的子任务，父任务、PR 和审过的提交记进它的 `landing_json`（只有建任务时写），执行器在机器上用 gh/glab 合这个 PR，只合审阅绑定里的那个提交（`--match-head-commit` / `--sha`，提交号取当前“通过”的 `ReviewOf.reviewed.commit`；任务不需要审阅时取回执报的提交，不取总控的说法），平台拒绝（要求的检查、审阅、冲突）就照原话报告；它这一轮结算为待验收且回执有一个 commit 时在父任务上落和本机并入同一种结果、发 `merged` 内部事件，主人只收一条推送。合入子任务的目标、验收标准、范围不能改：改了目标就能让它合别的提交，而账本记的还是审过的那个；要合别的就放弃它，重新并入。没有 PR：没有可并的，tycho 不把代码并进主机上的检出（`service/merge.ts` 已删），让执行器把分支推上去、开一个 PR |
| 上线 | `release_task` | 已验收、上线关 | 服务（和控制台“上线”同一个函数） |

**PR 网址只收形状对的。** 回执里那一项会写进另一轮的 brief，所以只收 `https://…/pull/<编号>` 或 `https://…/-/merge_requests/<编号>`，别的（带空白、换行、参数、多于一项）在合入入口拒绝，结算时也按“交付不齐”停住；判定和拒绝文字只在 `shared/pull-request.ts` 一处，不靠 brief 里的叮嘱。它属于哪个仓库不另查：平台按提交号核对，PR 的 head 不是审过的那个提交就合不进去。“验证”职能是主人能改的对象：被删了或改成只读，就不建合入子任务，说清怎么办。同一个提交的合入子任务还在（没验收、没放弃）时再要一次，返回那一个：它那一轮跑完、停在待验收，也还算在；先验收或放弃它，才能再建。“验证”职能要可写、交报告，不是就不建并说清怎么改。上线在启动命令之前记一行 `release.launch`，写明是主人还是总控；这一行写不进账本就不启动。

**为什么合 PR 交给执行器。** 合并是代码托管平台和执行器自己就会做的事；tycho 只管它们不知道的三件：许不许（授权、审阅）、合哪一个提交（登记的那一个）、做完告诉主人。CI 门槛交给平台自己的分支保护，不另造一道。

**做了就报告，不靠总控措辞。** 并入、上线、子任务的完成都走已有的成果推送（`pushes.ts` 的 `integrated`、`released`、`work_ready`）。

**默认：验收开，并入主线和上线关。** 对照同类产品：Codex cloud、Cursor 的后台 agent、GitHub Copilot coding agent、Devin 默认都只把改动推到自己的分支或开 PR，进主线和部署要人点；GitHub 的自动合并也是每个 PR 单独打开、以审阅和检查通过为前提。总控本来就能验收，保持不变。主人要长期授权的项目在设置页打开即可。

## 总控能读、不能写（2026-11-11）

总控以前以 `--tools ""` 启动，只有编排工具，看不到代码和 git，只能读回执：两个任务把账本升到同一个版本，要到合入失败才暴露。现在它能读，写仍然只能派任务。总控有哪些工具由 tycho 给定，是 [merged-design.md](merged-design.md) §1.1 的例外之一。

**只读靠 Claude Code 自己的权限，tycho 不另写过滤**（实测：[../spike/router-readonly.md](../spike/router-readonly.md)）。启动参数和环境只在 `service/session-host.ts` 一处：

| 参数或环境 | 管什么 |
|---|---|
| `--restricted` | Read、Grep、Glob 按写出来的路径出不了工作目录；不读主人和仓库的 settings 文件，那里的放行规则（比如主人放行的 `git push --delete`）、插件和 hooks 到不了总控；`--settings`（档位和排除项）和管理员下发的 managed settings 照样生效 |
| `--tools Read,Grep,Glob,Bash` | 会话里只有这四个内置工具，没有编辑工具 |
| `--permission-mode default --permission-prompts none` | 没人回答权限提示：没放行的一律拒，不会卡着等。git 不写进放行清单，CLI 自己判断哪些 git 命令只读，连参数和重定向一起看（`--output=`、`-c`、`> 文件` 都拒） |
| `--allowedTools mcp__tycho` 和 `Bash(gh pr view:*)` 等 | 编排工具；gh 只放行看 PR、CI、issue、仓库的子命令（`pr view/list/diff/checks/status`、`run view/list`、`issue view/list`、`repo view`），它们没有写文件的参数；不放 `gh api` |
| `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` | CLI 自己从它起的每个子进程（Bash、hooks、MCP 服务）的环境里去掉登录变量。绑定账号时令牌在总控的环境里（Windows 上的 `claude.exe` 不从描述符读令牌），没有它，`gh … --jq env` 就能把令牌读回给模型；按文字写的拒绝规则拦不全（`-aq`、`-vq` 这种合写的短选项就漏过去）。这个开关会把权限模式定为 default，所以上一行写的就是 default |
| `GIT_OPTIONAL_LOCKS=0` | git 自己的开关：`git status` 这类读不刷新主人的 `.git/index`、不抢它的锁 |

`init` 的工具列表必须恰好是这四个加编排工具，否则照旧停摆。新起的进程跑起来了、没初始化就带着退出码自己退出（比如 CLI 太老、不认 `--restricted`），总控停摆，原因里是 CLI 自己的话，那条消息放回队列，不是一条条记成待核实。服务照常。

**保证的是“不能写”，不是“读不到”。** “不能写”针对模型：写的路只有编排工具。读的范围不当保证：整个代码目录都读得到，包括 `.git/config`、`.env`、没提交的文件；`--restricted` 按写出来的路径判断，仓库里指向外面的符号链接或目录联接能读出去；CLI 的只读 git 判断不看参数值里的路径（`git blame --ignore-revs-file <工作目录外的文件>` 被放行）；gh 用主机上的登录，`--repo` 能指别的仓库，`--web` 会打开主机的浏览器（都见 spike）。这和别处一致：总控跑在运行服务的用户下，同一台机器上的 Worker 本来就读得到数据目录，边界是机器（AGENTS.md）。项目隔离管的是 tycho 的任务和知识；gh 只看本项目的仓库写在提示词里，是要求不是边界。档位里管权限和沙箱的键（`permissions`、`sandbox`）本来就由 `checkTier` 拒收，档位放不进写的放行；档位的 `env` 关不掉凭据清除（启动环境优先，见 spike）；档位里主人自己写的 hooks 和管理员的 managed settings 照常生效，那是主人或管理员的配置，不是模型能加的，和 Worker 一样透传。环境里的其他变量（登录以外的）照样读得到，边界是机器。

**读进来的文字是资料。** 代码目录里的 `AGENTS.md`、`CLAUDE.md` 由 CLI 照常读进来，是这个项目的约定；它们和代码、PR、CI 日志里的文字一样可能被别人写过，提示词写明不当指令，退回重做时写失败的摘要而不是整段原文。总控能把读到的东西写进任务（这是它唯一的写），这一点是提示词的要求，不是结构：Worker 收到的 brief 是总控写的。全局入口照旧排除（[knowledge-and-skills.md](knowledge-and-skills.md) §4.1）。

**工作目录。** 项目的默认来源是**主机所在机器上的一个文件夹**（`machine_uid` 是主机那次本机接入的登记号）时，总控就在那里起；项目的来源是仓库、是别的机器上的文件夹、或者一个来源都没有时，在 `<数据目录>/router-empty/` 这个空目录里起：没有代码可读，gh 带 `--repo` 仍能看。文件夹不在了或读不了，也用空目录，日志里写明，不因此停摆。起进程时在文件夹里起不来（比如刚被删掉、进不去），这一次不取消息，日志写明，不停摆；这个项目之后在空目录里起（另开一个记着空目录的上下文），直到项目换了来源、主人点“重启总控”或服务重启。用的目录和当时的来源记在执行器上下文的 `launch_json`（`cwd`、`code_dir`）。磁盘只在起进程时看，而且不占服务的事件循环（挂住的网络盘只拖住这个项目这一次启动）；每条消息之前只比账本里的来源。项目的默认来源变了，和“知识正文变了”走同一段换上下文（原因“总控的工作目录变了”）：Claude 按目录存会话，换了目录续接不上。升级前开的上下文没记目录，交给 CLI：它续接不了就是“续接被拒”，消息放回、换新上下文。

**提示词**（`service/router-prompt.md`）写明能读什么、写只能派任务；交回之后用 gh 核实 PR 的改动与 CI（执行者的分支不在主机的任何代码副本里，总控也不能 fetch，所以只交分支没开 PR 的看不到代码，要如实说），CI 没跑完就建一次性定时触发器回来看，挂了按状态 `rework_task` 或另建任务；派几个可能碰同一处（文件、接口、账本或协议版本、配置项）的任务之前先读代码核对，写清分工和合入先后。代码目录是已合入的基线，未合入的并行改动靠 gh 看 PR。CI 的结果是总控读到的资料，不是账本里的事实：服务不据它做任何决定。

## 项目的生命周期（2026-11-12）

项目从新建到删除只经过五件事：新建、改名、暂停、归档、删除。名字只是显示；暂停是临时停手；归档是收起来不用了；删除是空项目随时可以删、有历史的项目归档后可以删。每一件事各自由账本的一个动作做完，控制台和企微读同一个状态（账本版本 35 加 `project.archived_at`；删除的清理记录、用量留下的时长和“这一轮没报用量”在版本 38；名字一直是一个可改的列）。

| 动作 | 任务 | 总控 | 消息 | 触发器 | 企微 | 机器上的代码副本 |
|---|---|---|---|---|---|---|
| **新建** | 没有。 | 没有上下文；第一条消息到达时才起。 | 没有。 | 没有。 | 可以“进入”。 | 没有。 |
| **改名** | 不变：任务属于项目编号，不认名字。 | 不换上下文；下一条消息仍用它。 | 归属不变。 | 规则和记录不变。 | 按新名字匹配；当前项目按编号保留，所以仍指向它。 | 不变。 |
| **暂停** | 状态不变；不建新 Run，失联的一轮不判定、不接续。 | 不取新消息；在跑的那一条做完。 | 照常入账，回一句“项目已暂停，恢复后处理”。 | 到点的和 Webhook 来的拒收（`project_paused`），游标照常前进，不推。 | “项目”列表标“已暂停”；可以进入，消息回暂停。 | 不清理。 |
| **归档** | 和暂停一样停手：不建新 Run，失联的一轮原样等。 | 和暂停一样不取消息。 | 照常入账，回一句“项目已归档，恢复后处理”。 | 和暂停一样拒收，原因是 `project_archived`，游标照常前进。 | 不出现在“项目”列表，不能按名字切过去；临时当前项目已归档时当作没有当前项目；固定的项目归档后仍保留绑定，新消息待归属，可以用卡片换绑。 | 不清理。恢复后一切照旧，包括归档前是否暂停。 |
| **删除** | 一个事务删掉：任务、轮次及其记录和产物登记、审阅绑定、输入、审批卡、消息、会话段、执行器上下文、触发器（规则、投递、游标）、项目范围的知识条目和提议、推送、企微当前项目选择、派生机器邀请、项目行本身。 | 已经停住。 | 一条不剩。 | 没有规则或投递记录；tycho 级的入站来源不删，只把它从放行清单里去掉。 | 指向它的当前项目选择一起删掉。 | 主机 `releases/<run>/` 下的登记产物删掉；机器上 `tasks/<task>/repo/` 的代码副本记进 `work_cleanup`，由保留期清理那套命令发出去并确认。不碰代码目录和 GitHub 仓库。 |

- **归档不改任务状态、不删任何东西。** 恢复只把 `archived_at` 清掉：归档前是否暂停照原样，任务、消息、触发器、知识、机器上的代码副本都还在。已结束的任务照“结束满 7 天清理”走，与归档无关。
- **归档的项目暂时不问主人，恢复后照旧。** 每日简报和缺登录提示（`projectsWithoutLogins` / `no_login`）不列已归档的项目。“等你”提醒仍只回答账本里的事是否还在等（`pushStillWaiting`，归档不掺进去）；`tick` 选行时跳过已归档项目的推送行：不发提醒、不计提醒次数、也不关闭，行保持 open，恢复后的下一次 `tick` 照常判断和提醒。暂停只是临时停手，照旧提醒。和停手条件放在一起的 `ARCHIVED_AT` 是这几处同一个判据，各处不再另写。
- **删除分两种。** 从没留下记录的空项目随时可删，不用先归档；有历史的项目必须已归档，并且没有还没结束的轮次、没有可能还在跑的总控进程、没有会因这次删除而失去意义的知识把关或整理任务还在跑。拒绝时写明原因：“先归档才能删除”“还有 N 轮在跑，等它们结束”“总控还在处理，等它空闲退出后再删”“还有 N 个知识把关或整理任务在跑，等它们结束”。判定只在账本 `projectDeletable` 一处，接口、`projectView.deletable` 和页面都用它；删除接口还要 `confirm_name` 与项目名完全一致，页面要求主人把名字打全才让按钮可点。**总控空闲退出后 `router_context.live_at` 被清掉**，所以归档后总控不再取消息、空闲超时就会退出，这条不会长期卡住；删除入口不去停任何进程。
- **删什么、留什么。** 一个事务里删掉项目自己的任务、轮次及其记录和产物登记、审阅绑定、输入、审批卡、消息、会话段、执行器上下文、触发器规则（连同投递记录、游标）、项目范围的知识条目和知识提议、推送、企微当前项目选择、派生机器邀请，最后删项目行。保留：适用于所有项目的知识条目（出处或证据里指向被删任务、轮次的改成文字“来自已删除的项目 <名字>”，不留悬空编号）、其他项目的行、`change` 行（`task_id` / `run_id` / `message_id` 置空，不删行）、主人的代码目录和 GitHub 仓库。**入站来源也不删**：它是整个 tycho 的对象，属于调用方，钥匙跟着来源走；这次只把被删项目从它的放行清单里去掉（清单可能因此为空，来源还在、放行不了任何项目），和保留的知识条目去掉本项目是同一件事，算进 `scope_removed` 的“入站来源”。**用量不变**：`usage` 行保住数字、日子、登录和计量单元（`run_id` / `context_id` 置空，同一行写上 `dropped_source` 和 `dropped_unit`），用量页把它单列成“已删除的项目”而不是“额度查询”；轮数和时长同样不变——那一刻的时长写进同一行的 `duration_ms`，而报过用量的轮次和没报过的都一样：没报过用量的一轮（`input_tokens` 等四个数在账本里是空，不是零）为它写一行只有计量单元、时长、没有模型的 `usage` 行，用量页照样算它一轮、照样说它没报用量，不伪造执行器用量，也不把两轮说成一轮。**无项目的知识把关/整理任务不删**：它们不属于任何项目，只断引用，按三种情形分别表达——提议被删或它的输入随项目消失时，那份等待中的提议按现有“输入变了”的路径转 `stale`，它的把关任务随之放弃；整理任务从 `knowledge_json.entries` 里去掉已删条目，还有可整理的照常排队，没得整理就放弃；已经结束的任务只是记录里不再提被删的东西。三种都把该清的 `knowledge_json` 清掉，页面不会念出一个已经不在的编号，任务行和它的记录都留着。已经冻结的提议不改写：交了就冻结，改它等于改历史。唯一的例外是已发布提议 `final_json` 里每个 output 记下的“它变成了哪个条目”（`knowledge_id`）：那个条目被删了，这个名字就去掉，不留一个指向空处的编号；提议本身提交的内容一字不动。别的项目或无项目的任务、审批、消息、触发记录（`merged_into`）引用被删任务、轮次、消息、触发记录时，引用列置空或改写；不连带删掉别处的东西。审计一行 `project.delete`，detail 写 `{project_id, name, counts, scope_removed, canceled, reduced, finished}`：`counts` 是会删掉的，`scope_removed` 是保留但去掉本项目的，`canceled` 是随之放弃的未结束知识任务，`reduced` 是保留、材料变少、照常排队的整理任务，`finished` 是已经结束、只断引用的知识任务；确认框、审计和执行都从账本同一份删除集合派生，不各查一套，`canceled` 不把后两种算进去。
- **磁盘上清什么。** 主机 `releases/<run>/` 下这一轮登记过的目录由 acceptor 的 sweep 删掉，走保留期清理同一条逐目录的删除路径：一个目录删不掉不拖住别的待清理轮次，也不拖住普通那一遍，那一行留到下一次 sweep 再试，只有目录真的不在了才在账本里确认（`noteDeletedReleasesDropped` 写失败也一样，下一次补上）；机器上 `tasks/<task>/repo/` 的代码副本复用保留期清理：删除事务先在 `work_cleanup` 里按轮次记下登记编号和机器、节点，Run 行删掉后这份记录还在，客户端能收就发 `drop_task_code`、确认后才记 `code_dropped_at`；旧客户端、离线的机器留到以后，不假装清掉了。
- **判定只有一处。** 停手仍是 `service/messages.ts` 里那一个条件（暂停或归档），`ARCHIVED_AT` 是从它取的“已归档”片段；需要区分原因的四处只用同一个 `projectStopped` 回答 `paused` / `archived` / `null`，文案在 `shared/labels.ts`。

## 企微聊天选项目（当前规则）

在企微私聊说“我想换个项目”或“有哪些项目可以选”，Tycho 会发一张项目选择卡。当天首次打开私聊也可以用欢迎卡。项目按最近选择排序，每页最多三个；正文列出编号和完整项目名，点对应的“选1”“选2”“选3”，用“前页”“后页”翻页。发送“项目 关键词”可按部分名称搜索。选中后，新消息交给该项目总控。点“固定”建立固定关系，之后可换绑或解绑。群聊里 @ 机器人发送“项目”，从卡片选择项目后该群使用固定关系。解绑后需重新选项目。普通对话回复不反复附项目卡。选择器只影响以后发的消息，已暂存的消息用归属卡逐条处理。

固定关系以 `front_desk` 的空发送人行保存，变更时清除该聊天所有临时选择；只允许白名单操作。卡片令牌在内存中限时保存，绑定聊天和发送人，绑定变化后旧卡不能覆盖新关系。固定聊天中点名其他项目或引用其他项目的任务、轮次会被拒绝，不投给任何总控；审批仍按问题对象处理。归档的固定项目保留关系，新消息进入待归属，卡片可以换绑；删除项目时关系随之清除。未固定的聊天保留原来的“进入”、项目名前缀和待归属规则。

2026-11-14 的真实 Windows 企微私聊验过甲项目建任务后切到乙，甲的待验收通知仍回原聊天。后续实点解绑乙、选择并固定甲、直接换绑乙，审计时序与卡片一致。乙连续三轮普通回复均未附加项目卡，再说“我想换个项目”即在最新消息处打开新卡，无需翻历史。七项目的中间页六个短按钮分成三行两列，文字完整。手机显示仍待实测。验收结束后候选已停止，原服务和企微已恢复。本轮 Windows 自动测试为根测试 3281 项通过、24 项按条件跳过，Console 652 项通过，两套类型检查均通过。
