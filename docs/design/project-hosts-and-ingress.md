# 项目归属与开放入口

读者是部署多套 Tycho 的主人和接入外部渠道的实现者。候选版提供独立服务目录、便携项目的离线交接和外部结果回读。部署步骤和实际验收见[部署手册](../deploy.md#初始化另一套服务并移交项目)与[终态验收](terminal-architecture.md#82-已有证据和下一道门)。

## 项目归属

**办公、家庭等需要独立运行的环境可以各自部署一套 Tycho。一套服务可承载多个项目，每个项目同一时刻只由其所属服务写入。** 创建项目默认归属当前服务，从统一入口创建时由用户选服务。项目 ID 在改名、调整执行机器和迁移时保持稳定。所属服务保存项目的会话、任务、审批、触发器和结果，负责操作鉴权。备份、恢复和迁移也以归属服务为边界。迁移项目时，旧服务停止写入并处理在途工作，新服务接管数据和写入权，再更新入口路由。

执行位置由项目需要决定。QL 的总控可在办公 Windows 运行，经项目自己的 skill 和平台 API 申请、使用及释放集群 Linux 实例。家庭助理可在 NAS 上运行，需要时经家庭局域网调用其他设备。Tycho 保存任务、授权和交付记录。资源申请和实例生命周期沿用各环境已有的工具。能换机接续的工作从可访问且已核实的提交或产物继续，保存在旧节点的独有进度等核实或明确重做。

## 入口和故障边界

浏览器通过 HTTPS 访问统一入口或各服务自己的授权地址。外部入口可承载反向代理和 IM 适配器，按项目 ID 将请求转到归属服务。入口只保存转发需要的目录和聊天绑定。控制台可分别读取各服务授权返回的项目列表，按项目 ID 汇总，失联时保留上次读到的目录并标出离线。各服务的项目目录和账本仍由该服务负责。统一入口故障时，独立可达的控制台地址可以继续使用。服务内的定时和业务事件在该服务运行时照常处理。此次设计采用 HTTPS 路径。

## 项目入站

人从 IM 或控制台发消息，外部系统发签名 Webhook，各服务在本地产生定时和内部业务事件。项目服务按来源和事件类型核对权限、去重和入账，再交给总控或对应的业务操作。审批按钮由所属服务核对操作者和审批对象。IM 还负责回话、通知和交互，可按平台能力逐个增加企微、飞书、个人微信等适配器。聊天可固定到项目，也可按需切换。外部系统保有自己的触发条件，Tycho 管理服务内的定时与业务订阅。

自定义群聊规则或快慢分流可以运行在外部适配器中。适配器按它获准看到的消息筛选，简单问题可以按规则快答。需要调查、开发或持续跟踪的请求，才附上必要上下文和原消息引用，投递给相应项目。不同群可以用不同规则。

现有 `tycho-v1` 入口为 `POST /inbound/<来源编号>`。调用方使用来源密钥签名，发送稳定的事件 ID，按来源获准的项目范围投递。项目服务返回受理凭证，重试同一事件可复用凭证。调用方以自己的来源身份受理，其权限受来源和项目规则约束。凭证表示事件已入账，任务状态和交付由账本记录。

外部适配器用 `GET /inbound/<来源编号>/result/<受理凭证>` 查询自己获准的事件。允许公开答复的回执由总控单独发布，适配器用原消息引用回到同一线程。基于这套协议的飞书桥接已验证请求和回程，仍需实际飞书群聊验收。[回程协议](triggers.md#24-由签名来源回读自己的回执) · [飞书桥接](../../integrations/feishu/README.md)

## 验收

用一个实际群聊适配器验证闲聊忽略、简单问题快答、复杂问题入账、结果回原线程。相同事件重试只入账一次，另一个来源无法查询该事件的结果。关闭统一入口后，通过另一个已授权的服务地址仍能访问项目，办公或家庭服务内的定时触发照常。
