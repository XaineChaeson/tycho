# 触发器：定时、外部事件和内部事件把消息交给项目总控

读者：主人和实现者。状态：**已确认**（2026-11-09 主人确认；协调者稿经 Codex 对抗审阅后修订）。按终态写，不做过渡兼容。依赖 [project-sessions.md](project-sessions.md)：触发器把消息投给项目总控，结果按它的"主动触达"告诉主人。

## 结论

1. **触发器属于一个项目，只做一件事：在约定的时机，把一条消息可靠地交给这个项目的总控。** 接下来做什么由总控按它的规则和工具决定。触发器不执行任务、不重试业务、不监督进程。
2. **规则跟着掌握事实的那一方。** tycho 自己的时间（定时）和自己的业务事件（内部事件）是项目里的触发器；外部世界的事件，规则留在外部系统自己那里（GitHub 的 webhook 设置、别的项目自己的调度），tycho 只用**入站来源**（§2.2）接收一次次投来的请求，按 tycho 已知的事实路由到项目。外部的格式由内置的翻译器认，新种类随 tycho 发布；不在服务里加载外部代码。
3. **受理了才记账，记账了才回"收到"。** 规则（触发器）和受理记录（触发记录）分开存；触发记录、投出的消息、调度游标在同一个事务里落账。内部事件更进一步：在产生它的那次业务状态转换的事务里一起落账。
4. **触发来的消息不是主人的话。** 它的来源身份和项目一起，在工具接纳时从同一条链绑定；只有主人能做的动作（回答问题、放行、改项目准入、免审验收）本来就不在总控手里，触发不会让它们变得可用。
5. **不形成循环。** 由触发引起的工作产生的后续事件，不会再次触发触发器。
6. **触发器由控制台和项目总控管理，入站来源只由控制台管理。** 项目总控只能管本项目的触发器；入站来源是整个 tycho 的，它的密钥和能投到哪些项目只在控制台由主人定，不进会话。
7. **`schedule_wake` 保持原样。** 它是"到点让某个任务重新排队"，走任务状态机；触发器是"到点给总控投一条消息"。两者只共用时间解析和到期扫描。

## 起因

主人 11-09："会话的触发是不是也是一个设计？成熟的产品都有不同的事件触发、插件化设计……可以方便地布置定时任务或者触发任务。"参考了 dsh-superagent-prototype 和 agent-autoloop，以及 Claude Code、Codex、Cursor、Copilot、OpenClaw、Hermes、Devin、n8n 的做法（附录）。

现状：只有 `schedule_wake`，它预约的是任务，不是总控；"每天早上做一次检查""CI 失败就告诉某个项目""一项工作上线后接着做下一步"这类需求没有入口。

## 1. 对象

| 对象 | 保存什么 |
|---|---|
| **触发器** | 不变的编号、所属项目、名字、启用或停用、来源及其参数、固定指令、错过策略、有效截止时间（可选）、是否推送本回合终稿、修订号、谁建的 |
| **触发记录** | 只为**已受理**的发生而建：接收身份（见 §4）、来源事件编号、原定时刻与实际受理时刻、受理时冻结的触发器修订、事件数据（有大小上限）、它的消息、结果（已投递 / 已合并进另一条 / 过期） |
| **消息**（现有） | 真正交给总控的正文、来源身份、所属项目和会话段、处理状态。正文只存在这里，触发记录只引用它 |
| **调度游标**（每个定时触发器一个） | 已经处理到的原定时刻；只向前推进 |

没被受理的请求（签名错、超限、队满）不写触发记录，只计入按触发器的拒收计数和最近一次原因，避免风暴把账本写满。

控制台按触发记录如实显示"已投递""已合并""过期"，另显示拒收计数；不笼统地写"执行成功"。

## 2. 来源

### 2.1 定时

- 一次性（绝对时刻）、固定间隔（锚点 + 间隔）、cron（五个字段）。cron 必须带 IANA 时区（例如 Asia/Shanghai），默认取主机时区并显式存下来；页面显示下一次的本地时间、时区和 UTC 时刻。
- 夏令时：不存在的时刻跳过，重复的时刻只取第一次。
- 最小间隔是设置项。

### 2.2 入站来源

2026-11-12 主人确认：外部的触发规则不归 tycho 管，tycho 只接收“这一次的触发请求”。所以外部事件不再是项目里的一种触发器，而是**整个 tycho 的一个入站来源**：一个调用方（某个 GitHub 仓库的 webhook、别的项目的调度器、n8n 之类）一条，一个入口地址、一把（可轮换的）密钥、一个翻译器种类、主人放行的项目清单。什么时候投、投什么，由调用方自己的规则决定。

**来源保存：** 不变的编号、名字、翻译器种类、启用或停用、放行的项目（至少一个）、说明（可选，主人写给总控看的：这是谁、它的请求一般怎么处理）、是否推送本回合终稿、谁建的；拒收计数、连续问题（§8）和密钥挂在来源上，和项目里的触发器一样（密钥的领取、过渡和退役沿用第 3 步的做法，见文末第 4 步的实现记录）。

**翻译器**是内置的纯函数：输入请求头、原始正文和这个来源此刻有效的密钥，输出“签名对不对”和 0 到多条事件（事件编号、目标项目的线索、一行标题、附带资料）。它只验签和映射字段，不发请求、不碰账本；受理、去重、限流、来源身份、循环截断、推送终稿，全部走 §4 的同一个受理入口。本期两种：

| 种类 | 验签与防重放 | 事件编号 | 路由到哪个项目 |
|---|---|---|---|
| `tycho-v1`（通用） | 头 `X-Tycho-Event-Id`、`X-Tycho-Timestamp`、`X-Tycho-Signature`，可选 `X-Tycho-Project`；签名 = HMAC-SHA256(密钥, `v1\n<签名时间>\n<事件编号>\n<项目编号>\n` + 原始正文字节)，不带项目头时项目编号一段是空串；签名时间超出允许偏差就拒收 | 调用方给的 | 项目头写的项目；不写时，来源只放行了一个项目就是它，否则拒收 |
| `github` | `X-Hub-Signature-256` = `sha256=` + HMAC-SHA256(密钥, 原始正文)。GitHub 不签时间和事件编号；保留期内还按已验签的原始正文摘要去重，改事件头也不能重投，期满后仍可重放，页面上写明 | `X-GitHub-Delivery` | 正文的 `repository.full_name` 必须是 `owner/name`，和放行项目上配置的仓库比（不分大小写，认 https、ssh 和 `owner/name` 几种写法）；对上几个就投几个，各是一次独立受理 |

- `github` 的 `ping` 回 200、不受理不计数。附带资料不放整份载荷（可能有几 MB），只放事件种类（`X-GitHub-Event` 加 `action`）、仓库、编号、标题、链接、发起人、正文摘要（有上限）；总控要细节让执行器自己去看。要哪些事件在 GitHub 的 webhook 设置里勾，tycho 不另设过滤。
- 路由不到项目（项目头指了没放行的项目、仓库对不上任何放行项目）拒收，原因“没有对应项目”，只计数。
- **受理身份 = 来源 + 项目 + 事件编号**，其余同 §4（同内容回原凭证、不同内容拒为冲突）。
- GitHub 的事件编号和事件种类不在签名里，不能把换头当成新的事实。同一来源、同一项目在去重期内收到完全相同的原始正文时，复用原凭证、原消息，不延长保留期；代价是不同编号的真实投递如果正文逐字节相同，也只投一次。该判断只用已受理的记录，其他项目和曾被拒收的投递仍可重试。
- 消息第一行是“入站来源“名字”：收到 <种类> 事件 <编号>”，接着说明这是主人放行的外部来源投来的请求、不是主人说的话、附带资料不带任何授权，再是来源的说明（有的话）和附带资料。正文里调用方写的请求，总控按它的规则判断做不做；建任务等正常编排和触发回合一样（§6）。
- 入口 `POST /inbound/<来源编号>`，经门牌对外的不需要登录的路由只有这一条（`outside: true`）；签名是它唯一的认证。没有门牌时只能从内网投。控制台分别显示“没配置门牌，外部投不进来”“门牌连接故障”“可以接收”。
- 密钥只在控制台领取和更换，存 `secrets/`，带密钥编号；更换后旧密钥在过渡期内仍可验证，退役时刻落账。`github` 种类把领到的密钥填进 GitHub 的 webhook 设置。
- 没领密钥、停用前先验签名、拒收的状态码等细节，见文末第 4 步的实现记录。

### 2.3 内部事件

服务在一处声明每种事件：发生条件、稳定编号、载荷、项目怎么推出，并和"主动触达"共用同一份事实判定。本期四种，都对应现有的业务提交点：

| 事件 | 发生条件 | 项目 |
|---|---|---|
| 一项工作整体完成 | 顶层任务进入"就绪等验收"的那次转换（返工后再次就绪是新的一次） | 任务所属项目 |
| 已验收 | 验收的那次提交 | 同上 |
| 已合入 | 合 PR 进主线的那次提交（`task.integrate`；本机并入主机检出已经删掉） | 同上 |
| 已上线 | 上线结果落账的那次提交 | 同上 |

可以按本项目的对象过滤（例如只看某个任务）。"任务停住""机器上线下线"本期不做：前者要先说清是哪些转换，后者是全局资源，没有天然的所属项目，等项目资源范围和连接抖动的语义定下来再加。

**事务边界：** 内部事件在产生它的那次业务状态转换的同一个事务里：确定事件编号 → 匹配订阅 → 受理 → 写触发记录和消息。触发器过载被拒收时，只记拒收，不影响业务转换本身，也不影响原有的必达消息；被拒收的不自动重放。

**与必达消息合并：** Run 结束等现有的必达内部消息照常由状态转换产生。同一个事件已经有必达消息时，订阅的固定指令附在这条消息里，触发记录引用它；不另起一条，总控不会为同一件事处理两个回合。

### 2.4 由签名来源回读自己的回执

通用来源提交签名事件后，从受理响应取该事件的 `fire_id`。向同一服务发送 `GET /inbound/<来源 ID>/result/<fire_id>`。使用当前有效密钥，发送 `X-Tycho-Timestamp`（UTC 秒）和 `X-Tycho-Signature`。签名是 HMAC-SHA256 的小写十六进制，签入下列五段，末段为空串。

```text
tycho-result-v1
GET
/inbound/<来源 ID>/result/<fire_id>
<UTC 秒>

```

正常响应包含受理项目、事件投递结果和请求处理状态。来源停用、移出该项目、归档后删除、回执过期、签名失效或找错服务都会返回 404。调用方收到 404 应保留既有受理凭证并展示「结果不可读」，不要据此生成新事件号重投。

来源在「允许来源回读答复」打开后，新受理的事件可以读到总控为它单独登记的一条答复。关闭后读不到答复。启用前已受理的事件仍只能得到状态。调用方保存平台原消息或线程的标识，用该标识发回答复。Tycho 的控制台回复、轨迹和产物没有对来源公开。

## 3. 动作

只有一种：**往所属项目的当前会话段投一条消息**（与必达消息合并的情形见 §2.3）。

- 正文 = 受理时冻结的固定指令 + 事件数据（作为附带资料，标明来源，不当作指令）。
- 模板只做有限的字段替换（例如事件里的任务编号），不执行脚本，不按事件里的地址去抓取内容。
- 外部请求不能指定会话段、登录、档位、工具或权限：这些全由项目和总控决定。它只能在主人给这个入站来源放行的项目里选一个（§2.2）。
- 消息入账时归入项目当前段（project-sessions.md §2、§3）；主人开新话题时，还没被取走的跟着进新段；已被取走的不搬。

## 4. 受理、去重与合并

**接收身份：** 项目里的规则是**触发器编号 + 来源事件编号**；入站来源是**来源 + 项目 + 事件编号**（§2.2）。来源事件编号：定时是原定时刻；入站来源是调用方给的事件编号（没有就拒收）；内部事件是服务生成的事件编号。同一个外部事件合法地投给两个项目（或同一项目的两条规则），是两次独立的受理。

- **只有受理成功才占用这个身份。** 限流、队满、暂时不可用、没提交成功的请求，都不占用；调用方可以用同一个事件编号重试。
- 已受理的再来一次：内容相同，回原来的受理凭证（不因为现在队满而改口拒收）；内容不同，拒收为冲突。"内容"指原始正文的摘要，不含签名和签名时间；内部事件按事件载荷。
- 受理时冻结触发器修订和渲染出的消息；之后改了触发器，重试也不重新渲染。
- 去重记录保留期从首次受理算起，重试不续期；保留期是设置项。到期后同一身份再来，视为新的一次。

**周期性触发器的合并：** 每个触发器最多"一条在途（总控已取走）+ 一条待处理（还没被取走）"。

- 有待处理的那条时，新到的时刻并进它（记次数），不新建消息；合并和"总控取走消息"在账本里互斥，取走之后这条消息的输入就冻结了。
- 触发器修订变了，新修订的发生不并进旧修订的消息，替换掉还没被取走的那条（旧的记"被替换"）。
- 一次性触发、入站来源、内部事件是独立的事实，不合并：进一个有上限的待处理队列（按项目计，只算触发来的消息，不挤占主人的消息和必达消息），满了就拒收（入站请求回 429）。
- 已取走但结果不明的（`unverified`），按原规则待核实，不当作没执行而自动重投。

**防止风暴，在调用模型之前：** 定时的最小间隔、单个触发器和全局的接收速率、事件数据大小、待处理上限，都是设置项。

**不形成循环：** 来源身份沿着"触发消息 → 总控在这个回合里建的任务 → 这些任务后续的事件"一路带下去；带有触发来源的业务事件不再触发任何触发器。由服务判定，不靠总控自己识别。

## 5. 错过与时钟

三种情况分开：

| 情况 | 行为 |
|---|---|
| 服务停机期间错过 | 按触发器的错过策略处理 |
| 触发器被停用 | 不积压；重新启用后从未来的第一个时刻开始 |
| 全局的派发暂停（现有） | 沿用它原有的含义，触发器照常受理，消息照常入账 |

- **错过策略两种：** 补最近一次（记下合并了几个时刻）；跳过（只记"错过"，不投消息）。周期性触发器默认补最近一次，一次性的默认补投。
- **有效截止时间**和错过策略是两件事：过了截止时间的，不论什么策略都只记"过期"。
- **正常的扫描延迟不算错过：** 原定时刻之后在宽限期（设置项）内受理的，是正常触发。
- **游标只向前：** 墙钟前跳，跳过的时刻按错过策略处理；墙钟回拨，已经处理过的时刻不会再触发。修改规则后从未来的第一个时刻开始，不追溯。

## 6. 来源身份与权限

- 消息的来源身份（主人 / 触发器 X 的某次受理）和项目，在工具接纳时沿项目会话的同一条链绑定：进程令牌 → 已接纳的回合 → 消息 → 项目与来源身份；在读请求体之前完成，回合内不变，不接受模型传来的来源参数。
- 只有主人能做的动作，本来就只在主人的入口：回答问题、放行设备和机器、修改项目准入（登录、机器）、不经审阅验收。总控没有这些工具，触发也不会让它有；不需要再加"触发回合禁止这些"的判断。
- 建任务、选职能、用项目已允许的派生机器名额，是正常编排，沿用现有校验，触发回合和主人回合一样。
- 入站来源调用方的身份只来自验证过的密钥（哪个来源），不采用事件数据里自报的任何身份；一个请求带上来的项目编号也只能是来源放行过的那些。
- 正文里声称"已获授权"之类的文字不产生任何效力：授权只认账本和经过认证的动作。

## 7. 谁来管

- **控制台：** 项目页列出这个项目的触发器、最近的触发记录和拒收计数；新建、修改、停用、删除。入站来源在整个 tycho 的一页里：新建（选翻译器种类、放行的项目）、修改、停用、删除，地址和密钥在这里领取、轮换，并列出最近的受理记录和拒收计数。
- **项目总控：** 用工具新建、查看、修改、停用本项目的定时和内部事件触发器；作用域由服务端从会话推出（project-sessions.md §4）。入站来源它不能建也不能改。
- 主人在企微里说"每天早上 8 点检查一下……"，就是让项目总控去建一个定时触发器。
- 没有配置文件或命令行这第二个管理入口。

## 8. 结果怎么告诉主人

- 按 project-sessions.md §2.1 的三级规则：总控处理触发消息时提问就是"等你"，产出成果就是"成果"，其余不推。
- **推送本回合终稿**（触发器上的开关，适合"产出就是结果"的例行报告）：这条触发消息被成功处理后，把总控本回合的最终回复推给主人。按受理时冻结的定义、按消息编号去重、与消息收尾在同一个事务里写进 Outbox。它只管这一个回合；由此派出的任务的成果，走正常的"成果"通知。结果不明（`unverified`）的如实显示"未确认完成"。
- 触发器或入站来源本身出问题、需要主人处理时（签名一直验不过、待处理一直满、规则失效），按"等你"推一次，同一个问题合并提醒。
- 全项目的每日简报是服务自己生成的确定性通知，不需要唤醒总控。

## 9. 例行任务的经验

触发器保存"什么时候做、做什么"；知识和技能保存"据什么判断、怎样完成"；触发记录和运行历史保存"发生过什么"。例行任务里发现的经验，引用触发记录、任务、Run 和产物，走知识的提议和把关；不为每个触发器另建一份笔记。处理到哪儿了（上次检查到的位置之类）属于账本里的任务或项目对象，不写进触发器。

## 10. 不做

| 不做 | 理由 |
|---|---|
| 加载外部代码的插件事件源 | 安全风险，也违背"编排层，不是 harness"（[merged-design.md](merged-design.md) §1.1）；复杂的外部系统可以先由 n8n 之类的工具处理，再投到这里的入站来源 |
| 看门狗 agent | 服务存活交给服务管理器；机器和 Run 由现有恢复机制核实；被监督的服务唤醒自己的救援者，覆盖不了服务本身停掉的情况 |
| 触发后直接建任务或启动 Worker，绕过总控 | 少了一层判断；执行、权限、单活跃 Run 已有明确的负责方 |
| 多来源的"且"、等待窗口、工作流画布、任意代码条件 | 当前没有使用方；多个来源要做同一件事，先建多个触发器 |
| 积压的全部时刻逐次补跑 | 恢复时会形成风暴 |
| 把 `schedule_wake` 改成"到点给总控发消息" | 会把"任务已获准重新排队"变成"到点再让总控决定"，行为不等价 |
| 除通用协议和 GitHub 外的产品原生翻译器（GitLab、飞书等） | 有真实接入需求再加，加时写明它能提供哪些保证 |
| 入站来源上的事件过滤、固定指令 | 过滤属于调用方自己的规则（如 GitHub 的事件勾选）；怎么处理属于总控和项目常驻规则 |

## 11. 分步

在项目会话第 1 步（项目总控、消息归属、工具作用域）和第 2 步（主动触达）之后：

1. 触发器、触发记录、调度游标；定时来源（三种 + 时区 + 错过策略 + 截止时间 + 宽限）；受理身份与去重；周期合并与有界队列；限流与拒收计数；来源身份绑定与循环截断；项目总控的管理工具；控制台列表与编辑；与 `schedule_wake` 共用时间解析和到期扫描。
2. 内部事件来源：四种事件的一处声明、与业务转换同事务、与必达消息合并。
3. Webhook 来源：v1 协议、密钥领取与轮换、门牌路由、三种接收状态的显示。
4. 入站来源（2026-11-12）：把第 3 步的“Webhook 触发器”整个换成 §2.2 的入站来源，旧的路由、工具参数、页面和设置一并删掉，不留两条路；账本迁移把现有的 Webhook 触发器各转成一个只放行原项目的 `tycho-v1` 来源（固定指令转成说明，密钥和退役时刻原样带过去），它们的触发记录保留。

## 第 1 步的实现记录

设计没写死、实现时定下的细节，按“谁依赖它”留在这里：

- **账本（版本 21）。** 触发器 `trigger_rule`（规则、修订号、拒收计数和最近一次原因、删除时刻）、触发记录 `trigger_fire`、调度游标 `trigger_cursor`（每个定时触发器一行，只存“处理到的原定时刻”）；任务多一列 `trigger_fire_id`，内部消息多一列 `task_id`（它说的是哪个任务）。删除是标记删除：触发记录要留着说明发生过什么。
- **时间只有一处**（`service/schedule.ts`）：带时区的时刻解析（`schedule_wake` 用的就是它）、三种规则的下一时刻、错过时刻的计数（数到一万为止，最后一个时刻另外按窗口往回找）、两次触发的最近间隔。cron 是五字段，日和星期按 Vixie cron 的规则组合：两个字段只要有一个以 `*` 开头（`*/2` 这种步长也算），一天要同时落在两个字段里；两个都不以 `*` 开头才是“任一”。月和星期可以写英文缩写；按时区的墙钟算，夏令时里不存在的墙钟时刻跳过，出现两次的只取第一次。cron 不写时区就用主机时区，并且存下来。五年内不会触发的 cron 建不了。最近间隔不靠抽样：墙钟上的最近间隔按字段算准（同一天相邻两个时刻，和相邻两个匹配日之间，日子的规律 400 年一循环，扫一个循环），真实时间只在时区换偏移时和墙钟不同，而跨过每一次换偏移的相邻时刻只有一对，搜索期限（五年）里的每一次都算上。
- **到期扫描**是账本的 `fireDue`：先做 `schedule_wake` 的到期，再做定时触发器，每个触发器一个事务，一个出错不拦别的。服务启动时先扫一次，之后独立的计时器每 5 秒扫一次（不挂在派发循环上：派发一轮可能要等机器好几分钟，会把准时的触发拖成迟到）；降级和恢复清点期间不扫，全局暂停照扫。派发循环仍在自己那一轮里做 `schedule_wake` 的到期，好让被唤醒的任务在同一轮派出。
- **准时与错过。** 原定时刻之后 `triggers.graceMs` 以内受理的是准时的，正好等于宽限期也算准时。一次扫描看到的时刻里，宽限期以外的算错过：补最近一次时只投最近的那个时刻一条，记下一共几个时刻、其中几个是迟到的；跳过时，迟到的合成一条“错过”记录（记个数），宽限期内的照常投。个数数到一万就停：记录上标“截断”（`merged_capped`），事件数据带 `moments_at_least`，消息、`list_triggers`（`moments_at_least`）和控制台都说“至少 N 个”，不把下限当精确数。
- **截止时间。** 截止之后的第一个时刻记一条“过期”，此后这个触发器再没有下一次，扫描也不再碰它。
- **游标只向前。** 建、改（任何一项变了都是新修订）和重新启用都把游标推到 max(游标, 现在)；停用不动游标、也不扫，重新启用不补。回拨的时钟看到的“下一次”在游标之后，所以不会重触发。改规则时只有时间规则真的变了（按规范形式比，页面每次都把整份定义发回来）才按新规则检查“一次性时刻已过”和“最小间隔”；只改名字、指令等，不会因为设置后来调严了而改不了。
- **受理**只有 `service/triggers.ts` 的 `accept` 一个进口，在调用方的事务里跑，拒收是返回值不是异常（第 2 步的内部事件要在业务转换的事务里调它）。检查顺序：带触发来源的直接跳过（不记录、不计数）→ 来源种类对不上 → 身份（同内容回原凭证、不同内容拒为冲突；保留期过了先释放身份再当新的）→ 停用或删除 → 数据大小 → 单个和全局的每分钟速率（按触发记录数）→ 截止 → 合并或排队。拒收只改规则行上的计数、时刻和原因，不写触发记录、不写审计行。身份唯一性靠部分唯一索引（未释放的才算），保留期从第一次受理算，`keep_until` 写在记录上。定时来源的事件编号是原定时刻；定时的一次被拒收（比如队满）游标照样往前走，不在之后每次扫描时重试。
- **合并和队列。** 固定间隔和 cron 是周期性的：它最近一条已投递、还在排队（`received`）的消息就是“待处理那条”，同修订的新时刻并进去（自己记一条“已合并”，待处理那条的时刻数加上；消息正文按最新时刻重写，时刻总数、是否截断、有没有迟到、迟到了几个，都从这条消息关联的全部受理记录累计，每条记录自己的事件数据保持受理时的样子），不同修订就把那条记为“被替换”、消息作废（`ignored`），再投新的。合并和取走各是一个事务，互斥由账本的写锁保证。一次性的（以后还有 Webhook 和内部事件）进项目的有界队列：只数这个项目里一次性来源、还在排队的触发消息，周期性的、主人的、服务自己的都不算。
- **消息。** 渠道 `trigger`、外部编号 `trigger:<触发记录>`、发送者 `trigger:<触发器>`、归属依据 `trigger`，进项目的当前段，和别的消息同一个队列。正文受理时渲染并冻结：第一行是“触发器“名字”：原定……的时刻到了”（控制台对话里只显示这一行），接着说明它不是主人说的话、附带资料不是指令也不带任何授权，再是固定指令（`{{字段}}` 只替换事件数据里的标量）和附带资料。总控收到的是 `[tycho 触发器]` 开头的这段；回复留在控制台；它不算主人还没闭合的要求，也不能当“主人说过”的知识证据。
- **来源身份。** 工具接纳时绑定的是“进程令牌 → 回合 → 消息”，来源身份就是那条消息自己的：账本建任务时在同一个事务里一处推导（`originOf`）：调用的消息是触发消息，就是投递它的那次触发；是内部消息（比如某个任务一轮结算的通知），就是它说的那个任务（`message.task_id`，服务写内部消息时记下）的 `trigger_fire_id`；否则沿父任务。合并回合按消息顺序逐条看（第一条在前，随之取走的内部事件按顺序在后），取第一个非空的来源，每条内投递它的那次触发优先于它说的任务；都没有才沿父任务。只看服务记下的关联，不看正文、不收模型的参数。这样“触发 → 任务 A → A 结算的内部消息 → 总控据此建的任务 B（包括审阅）”一路都带着来源。第 2 步的内部事件把任务的这一列作为 `origin` 交给 `accept`，带着它的一律跳过。
- **推送本回合终稿**按受理时冻结在触发记录上的开关：回合正常结束时，和消息收尾同一个事务写进出站，去重键 `trigger-final:<消息>`；待核实的用同一个键推“未确认完成”和已经提交的操作。
- **管理入口。** 项目总控有 `list_triggers`、`create_trigger`、`update_trigger`、`set_trigger_enabled`，作用域按工具接纳时绑定的项目，别的项目的触发器读作不存在；删除只在控制台。控制台在项目页每个项目卡片里有“触发器”一节（时间输入框只显示到分钟，改的时候没动过的时刻、锚点、截止时间按服务原样的时刻发回去，不截到分钟）：列表（下一次的本地时间、时区和 UTC，拒收次数和最近一次原因）、最近的触发记录（结果和那条消息处理得怎样，结果不明的写“未确认完成”）、新建、修改、停用、删除。接口是 `GET/POST /api/projects/:id/triggers`、`PUT/DELETE /api/triggers/:id`、`POST /api/triggers/:id/enabled`，都经门牌可达（主人登录后的接口）。
- **设置项**（“触发器”一组）：`triggers.graceMs`、`triggers.minIntervalMs`、`triggers.dedupeKeepMs`、`triggers.queueMax`、`triggers.perTriggerPerMinute`、`triggers.perMinute`、`triggers.dataLimitKb`。
- **这一步没做：** §8 里“触发器本身出问题按‘等你’推一次、同一问题合并提醒”（第 3 步做了，见下面）；Webhook 来源（第 3 步）。内部事件见下面第 2 步的记录。

## 第 2 步的实现记录

- **一处声明**（`shared/internal-events.ts`）：四种事件的种类、名字、发生条件的说法，和产生事件的四个构造函数（编号、载荷、它说的任务）。项目不写进载荷：一律是事件所说任务的项目；没有任务的（不是哪一轮产出的上线）没有项目，只推给主人、不触发。账本里只有一个 `internalEvent`：在产生它的事务里，推送表（`PUSH_LEVELS`）有这个种类就推给主人（推送的去重键就是事件编号），再交给触发器的 `offerEvent`。主动触达和触发器读的是同一个事件对象，不各判一遍。
- **四个提交点和编号。** 一项工作整体完成：`settleRun` 里这项工作从“没完成”变成“完成”，编号 `work-ready:<这一轮>`，任务是顶层任务；返工后再就绪是另一轮，编号自然不同。“完成”只由账本的 `workReady` 按整棵任务树判定：树里每个任务都是待验收、已完成或已放弃，至少一个待验收，没有等主人回答的问题；带着子任务的草稿只是分组、不算，别的草稿算没做完。页面的概况（`summarizeWork` 的 `dot`）在有待验收时会盖住失败、等预约和草稿，不是这件事，主动触达的“成果”推送和触发器都不读它。只在一轮结算时判：靠放弃最后一个没做完的子任务变成完成的，本期不发。已验收：`acceptTask`，编号 `accepted:<任务>:<这是这个任务第几次验收>`（按审计行数）。已合入：并入由账本的 `noteIntegrated` 一处收口（合 PR 的子任务在这一轮结算为待验收、回执有一个 commit 时走它，`noteAction('task.integrate')` 也转发到它），编号 `task.integrate:<任务>:<提交或时刻>`；本机并入主机检出的路已经删掉（docs/design/code-sources.md §6），`merged` 只有这一个编号前缀。它发一个 `merged` 事件：只经订阅匹配，不另推，主人收到的是并入的成果推送。已上线：`noteReleased`，编号 `released:<这次上线的标记>`。服务每一轮都读同一份上线结果，所以“这份结果处理过了”是账本里的一个标记（设置表里的 `release_handled`，存最后处理的那份；结果只会往前走），和推送登记、订阅匹配同一个事务写：处理过的不再匹配，当时没有订阅、被拒收、停用的，之后新建、放开、重新启用也不补，不看去重保留期；没提交成功的由下一轮接着处理，不论是这个进程还是重启后的，不看进程什么时候启动（结果文件写好、入账前崩溃的也不会漏）。验收不在推送表里，所以只给触发器。
- **订阅。** 来源 `event`，定义里写 `event: { kind, task_id }`（存在 `params_json`）；`task_id` 可选，必须是本项目的任务，匹配它和它下面的任务（事件所说任务往上的一串里有它）。没有时刻、不建游标，“错过”不适用，截止时间照常（过了截止的事件只记“过期”）。来源建好后不能改；改时只认本来源的那一份定义（页面整份发回来时另一份被忽略），原样发回不是新修订。只匹配启用、未删除的：停用的不订阅，不算拒收。
- **事务和拒收。** 匹配和受理都在业务转换的那个事务里，任一边崩溃就一起没提交；提交后不会再来一次（转换本身已经做过）。被拒收（速率、队满）只在规则上计数，不撤业务转换、不拦必达消息和推送、以后不重放。
- **与必达消息合并。** 一项工作整体完成时，那一轮结算本来就有一条给总控的内部消息（`run:<这一轮>`）：每个订阅的固定指令和附带资料都附在这条消息后面，触发记录的 `message_id` 指它，结果是“已投递”；附上去的不进触发消息的有界队列（队列只数渠道是 `trigger` 的消息）。其余三种没有必达消息，各自新建一条触发消息，进有界队列。附了订阅的内部消息被处理完，订阅要求“推送本回合终稿”时同样推一次（同一个去重键 `trigger-final:<消息>`，几个订阅附在同一条上时只推一次）。合并回合里同样逐条看：每条附了订阅的内部事件都用本回合的回复推自己的一条（键是它自己的 `trigger-final:<这条消息>`），但只有第一条替换 `work-ready:<轮次>` 那句服务的原话；随后一起取走的保留原话。
- **循环截断。** 事件的来源身份是“带来这件事的任务”往上第一个 `trigger_fire_id`：一项工作整体完成看结算的那个任务，其余看事件所说的任务。有就跳过，不记录、不计数。附了订阅的内部消息那一回合建的任务，按 `originOf` 记下附上去的那次触发，所以它后面的事件也不再触发。
- **管理入口。** `create_trigger` 多 `source` 和 `event`，`update_trigger` 多 `event`，`list_triggers` 多 `source`、`event`；控制台的触发器表单多一个“来源”（建好后锁住）、事件种类和“只看这个任务”。规则的说法（`schedule_text`）对订阅写成“内部事件：已合入（……）”，下一次一栏写“订阅的事件发生时触发”。

## 第 3 步的实现记录

下面记的是第 3 步当时的实现。第 4 步把它换成了入站来源（§2.2）：路由、工具参数、页面和设置名都已不存在；签名比对、密钥文件、拒收原因和问题提醒的判据沿用，只是挂在来源上，实际实现在文末“第 4 步的实现记录”。

- **账本（版本 22）。** 新表 `trigger_key`（密钥编号、所属触发器、谁领的、什么时候领的、退役时刻；在用的退役时刻为空）；`trigger_rule` 多四列：`streak_reason`、`streak_count`（同一种原因连续几次）、`problem_since`（够数成为问题的时刻，不是问题时为空）、`alerted_at`（签名问题最近一次推给主人的时刻）。
- **协议（v1）。** 入口 `POST /webhooks/<触发器编号>`；三个头 `X-Tycho-Event-Id`（1–200 个可打印 ASCII 字符）、`X-Tycho-Timestamp`（UTC 整秒）、`X-Tycho-Signature`（64 位小写十六进制）；签名 = HMAC-SHA256(密钥文本的 UTF-8 字节, `v1\n<签名时间>\n<事件编号>\n` + 原始正文字节)。密钥是 32 个随机字节的十六进制文本。签名在 `service/webhook.ts` 拿账本说此刻还有效的每把密钥去比（定长比较），比中的密钥编号交给账本；账本的 `receiveWebhook` 在一个事务里再看一遍那把密钥此刻是否有效，按这个顺序判：签名缺失，或事件编号、签名时间缺失或格式不对（`unsigned`，400）→ 签名存在但格式不对（不是 64 位小写十六进制）或验证失败（`signature`，401）→ 签名时间超出 `triggers.webhookSkewMs`（`stale`，401，正好等于偏差算在内）→ 第 1 步的 `accept`（停用 403、冲突 409、过大 413、限速和队满 429）。先验签名再看时间，所以没验过的请求只知道“签名不对”。拒收都只计数、不占身份。受理了回 200 和凭证（`fire_id`、`duplicate`），重签重试回原凭证；内容按原始正文字节的摘要比，签名和签名时间不算。事件数据是 `{ event_id, body }`：正文是 JSON 就按 JSON 放，其余 UTF-8 文本按文本放，不是文本的按 base64 放在 `body_base64`；`{{event_id}}` 可以进固定指令。消息第一行是“触发器“名字”：收到 Webhook 事件 <编号>”。
- **没领密钥、删了的触发器、不认识的编号**，回答和没有这个接口一样（404“没有这个接口”），不计数。停用的照样先验签名，验过了才拒为“已停用”。
- **密钥。** 只在控制台领取和更换（`POST /api/triggers/:id/key`，主人登录，经门牌可达）：先写 `secrets/triggers/<密钥编号>`，再提交账本；提交失败删掉文件；服务启动时和每次领取后清掉账本里已经不再有效、或者没有记录的密钥文件。秘密只在这次的回答里，页面只列密钥编号、领取时间和旧密钥的退役时刻。更换时在用的那把的退役时刻 = 现在 + `triggers.webhookRotateMs`（可以是 0，换了立即作废），已经在过渡的保持自己的时刻；删触发器时把它的密钥都退役在删除时刻。总控能用 `create_trigger` 建 Webhook 触发器（只有名字、指令、截止、推送终稿），`list_triggers` 只给 `webhook_ready`（领没领），不给密钥编号。
- **路由。** 路由表多一种 `webhook: true` 的行，类型上必须 `outside: true`，处理时不看 Cookie、本机令牌、总控工具令牌，只交给签名。经门牌对外不需要登录的路由只多了这一条；接口清单（`http.routes`）带上每条路由的认证方式，测试按它核对。没有门牌就没有对外监听，Webhook 只能从对内监听投。控制台的触发器页按门牌状态写三种：没配置门牌（`off`）、门牌连接故障（`connecting`、`down`）、可以接收（`connected`），地址按“对外地址”拼，没填就只给路径。
- **触发器自己出的问题（§8）。** 拒收原因按问题归类：缺头、签名不对、签名时间不对算“签名一直验不过”，队满算“待处理一直满”；定时规则在扫描里算不出来（比如升级后不认识的时区）算“规则失效”，记录在单独的事务里（扫描那个事务已经回滚），账本写不进去的降级不算。同一类连续 `triggers.problemAfter` 次（默认 5）成为问题：记下 `problem_since`，按推送表的“等你”推一次（去重键 `trigger-problem:<触发器>:<problem_since>`；签名问题另受下面的时间窗约束），之后按 `push.remindMs`、`push.remindMax` 提醒。中间收下一次、换成别的原因、停用或重新启用、改了规则（规则失效那一类）、规则又算得出来，连续次数就清零，问题就没了；之后再出的是新的一个问题。“还在不在”只由 `problemHolds` 判：触发器启用、没删，`problem_since` 和推送时一样，队满那一类还要项目里待处理的触发消息此刻仍然满；页面、提醒入队、提醒和首次推送发出前都问它。扫描里一条规则算不出来不再拦住别的规则（以前在事务外算下一时刻，抛错会中断整轮）。
- **审阅后的修正。** 规则算不出下一时刻时，查看、列表、修改、停用照常：页面和 `list_triggers` 给出定义、`next_error`（为什么算不出）和“下一时刻未知”，只改名字、指令这些时原样留着存下的时间规则不再重新解析，停用照常提交。队满的问题在总控取走这个项目的一条触发消息、队列不再满时，在同一个事务里结束（`queueTaken` 清掉连续次数和 `problem_since`），之后再满是新一轮，重新数、拿新的 `problem_since`、再推一次；`problemHolds` 仍是唯一判定，队列此刻不满也不算问题。签名问题（没有密钥的人也能制造）推给主人按触发器和设置项 `triggers.problemAlertWindowMs`（默认 1 天）合并：推过一次（记 `alerted_at`），窗口内再成为问题只在页面上显示、不再推，中间正常收下的请求让连续次数清零但不归还这份额度；已推的那条在还有签名问题、且没有更新的一条推过的时候照常提醒（判定看 `alerted_at`），窗口外再成为问题就推新的一条。拒收计数照常。
- **设置项**（“触发器”一组）多四项：`triggers.webhookSkewMs`（默认 5 分钟）、`triggers.webhookRotateMs`（默认 1 天）、`triggers.problemAfter`（默认 5 次）、`triggers.problemAlertWindowMs`（默认 1 天）。
- **这一步没做：** 产品原生签名（GitHub 等）；按来源地址限流（没验过签名的请求也会在规则上计一次拒收，对一个已知编号的风暴只是一条 UPDATE，不写触发记录）。

## 第 4 步的实现记录

- **对象和账本（版本 40）。** `inbound_source`：不变的编号、名字、`kind`（`tycho-v1` 或 `github`）、放行的项目（`projects_json`，建和改时至少一个；删掉一个项目可能把它变成空清单）、说明、`push_final`、启用、谁建的、删除时刻，以及拒收计数、连续问题、签名问题的最近推送时刻。`inbound_key`：密钥编号、所属来源、谁领的、什么时候领的、退役时刻（在用的为空）。`trigger_fire` 重建：`trigger_id` 和 `source_id` 恰好一个，来源的受理身份是 `(source_id, project_id, event_id)`，规则的仍是 `(trigger_id, event_id)`；来源的记录不冻结修订（`revision` 为空），正文按受理时的来源渲染后冻结。旧的 `trigger_key` 删除，密钥行搬进 `inbound_key`。
- **翻译器是一张表加两个纯函数。** `service/inbound.ts` 里的 `TRANSLATORS` 一行一个种类；`service/inbound/tycho-v1.ts` 和 `github.ts` 只接收请求头、原始正文、此刻有效的密钥和放行项目（带 `repo`），返回验签结果和 0..n 个事件；不发请求、不碰账本。新种类加一个文件、一行登记。
- **`tycho-v1`。** 头 `X-Tycho-Event-Id`（1–200 个可打印 ASCII）、`X-Tycho-Timestamp`（UTC 整秒）、`X-Tycho-Signature`（64 位小写十六进制），可选 `X-Tycho-Project`。签名 = HMAC-SHA256(密钥文本的 UTF-8 字节, `v1\n<签名时间>\n<事件编号>\n<项目编号>\n` + 原始正文字节)；不写项目头时项目编号一段是空串，写了就被签进签名，改头一定验签失败。签名时间超出 `triggers.inboundSkewMs` 拒为 `stale`，正好等于偏差算在内。项目头指的项目不在放行清单里、或不写项目头而放行了不止一个项目，拒为 `no_project`；放行只有一个项目时不写头就投它。
- **`github`。** `X-Hub-Signature-256` = `sha256=` + HMAC-SHA256(密钥, 原始正文)，不签时间；`X-GitHub-Delivery` 是事件编号，`X-GitHub-Event` 加正文的 `action` 是事件种类。正文的 `repository.full_name` 与放行项目的 `repo` 比（都归成小写 `owner/name`：认 `https://github.com/`、`git@github.com:`、`ssh://git@github.com/`、`git://github.com/`、`github.com/` 几种前缀和结尾的 `.git`），对上几个项目就各是一次独立受理；对不上拒为 `no_project`。`ping` 验过签名后回 200、不受理不计数。附带资料只放事件种类、仓库、编号、标题、链接、发起人、正文摘要（2000 字，截断写明是 tycho 截的），不放整份载荷。
- **入口。** `POST /inbound/<来源编号>`，路由表里 `inbound: true`（类型上必须 `outside: true`），签名是唯一认证；没有门牌时只能从内网投。没领密钥、删了的来源、不认识的编号回答 404“没有这个接口”，不计数。拒收的状态：缺头 `unsigned` 400、签名不对 `signature` 401、时间不对 `stale` 401、没有对应项目 `no_project` 422、停用 `disabled` 403、冲突 `conflict` 409、数据过大 `too_large` 413、限速和队满 429、项目暂停 503。受理了回 200 和每个事件的凭证（`receipts`，各有 `fire_id`、`outcome`、`duplicate`）；重签重试回原凭证，内容按原始正文字节的摘要比，签名和签名时间不算。一个 GitHub 事件对上几个项目而只被部分拒收时，回答 200 并逐个给出结果。
- **同一个受理入口。** `receiveInbound` 在一个事务里重新读来源和此刻有效的密钥，再让每个事件走第 1 步的 `admit`：去重、限流、队满、项目暂停、循环截断、渲染、推送终稿、问题计数都没有第二套。来源级的拒收（签名、时间、没有对应项目）也记在这张来源的拒收计数和连续问题上；队满的问题记着是哪个项目（`streak_project_id`），`queueTaken` 只结束那个项目的队满问题。消息第一行是“入站来源“名字”：收到 <种类> 事件 <编号>”，接着说明这是主人放行的外部来源投来的请求、不是主人说的话、附带资料不带授权，再是来源说明和附带资料。
- **管理只在控制台。** `GET/POST /api/inbound`、`PUT /api/inbound/:id`、`POST /api/inbound/:id/enabled`、`DELETE /api/inbound/:id`、`POST /api/inbound/:id/key`，都经门牌可达。页面在侧栏“配置”里是独立一页：列表（种类、放行的项目、说明、地址、密钥编号和退役时刻、拒收和问题）、新建和修改的抽屉（选种类、勾放行的项目、写说明和是否推终稿）、停用、删除、领取和更换密钥、最近的受理记录、门牌三种状态。密钥的秘密只在那次回答里出现一次。总控的工具里没有入站来源：`list_triggers` 只有本项目的规则，`create_trigger` 的 `source` 只有 `schedule` 和 `event`。
- **密钥文件沿用同一处。** `secrets/triggers/<密钥编号>` 不改名，第 3 步领过的密钥在升级后照常验证；服务启动和每次领取后清掉账本里已经不再有效、或者没有记录的文件。更换时在用的那把的退役时刻 = 现在 + `triggers.inboundRotateMs`（可以是 0，换了立即作废），已经在过渡的保持自己的时刻；删来源时把它所有的密钥退役在删除时刻。
- **删项目时来源留下。** 入站来源是整个 tycho 的对象，属于调用方，不属于任何项目：删一个有历史的项目不删来源、不停用它、不动它的密钥，只把被删项目从 `projects_json` 里去掉（清单可能因此为空，来源还在、放行不了任何项目，页面照实显示），和保留的知识条目去掉本项目是同一件事，算进那次删除的 `scope_removed` 的“入站来源”。`updated_at` 不动：来源本身没有被改。
- **迁移（39 → 40）。** 每个旧的 Webhook 触发器（含已删除的）变成一个同编号的 `tycho-v1` 来源，只放行它原来那个项目；固定指令成为来源说明；密钥行和退役时刻原样搬过去；它的受理记录把 `trigger_id` 换成 `source_id`、修订置空；已删除的来源保留删除时刻，不列出；排在他们身上的 `trigger_problem` 通知把 `trigger_id` 改写成 `source_id`；`tunables` 里的 `triggers.webhookSkewMs`、`triggers.webhookRotateMs` 改名为 `triggers.inboundSkewMs`、`triggers.inboundRotateMs`，值不变。没有旧触发器的账本只建两张空表，不写审计。
- **设置项。** 原四项里两个改名：`triggers.inboundSkewMs`（默认 5 分钟）、`triggers.inboundRotateMs`（默认 1 天），并在控制台归到“入站来源”一组；`triggers.problemAfter`、`triggers.problemAlertWindowMs` 不变。其余“触发器”组的设置照旧。
- **安全审阅修正。** 翻译器声明事件编号是否被签名覆盖，账本对未覆盖的编号同时按原始正文摘要查找仍在去重期内的受理记录（同一来源、同一项目）。不依赖 GitHub 的未签名请求头判断是否是新事实，不延长首次受理的保留期，重启和轮换密钥不改变判断。仓库路由只接受完整匹配的 GitHub 地址，载荷的 `repository.full_name` 单独按 `owner/name` 解析，构造的嵌套前缀、其他主机、查询串和多余路径不参与匹配。
- **这一步没做：** GitHub 不签时间，去重保留期结束后仍可重放；没有按来源地址限流（没验过签名的请求也会在来源上计一次拒收，只是一条 UPDATE）；没有 GitLab、飞书等原生翻译器，也没有入站来源上的事件过滤或固定指令。
