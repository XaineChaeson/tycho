# 按职能派发，档位由职能推出

读者：主人和实现者。状态：**已确认，分步实现中（1–4 已落地，§10 的第三档已落地）**；第三档“操作档”见 §10（2026-11-08 主人确认；协调者、Codex、dsh 三份独立稿互审后的定稿；三份原稿和裁决理由见文末）。

## 结论

**派任务时先选职能，档位由职能推出，不再每次判断"这活难不难"。**

1. **档位固定为三个，名字说用途：操作档、执行档、决策档，从下到上排序。** 不再叫 `cheap` / `strong`，也不让每个账号自己起档位名：档位名是任务和账号之间的接口，必须全局固定。模型和推理强度只写在各账号的档位内容里，决策档不等于"强度拉满"。
2. **职能是控制台里可增删改的对象。** 预置四个（实现、审阅、分析、验证），每个带默认档位、权限、交付物和"要不要独立审阅"。任务必须选职能。
3. **写死的只有四条不变量，由服务强制，不靠 brief 措辞：**
   - 审阅绑定到具体产物（提交、包摘要），产物一变旧审阅作废；审阅者看不到作者的结论，用新会话。
   - 有别的执行器能审时，审阅者不能是写过这份产物的执行器；别的执行器都审不了时，由写过的执行器开新会话来审，这一轮和它的结论都标"未换执行器"；连它也审不了才停下。总控不能放宽（钉不了写过的执行器）；只有主人能在控制台"不经审阅验收"，并留记录。
   - 只读职能只派给执行器声明了、并且机器实测过原生只读手段的那一对；这一轮结束后核对代码没被改，改了就不采用结果（§5）。
   - 被有效审阅打回的产出，服务把重做升到上一档：操作档 → 执行档，执行档 → 决策档；已是决策档再被打回就停下找主人。三个档位本身就是终止条件，不需要计数器。
4. **其余都是数据**：职能有哪些、各自的默认档位和权限、每个账号每档的内容。单个任务可以覆盖档位，必须写理由，记进时间线。职能页显示每个职能被覆盖的次数和首轮审阅打回率，让主人看着改默认值；不自动改、不发提醒。

## 1. 为什么

"强 / 弱"一个词同时回答了三件事：这活要不要重新判断问题、用哪份推理配置、现在哪个账号有空。结果是名额反过来改写了活的性质，想得久被当成聪明，贵被当成好。今天的三个反例各对应一件：

| 反例 | 被混进来的那件事 |
|---|---|
| 一个"根因已明"的修复因为强档名额被占给了便宜档，实际是一次推翻根因的诊断 | 名额决定了活的性质 |
| dsh 强档推理强度拉满，一个实现切片 56 分钟没写出一行 | 想得久被当成能力 |
| Claude 强档配了额度很贵的模型，烧得太快 | 贵被当成好 |

改成按职能：职能回答第一件事，档位内容回答第二件，现有的账号挑选（额度、负载、机器）回答第三件，三件各归各处。

职能也会判错（诊断还是可能被派成实现），但判错会变成一个看得见的标签，并且有三道兜底：审阅打回、系统升档、职能页的打回率。按难度派发时这三样都没有。对第一个反例还有一条直接的规矩：根因没有人验证过，就先派"分析"，不派"实现"。

## 2. 档位

| 标识 | 页面上叫 | 用途 |
|---|---|---|
| `operate` | 操作档 | 照着做、跑出结果：跑测试、复现、按规则批量改、跑数据，交报告 |
| `execute` | 执行档 | 靠做完拿结果：范围明确、结果可核对 |
| `decide` | 决策档 | 靠想清楚拿结果：分析、设计、审阅 |

- **只有这三个，名字和它们的先后只在 `shared/` 声明一处**，服务和控制台都从那里读。账号的档位字典只能用这三个键；只填一个也行，那个账号就只接那一档的活。没填的档不回落到机器上的默认配置。
- **顶替只有一条：操作档没填，就用同一个登录的执行档内容**（§10.3）。只往上顶一级，不往下：执行档没填不会拿操作档的便宜内容，决策档不顶替。只填了决策档的登录仍然只接决策档的活。刚填了执行档、还没填操作档的账号，验证任务照旧跑得起来。
- **不加第四档。** dsh 原来的 `escalation` 档去掉：决策档反复不过，该换执行器，不是同一个执行器再加强度（同源盲点）。2026-11-11 出现的第三种用途在执行档**下面**加了一档操作档（§10，已落地）；在决策档上面加强度的理由仍然成立，不加。
- **服务不保证不同账号的同一档水平相当**，只保证派的是这一档、这份内容执行器能用、快照里记了实际内容。
- **推理强度属于档位内容**，任务和职能都不带强度。控制台档位那一行给一句推荐：决策档用更强的模型、中到高强度；执行档用便宜好用的模型、低到中强度；操作档用最便宜够用的模型、低强度。"想得久"由时限管（`run.timeoutMs`、账号的 `timeout_ms`），不由升档管。
- **没有空闲的决策档时任务等着**，不因为执行档有空就降档。

## 3. 职能

**职能是账本里的对象**（照 `service/machines.ts` 的形状：一张表、取对象的接口、控制台增删改）。任务有一个必填字段 `role_id`。职能挂在任务上，不挂在账号、机器或项目上：同一个账号今天做实现、明天做审阅。

### 3.1 预置四个

只预置在权限、交付物、要不要被审这三条上真有区别的：

| 职能 | 默认档位 | 权限 | 交付物 | 要独立审阅 |
|---|---|---|---|---|
| 实现 | 执行 | 可写 | 提交 | 是 |
| 审阅 | 决策 | 只读 | 结论 | 否（它就是独立的那一方） |
| 分析 | 决策 | 只读 | 报告 | 否 |
| 验证 | 操作 | 可写 | 报告 | 否 |

"设计""诊断""调研"和"分析"结构相同，主人需要时在控制台加，加出来的是数据。"验证"是跑测试、复现、做操作：要写和跑进程，但不交提交。只读的审阅要用到测试结果时，另派一个验证任务去跑，审阅者判断结果够不够。

### 3.2 职能的属性

| 属性 | 谁用 |
|---|---|
| 名字、说明（含"什么时候别用它"） | 总控选职能、控制台 |
| 默认档位 | 派发时推出档位 |
| 权限：只读 / 可写 | 派发时筛账号、改写启动参数 |
| 交付物：提交 / 报告 / 结论，从固定词表里选 | 结算时校验回执，缺了就记"交付不齐"，不进待验收 |
| 要不要独立审阅 | 验收关 |

不放在职能上的：模型、强度（档位内容）、时限、并发（账号和设置）、技能（项目）、重做次数（不需要）。审阅这一职能的权限必须是只读、交付物必须是结论，这是任务类型的不变量，控制台不让改。

### 3.3 任务上记什么

- `role_id`，加上可选的档位覆盖 `{ tier, reason }`。**不再单独存一个和默认值重复的 `tier` 字段**：实际档位 = 覆盖 ?? 职能的默认档位；审阅任务在两者之间多一层，跟着绑定的被审那一轮的档位（§11.5）。
- 覆盖要理由：总控不写理由，工具直接拒绝；主人在控制台改，理由可以不写。系统升档也是一条覆盖，理由由系统写。**升档之后总控不能再改这个任务的档位覆盖。**
- Run 的快照记下这一轮的职能（当时的内容）、实际档位和它的来源（默认 / 覆盖 / 升档）、实际用的权限方式。改职能只影响以后的 Run。

## 4. 审阅

**审阅照旧是普通任务**（[self-iteration.md](self-iteration.md) §3.2），只多三样东西。

**① 绑定产物。** 审阅任务带 `review_of`：被审的任务、那一轮 Run、产物身份（提交号、包摘要、文件名和大小，复用现有产物身份）、验收标准的修订号。这份绑定由服务从已登记的产物生成，总控只指名被审的任务。产物或验收标准变了，旧结论就不再满足验收，不需要谁去"作废"它。

**② 独立。** 依据是"它能挡住哪种影响"：

| 要求 | 强制 | 挡住什么 |
|---|---|---|
| 不给作者的结论 | 是 | 先入为主。审阅的 brief 由服务另走一条生成路径：被审目标、验收标准、来源与产物按绑定冻结；审阅任务的额外核验要求与指定证据单列，不自动附作者的总结、报告和会话（正式报告作为被审产物时按 §5 交付） |
| 新会话 | 是 | 作者的上下文。审阅不能续接被审任务的会话 |
| 换执行器 | 有别的执行器能审时是 | 同源盲点。排除被审产物从基准到现在之间，所有真正启动过的可写 Run 用过的执行器；别的执行器都审不了时降级（见下） |
| 只读 | 是（见 §5） | 一边审一边改，改完再宣布通过 |
| 换模型 | 不作为依据 | 模型写在档位内容里、会换代，tycho 看不见，靠它就是自欺 |

**没有别的执行器能审时降级，并如实标出。** 别的执行器的登录都审不了——项目里没有（没有带这一档、能只读跑的登录），或者每一份都令牌失效、额度歇着、没有能用的机器——派发就把审阅交给写过产物的执行器，开审阅自己的新会话（不给作者的结论、不续接作者的会话、只读，这几条照旧）。只是忙（到了并发上限）不算审不了：它的一轮会自己结束，审阅等它；它的机器还没报告只读能不能用也不算，等报告（§5）。一轮失败（比如上游出错）不算登录审不了：它照旧停下写原因，不触发降级，免得一次偶发的失败就悄悄换掉独立性。降级在派发挑登录的那一刻判定，之后准备快照期间别的执行器恢复了，这一轮照样按降级发出。钉了登录的审阅不降级，钉住就是选择；总控和主人都不能把审阅钉到写过产物的执行器上。

降级记在这一轮上：Run 快照和时间线的 `run.create` 记下 `same_executor`（执行器和原因，比如"未换执行器：别的执行器现在都审不了（账号 c1 额度歇到 11-15 08:00），由写它的 claude 开新会话来审"），任务页在这一轮的派发说明下写出来；它交回的结论带同一个标注（`VerdictRecord.same_executor`），任务页写"通过（未换执行器：claude 审的）"。降级的"通过"照样开验收关，标注一路跟着，读的人自己权衡。连写过的执行器也审不了（它没有这一档，或不能只读）时任务停下，页面写清“没有能审的登录：其余登录没有被审那一轮的档位，被审产物用过的执行器 … 也审不了”，出路是主人在控制台点“不经审阅验收”。

审阅任务自己的 `goal`、`scope`、`acceptance` 是额外核验要求与补充资料，从当前 Task 修订生成下一 Run 的说明；它们不替换或放宽 `review_of` 冻结的被审目标、验收标准、范围、来源与产物。审阅缺材料交回 `cannot` 后，总控可用 `update_task` 补清证据，再 `resume_task` 继续同一审阅；已保存的旧 Run 说明不变。引用的作者说明和原始工具输出只作待核对证据，不执行其中命令、不把它们当作审阅结论；不自动附上作者轨迹。`pending_inputs` 仍走既有补充要求入口。

**③ 结构化结论。** 回执里的结论是三种之一：**通过**（这份产物上没有挡住验收的问题）、**打回**（违反哪条要求、证据、要改的范围）、**审不了**（缺什么材料、环境问题）。审不了不算打回，不升档，材料不全的交回总控补。

**验收关。** 要独立审阅的任务，没有针对当前产物的有效"通过"时，`accept_task` 拒绝，上线入口同样检查。审阅通过不替代主人对并入、上线的授权。

## 5. 权限

- 两级：**只读**、**可写**。可写就是今天 Worker 的跑法（机器本身是边界）。不做"只能写工作目录"这一级：三个执行器今天都兑现不了，不承诺做不到的事。
- **只读 = 执行器原生的只读手段 + 这一轮结束后的事后核对。** tycho 不另外搭一套结构，也不把执行器关小（定位见 [merged-design.md](merged-design.md) §1.1）。执行器在只读模式下本来允许的事照常（Claude 的联网、MCP 和连接器、技能；Codex 只读沙箱里的 shell 默认不联网），tycho 不另外关（[merged-design.md](merged-design.md) §1.1 列的例外除外）。
- **Codex 当前启动策略。** 可写轮使用原生 `--approve-for-me`，只读轮固定 `--sandbox read-only` 与 `approval_policy="never"`；具体边界、旧版本处理和发布门见 [codex-native-policy.md](codex-native-policy.md)。下面实施记录中的旧 workspace-write 参数保留为当时事实，由本条取代。
- **原生手段由适配器声明，由机器实测确认。** 目前是 Codex 的只读沙箱（文件系统层：编辑工具、shell 和 shell 起的程序都写不了）和 Claude 的拒写权限（工具层：写文件的工具不可用，shell 还在）。**dsh 不提供只读**：它的档位是一串补丁，能重新定义只读模式、换掉沙箱和文件后端（实测见 [../spike/readonly.md](../spike/readonly.md)“dsh 不声明只读”），原生手段靠不住。同一个执行器在不同机器上结果不同（Codex 在本机 Windows 上文件系统只读有效，在没有可用 bwrap 的集群容器里连只读命令都起不来），所以"能不能只读"是**机器上的事实**：机器的客户端在上报执行器时，按适配器声明的只读方式跑一次不写东西、不耗额度的小探针，起得来就报"只读可用"和层，起不来或说不清就报不可用并带上原话。派发只把只读职能交给"只读可用"的那一对机器和执行器；没报、报不可用、执行器不提供只读的都不接，不降级成可写。派发、控制台都不认执行器的名字，只认声明和机器的报告。
- **事后核对：结束时的代码目录还是快照绑定的那个提交。** 只读那一轮在一个只属于这一轮的目录里解出干净的代码，不碰任务保留的代码目录（上一轮的改动混不进基线，这一轮的改动也留不给后面的轮次），核对完就删掉；仓库来源的只读轮一律如此，不论它有没有指名要检出的提交。工作目录来源没有 tycho 的副本可核对，只有一条信息：开始和结束时各读一次它的 HEAD 和 `git status --porcelain`（只读，不留可选锁，不改忽略规则），有差别就记“这一轮期间目录有变化”随结束报告上报，**不据此拒收回执**——那个文件夹不归 tycho，别的活和主人也在动它（[code-sources.md](code-sources.md) §8 第 1、2 条）。起 Worker 之前，机器上的看管进程记下基线：当前提交、分支和其余引用、纳入版本管理和没被忽略的文件；这一轮结束后再看一次，把两次的差别作为证据报回主机。有任何一项变了，这一轮的结果不采用：回执里的结论、报告、知识提议都不记，这一轮以失败结束、原因写明改了什么；开始时有代码、结束时核对不了（目录没了、git 出错，或有退出码却没有核对证据）同样不采用，原因写“核对不了”和原话。被仓库里的规则忽略的文件不算（跑测试留下的输出）。这一轮本来就没有代码（例如知识的把关和整理）就记“这一轮没有代码，无可核对”，照常结算。
- **被改是预期内的事，先自己处理。** 跑测试可能留下没被忽略的输出，所以不采用之后自动重派一次：开新会话，brief 写明临时输出放到代码目录以外。同一个任务紧接着的上一轮也是因为核对不采用的，才停住找主人；计数由账本在结算的事务里判，和“连续丢失”同一种做法。这一轮结束只记一条记录、不投给总控，下一轮自动重派（[project-sessions.md](project-sessions.md) §3）。
- **只读那一轮不交文件。** 它要交的只在最后一条消息里；主机取回产物时不收只读快照的 Run，所以它放进 `artifacts/` 的东西不会被登记成产物。回执以「最后一条消息」声明报告时，Runner 把适配器认可的最终回复交给账本，随首次被采用的结算在同一事务内保存一份 `run.report`。正文先脱敏，最多保存 128 KiB UTF-8，记录摘要、大小、完整性与来源；不完整不能称作完整报告。普通任务、轨迹和历史列表只返回元数据，正文沿现有报告读取入口按权限展开。它不依赖有保留期限的诊断事件。
- **历史报告只从原始输出恢复。** 尚未保存正文的旧轮次必须原来已被采用；读取时核对原节点登记，完整读取不超过 8 MiB 的 stdout 与 stderr，再用原适配器解析并核对已存回执，才可补记恢复时观察到的报告。已经保存的正文不被后来输出替换。不重结算、不改变任务和通知，也不绕过项目移交后的写权冻结。原始输出缺失、过大或无法核实就说明无法恢复，不拿诊断尾巴拼完整报告。
- **审阅报告绑定报告本身。** 职能交付物为报告且使用上述最终回复时，独立审阅绑定同一正式报告的身份与摘要；报告本身不可得或只保留前段时不能绑定完整交付物审阅。代码交付仍使用原有的提交和产物身份，不把作者的最终叙述自动混入代码审阅。知识引用与历史展开读取同一份正式报告，不再保存第二份正文。知识提案受理时先按调用者的实际读范围核对任务、轮次与消息证据，才验证摘录；未获准的引用不能返回正文是否匹配。总控工具 `get_run_report` 按项目读取同一报告，`get_run_log` 仍只返回有保留期限的过程事件。
- 这些对所有只读职能一样，不看执行器、不看兜到哪一层。
- **保证到哪为止，照实说。** 核对只比开始和结束两个时刻：改了又改回去的看不出来。它和机器上别的证据一样防误判、不防存心作恶的 Worker（证据和 Worker 是同一个系统用户，机器本身是边界）。核对只覆盖这一轮的代码目录。联网和 MCP 能在外面产生副作用（推送、改在线文档），代码目录以外的写也看不见；这些由执行器自己的权限和机器上的配置管，tycho 不承诺。机器自己的基础配置（`~/.claude/settings.json`、`$CODEX_HOME/config.toml`）照常生效，那里写的钩子和服务只读那一轮也会带上，由配机器的主人负责。
- **启动参数由服务按职能改写**，不看账号自己设的权限模式（它只能更紧，不能更松）。
- **档位内容里不能夹带权限、沙箱、审批这类设置**：适配器声明哪些键是管权限的，`checkTier` 在保存时就拒掉。这是给主人的提示，不是保证：按行认不全所有写法，机器上的档位文件也不读；代码变没变看事后核对。"高级"里别的原文照旧保留。
- 真正兜得住的一层在服务端：并入主线要求任务已验收，主人和总控一样；总控还要项目授权（project-sessions.md 文末“总控可以自己做的事”）。上线默认只有主人能点，项目授权总控之后总控也只能对已验收的任务做，审阅关和上线关照旧。Worker 的工具里没有这几条。只读职能只是让"审阅者顺手改代码"不被采用，不是安全边界。

报告引用由服务的报告边界统一识别：最后回复只认回执 `ref` 逐字等于「最后一条消息」，文件报告用本轮 `artifacts/` 根目录下报告文件的实际路径。无法识别的声明保留原引用并显示问题，不从普通叙述猜报告，也不尝试文件读取。主人可以退回返工，让执行器重新交付报告和回执。

报告职能派审阅时，服务先核对报告声明，再核对声明的实际文件是否取回；没有声明、引用无法识别、只读轮次声明文件或声明的文件没有取回，都拒绝绑定并记录产物问题。最后回复仍要求已保存完整正文。文件报告沿用产物登记的文件大小限制；Console 文本预览和自动随轮交付正文各有预算，不会因此阻止登记。登记成功不等于正文已随轮送达：过大、非 UTF-8 或未能核对的文件只在审阅清单写明未携带原因，审阅者没有取得必要正文时应报告“审不了”，不能只凭清单判通过。这个检查只约束审阅登记，主人直接验收沿用现有语义。

## 6. 升档

**由服务在结算审阅的同一个事务里触发**，总控不用再调一次：

1. 结论是"通过"：什么都不做，被审任务留在待验收。
2. 结论是"打回"，被审的那一轮不是最高的决策档：被审任务按现有"送回去改"退回队列，打回意见进下一轮输入，档位覆盖写成**上一档**（操作档 → 执行档，执行档 → 决策档），理由"审阅打回，升到 X 档"，新的一轮开新会话。
3. 结论是"打回"，被审的那一轮已经是决策档：任务停下找主人，附上审阅意见。

重复结算同一个审阅只退回一次；过期的审阅（产物已经变了）只留历史。额度用完、登录失效、机器失联、"审不了"都按原规则处理，不算质量打回。

"重做那一片"以任务为单位：服务不从审阅文字里自动切代码片，总控在派发前就把独立的交付切成任务。

## 7. 什么写死、什么是数据

| 写死（改了要动代码和测试） | 数据（控制台） |
|---|---|
| 先选职能，档位从职能推出 | 有哪些职能，名字、说明、默认档位、权限、交付物、要不要审 |
| 档位只有操作、执行、决策三个，名字和先后只在 `shared/tiers.ts`；操作档没填时用同一登录的执行档内容 | 每个账号每档的内容（模型、强度、高级原文） |
| 审阅绑定产物、看不到作者结论、新会话、换执行器（别的执行器都审不了时降级并标出） | 单个任务的档位覆盖（带理由） |
| 只读职能只派给声明并实测过原生只读的执行器；结束后核对代码没被改 | `roles.signalWindow`（统计窗口，默认最近 20 个任务） |
| 审阅打回就往上一档升，最高档（决策档）被打回找人 | |
| 审阅职能只读、交结论；交付物词表 | |

**统计**：职能页每行两个数，都从 Run 快照算，不建新表：

- 最近 N 个任务里有几个覆盖了默认档位，附上理由；
- 首轮有效审阅里被打回的比例，按被审那一轮的档位分开算（§10.4：统计这一步做的时候）。

覆盖多可能是默认档位不对，也可能是一个职能里混了两种活；打回多可能是档位低了，也可能是需求没写清。数字只是检查的入口，主人看着改。

## 9. 分步实现

每一步做完都能单独用。

1. **档位改名并固定成两档。已落地**（账本版本 15，分支 `tiers-step1`）。形状：`decide`（决策档）和 `execute`（执行档）两个标识、页面名称、一句用途和一句推荐内容，只在 `shared/tiers.ts` 声明一处；账号的档位字典只接这两个键、至少填一个，没填的不回落到机器上的默认配置；`create_task`/`update_task` 的 `tier` 和 `router.tier` 也只接这两个（工具 schema 里的 `enum` 就是校验，参数说明写清哪一档给哪种活）。控制台账号页是固定两行、可以留空（留空表示这个账号不接这一档），没有"加一行""起名字"这类入口；总控设置里选档位的地方按页面名显示。迁移 14→15 只做改名，不改任何档位内容：账号里的 `cheap`/`strong` 改成 `execute`/`decide`；别的名字（`escalation`、自起的名字、旧布局留下的 `default`）不猜、原样留着；某个账号同时有旧名和它要改成的新名（比如 `cheap` 和 `execute`）时，这个旧名**哪里都不改**——账号里两个键都保留，别的账号、任务和总控也跟着不改——由主人决定两个名字各留哪一份值。控制台把留下的旧名字标"系统不再用这个名字"并给一个"改成决策档 / 执行档"的动作（目标档已有内容时先说清会覆盖）。没结束的任务里映射不到的档位名（撞名的也在内）让任务进"等你决定"并写明理由，撞名的那条写明是哪个账号同时有哪两个名字；**还有一轮在外面跑的任务不改状态**，那一轮照它自己的快照核实和结算，旧名字只在这个任务下次进队列时由 `moveTask` 拦住。映射不到的 `router.tier`（撞名的也在内）让总控停摆，理由说清去哪改。旧名字的改名表和撞名规则只属于这一步迁移（`service/db.ts`），运行中的程序只认 `shared/tiers.ts` 里的名字（当时是两个，§10 之后是三个）：留下的旧名字一律说成“档位只有<全部档位>几个”（2026-11-10 收拢）。Run 的快照自始至终不动，恢复照旧核实旧执行：升级时已经起来的那一轮不会被当成没开始，也不因为改名丢掉回执。账号的档位内容一个字没变，各档内容要不要按 §2 的推荐调一遍是主人的事。
2. **职能对象和按职能建任务。已落地**（账本版本 16，分支 `roles-step2`）。形状：职能是账本里的 `role` 表，词表（权限只读 / 可写，交付物提交 / 报告 / 结论）、预置四个和审阅的不变量只在 `shared/roles.ts` 声明一处；`service/roles.ts` 判定一个职能合不合格，控制台“职能”页经 `/api/roles` 增删改。职能的标识（`implement`、`review`、`analyse`、`verify`，主人加的由主人起）定了不改，名字、说明、默认档位、要不要独立审阅都能改，名字不能重名。审阅（`review`）的权限只能只读、交付物只能结论，而且不能删；还有没结束的任务用着的职能也不能删。权限、交付物、要不要独立审阅这一步只记录。任务存 `role_id` 和可选的覆盖（`tier_override`、`tier_reason`），不存档位：实际档位在每次读任务时由账本推出（覆盖 ?? 职能的默认档位），连同来源（职能默认 / 单独指定），挑账号用的就是它。账本要求建任务必须给一个存在的职能；总控的覆盖必须写理由（工具拒绝空理由），主人在控制台任务页改职能和档位时理由可以不写；职能和覆盖的变化连同原值记进 `task.update` 的时间线。Run 的快照由 `createRun` 在同一个事务里记下当时的职能内容、实际档位、来源和覆盖理由；快照准备好之后任务的档位变了，这一轮不发。总控多了只读的 `list_roles`，`create_task`/`update_task` 的 `tier` 换成必填的 `role_id` 和带理由的 `tier_override`（`update_task` 填 null 去掉覆盖），`list_tasks`、`get_task` 显示职能、实际档位和来源；没有改职能的工具。迁移 15→16 不猜职能：去掉任务的 `tier` 列；下一步就是进队列的任务（排队、停住、等定时、没有待答问题的“等你决定”）进“等你决定”，理由“这个任务还没有职能，选一个职能再继续”；还有一轮在外面跑的、等验收的、有问题待答的、草稿保持原状态，等它们下次要进队列时由 `moveTask` 拦住（答复、退回、入队、自动接续都走它），“继续”在没选职能时直接拒绝；已结束的任务 `role_id` 为空，页面写“（旧）没有职能”；Run 快照不动。没有职能、也没钉账号的任务，它失联的那一轮过了宽限期也找不到接续的去处：旧的一轮原样留着、不判死，页面写“这个任务还没有职能，选一个职能后才能核实和接续失联的那一轮”，总控经内部事件被告知一次；选了职能后照原规则核实和接续。任务页如实写“这一轮没有只读保证”，职能页写明权限和独立审阅目前只记录、尚未强制。控制台没有建任务的表单（任务都由总控建），所以“按职能选”落在任务页的“职能与档位”表单上。做完后不再每次判断难不难。
3. **审阅的绑定、独立和升档。已落地**（账本版本 17，分支 `roles-step3`）。形状：
   - **绑定。** 审阅任务是职能为 `review` 的任务，建的时候必须指名被审的任务（总控 `create_task` 的 `review_of`），别的职能不能指名，审阅任务也不能改成别的职能、别的任务不能改成审阅。被审任务必须在待验收。服务先记下被审任务当时的最近一轮和修订，再经现有的读文件通道把那一轮的产物取回主机。取回并登记是一个动作，提交点是账本里的登记：先取到一个单独的临时目录（`<数据目录>/releases/.incoming-…`），在那里校验产物名，全部成功后用一次改名把它变成这次登记自己的目录（`<数据目录>/releases/<run>/<登记编号>/`，验收时取回的也是这样），再在一个账本事务里把这次登记（编号、时间、文件的名字 / sha256 / 大小）记在那一轮 Run 上（`run.artifacts_json`）；目录由编号推出，不另存。**登记是产物的唯一权威**：目录写好后不再改写，没有“换上正式目录”“删旧目录”这一步；审阅派发、验收、上线（放行和读包的字节）、任务页和合 PR 都从那一轮当前的登记找目录和文件，不扫磁盘、不读磁盘上的清单，磁盘上有而账本没登记的目录谁都看不见。登记提交之前的任何一步失败或崩溃，结果只有一种：上一份登记和它的目录原样，新目录最多留在磁盘上、没被登记就等于不存在；服务启动时和每次取回结束时，只清掉从来没被登记过的目录（崩溃或失败留下的）和没有取回在写的临时目录；被登记过的编号目录即使已被后来的登记替换也保留——审阅绑定、发布记录还指着它，独立的升级命令也可能正读着它，所以读者不用加租约。取回失败的原因记在同一轮的登记旁边（不动登记），任务页同时给出当前在用的登记和最近一次失败：没有登记时说“没取回来”，有旧产物时说最近一次重新取没成功、现在用的还是之前那一份，两种都带“重新取产物”；校验没过的那一轮什么都不登记，它的文件也不留。旧格式（直接放在 `releases/<run>/` 下的文件和 `release.json`）不读、不显示、也不删，要用就重新取一次。同一轮的取回在服务进程里排队，一次一个。“没有登记”和“登记了零个文件”是两回事。**绑定的提交**（`shared/sources.ts` `ReviewedCommit`）不再从交回的代码包里读：由干活的机器在一轮结束时读出来、随这一轮的结束报告报回（`shared/node-protocol.ts` 的 `NodeSourceHead`，机器端在 `node/source-head.ts`，账本存进这一轮 Run 的 `error_json`）。仓库来源取执行器回执报的分支和提交，并要求机器读的正是那条分支、它用 `git ls-remote` 读到的远端头正是那个提交——持有仓库访问身份的是机器，主机自己不问远端（核实不了、机器没报、或对不上，如实说明、不绑定，也不取产物）；工作目录来源取机器读到的那个 HEAD，并把文件夹的路径记进绑定（审阅说明要点名那个文件夹）。一个代码来源都没有的任务没有这个提交，按文件绑定。这个提交由 `service/accept.ts` 的 `register` 在取产物之前算出，随登记编号一起交给账本。账本在建审阅的事务里核对：被审任务的最近一轮和修订还是取回开始时的那一轮、那一修订，登记也还是这次取回做的那一份（没有被后来的取回替换），否则拒绝这次绑定；绑定里的文件从这份登记里读，提交按形状核对（仓库来源必须有分支和地址，工作目录来源必须有路径）。绑定存在审阅任务的 `review_of_json` 里：被审任务、那一轮 Run、修订号、当时的目标 / 验收标准 / 范围、登记的文件、被审提交（`reviewed`）、任务起点（`start`：这一轮机器最先读到的 HEAD，没有就不给）和写过它的执行器；不再有基准提交。验收这一轮时不再重取，用的就是登记的那一份。**当前产物**只有一个定义（`service/review.ts` 的 `productStale`）：被审任务最近一轮 + 当前修订 + 那一轮的来源与提交（`roundCode`，从这一轮自己的回执和机器报告读）+ 那一轮登记的完整文件集合；验收关、上线入口、审阅结算都用它比较，任何一项变了或文件未登记，旧结论就不算，没有“作废”动作。要不要独立审阅，看产出当前产物的那一轮 Run 快照里的职能；改任务的职能只影响以后的 Run。
   - **独立。** 审阅的 brief 由 `runner/snapshot.ts` 另一条路径生成：只给被审任务那个修订的目标、验收标准、范围，被审的那个提交（仓库来源连地址和分支一起说清，并说明干活的机器读那条分支的远端头时它就是那个提交；工作目录来源说它是那一轮结束时机器读到的 HEAD，并点名那个文件夹）、登记的文件和摘要，以及"测试自己跑、跑不了就写审不了"；改动范围是任务起点到被审提交（`git diff 起点..提交`，没有起点就只给被审提交，并说明范围说不出来）；工作目录来源说清 tycho 不替它 checkout、要跑测试自己开 worktree、HEAD 不等于被审提交或有未提交改动时结论写"测试没有在被审的提交上核实"；审阅输入的冻结基准、额外核验要求与补充材料统一按 §4 处理。审阅这一轮拿到的代码来自被审任务的代码来源（仓库：审阅机器 clone 后检出被审提交；工作目录：同一文件夹、执行器原生只读模式对着被审提交看），不再是交回的 git bundle；它的会话只属于审阅任务自己。会话也只在同一档位内续接：档位变了（升档、主人改了）就开新会话。
   - **换执行器。** 写过的执行器按保守口径算：被审任务每一轮发起过启动的 Run，只要没有被判定为“确实没有启动”（失联依据是 `not_started`），快照里职能又不是只读，它的执行器就算写过（第 2 步之前没记职能的旧 Run 算可写）。启动的应答丢了不等于没启动：核实时机器上看得到启动证据，就把启动时刻记进 `started_at`，之后判丢失也不抹掉。挑账号（`candidateAccounts`）、钉账号（建任务、改任务）、建 Run 三处都拦。没有合格账号时任务停住，理由"等合格的审阅者：被审产物用过的执行器是 …，其余账号没有决策档"（后来由 §4 ② 的降级取代：别的执行器都审不了时由写过的执行器开新会话来审，只有连它也审不了才停住）；总控改不了绑定、钉不了被排除的账号、改不了职能。
   - **结论。** 回执词表（`RECEIPT_SPEC`）加了 `verdict`：`result` 是 `pass` / `reject` / `cannot`，加一句 `summary`；打回至少一条 `violations`（`requirement`、`evidence`、`scope`），审不了要写 `missing`。结论存在审阅任务的 `verdict_json` 里，带当时是否还对得上被审产物（`current`）。审不了：审阅任务停住、理由写缺什么，被审任务不动。
   - **交付物。** 结算回执是 `done` 的一轮时，按快照里那一轮的职能核对：提交 = `artifacts` 里有 `kind` 为 `commit` 的具体提交号（只给分支不算），报告 = 有 `report`，结论 = 合格的 `verdict`。缺了任务停住，理由"交付不齐：…"，不进待验收。brief 的回执一节写明这个职能要交什么。
   - **验收关。** 职能要独立审阅的任务，没有一份对得上当前产物的"通过"，`acceptTask` 拒绝（总控的 `accept_task` 和控制台的"验收通过"走同一处）。控制台在这时把"验收通过"换成"不经审阅验收"，时间线上 `task.accept` 带 `without_review: true`；总控调不了（工具里没有，账本对总控也拒）。上线入口（控制台"上线"）同样检查：要独立审阅的任务，只有被一份有效"通过"覆盖的那个包（名字、摘要、大小都对）、或主人不经审阅验收过的，才能上线。并入主线要求任务已验收，主人和总控一样；总控还要项目授权“并入主线”（project-sessions.md 文末“总控可以自己做的事”），验收那一步本来就过审阅关。
   - **升档。** 在结算审阅那一轮的同一个事务里：通过不动；打回且对得上当前产物时，被审那一轮是执行档 → 写覆盖为决策档（来源"审阅打回后升档"，理由"审阅打回，升到决策档"），按 `rework_task` 同一个退回入口回到队列，打回意见作为下一轮的输入，时间线记 `task.escalate`；已是决策档（升档来的或本来就是）→ 用现有的提问机制向主人提一个问题，问题里带审阅意见，问题本身记着是哪个审阅提的（`approval.review_task_id`），任务进“等你决定”；只有主人的答复能让它回到队列，总控不能 `resume_task`，也不能改它的目标、范围、验收标准、职能、档位，或者挂起、预约、另提问题把它从这个问题上挪开（放弃仍可以）。升档那一轮的 Run 快照记下来源和理由。对不上（已经退回过、又跑过一轮、标准改过）只记历史。同一轮重复结算是迟到结果，什么都不做。额度、登录、失联、审不了都不经过这条路。升档之后总控不能改这个任务的档位覆盖，主人可以，改了就不再是升档。
   - **账本 16→17** 给任务加三列（`tier_escalated`、`review_of_json`、`verdict_json`）、给 Run 加一列（`artifacts_json`）、给提问加一列（`review_task_id`），不改任何任务的状态；v16 留了 schema fixture。
   做完后四条不变量里有三条闭环。
4. **只读落实。已落地**（分支 `readonly-step4`，账本版本不变，仍是 17）。实测见 [../spike/readonly.md](../spike/readonly.md)（本机 Windows 与 Linux 集群各一组），探针的实录在 `tests/fixtures/readonly/probe/`。形状：
   - **适配器声明。** `readOnly`：只读那一轮加的参数、兜到的层、一条探针，以及这一轮能带哪些档位值（`tierProblem`）。Claude 是 `--tools Read,Grep,Glob --strict-mcp-config`，工具层，账号的权限模式照旧（哪种模式都给不回不在会话里的工具），而且只接只写 `model`、`effortLevel` 的档位内容（hooks 这类设置能绕到工具层外面）；Codex 是 `--sandbox read-only`，文件系统层，只读那一轮**一律不加** `--dangerously-bypass-approvals-and-sandbox`（可写那一轮也不加：可写由适配器在命令行上说清，`--sandbox workspace-write`，不带沙箱开关的 `codex exec` 是只读的；Windows 上用哪种沙箱实现它是那台机器自己的配置 `[windows] sandbox`，tycho 不替它选、档位里也不收，没配时 Codex 会把 workspace-write 退成只读，这一点目前没有探测；实录在 `tests/fixtures/codex/0.162.0/writable/`），而且只接只写 `model…` 键的档位内容（profile 和别的键都能带进看不见的设置）。**dsh 不声明**：`--permission-mode read-only` 只挑一个档位能重新定义的预设；在所有档位之后钉一层固定补丁实测有效，但复核又找到档位绕开它的两条路（自定义沙箱 runner、换掉文件后端），档位能插入任意插件，堵一条还有下一条，所以不承诺（[../spike/readonly.md](../spike/readonly.md)）。dsh 保留 `minVersion`（0.2.2-rc.1）：可写的 Worker 也要它认 `--permission-mode`。`checkTier` 认得管权限、沙箱、审批的档位键（各适配器自己的一张表，只有它读：Claude 的 `permissions`、`sandbox`；Codex 的 `sandbox_mode`、`approval_policy`、`sandbox_workspace_write`、`sandbox_permissions`，按点分路径的任何一段认；dsh 的 `sandbox`、`sandbox-policy`、`bash-sandbox`、`pwsh-sandbox`、`fs-sandbox`、`approval`、`permission` 这几条 patch），见到就拒，说清是哪几个键；保存时拒，已存的在派发前同样拒那一档（任务停住，理由写清），不静默剥掉。这是提示，不是保证。Claude 原来对 `permissions.defaultMode` 的形状校验随之去掉：整个 `permissions` 都不收了。
   - **机器实测。** 见 [nodes.md](nodes.md) §1.2“只读探针”：只问声明了只读方式的执行器，不写东西、不耗额度；起得来报“只读可用（层）”，起不来或说不清报不可用并带原话；版本低于 `minVersion` 报“这一版用不了：……，升到 X 以上”。随现有的执行器报告上报，主机存在那台机器上；机器页按主机自己的声明读它，dsh 写“这个执行器不提供只读”。没报（旧客户端）就是不可用。
   - **派发。** 任务读出时由账本推出职能的权限（`TASK_SELECT` 的 `permission`）。三处同一个判断：挑账号（`candidateAccounts`，执行器不提供只读、或这一档不是这一轮能带的档位值的账号不是候选，`service/readonly.ts` 的 `readOnlyRefusal`）、钉账号（建任务、改任务、改职能时拒）、建 Run（`createRun` 在同一个事务里按当时的职能和执行器声明记下 `access`；快照是按另一种权限准备的就不发）。挑机器只给“这台机器报告这个执行器只读可用”的那一对；机器上的执行器版本太旧时，这台机器不接这个执行器的任何活（可写的也不接）——版本由主机拿报告里的实际版本和**主机自己的**适配器声明的最低版本比，不靠客户端自己算，旧客户端报上来的旧版本一样拦住。一次派发开头读一次任务的职能权限并带着走：挑机器、选会话、准备快照都用这一份，`createRun` 在事务里核对它还有效，变了（比如挑机器等应答时主人把职能改成只读）就放弃这次选择，任务留在队列里，下一轮按新的权限重新派。还没起来的一轮换机器（`rehostRun` 之前）用同一条判断。所有能用的机器都已经报了不可用时，任务停下，理由“没有能只读跑的机器和执行器：账号 b 的执行器 dsh 不提供只读；机器 a 上的 codex：只读起不来：……；……”，被排除的账号和机器各写一条；还有机器没报时只是等着，报告来了就派。从不降级成可写。判断只在 `service/readonly.ts`。
   - **启动参数。** 快照的 `access` 记下实际用的权限方式和层（`{ permission: 'read', layer, args }` 或 `{ permission: 'write' }`；第 4 步之前的旧快照没有，等于可写）。服务按它把这一轮交给适配器（`roundTurn`，首轮和续接同一处），适配器按自己的声明改写参数，不看账号自己设的权限模式（只能更紧）。会话只在同一种权限内续接。只读那一轮的 brief 照层说实话：写不了任何文件（`artifacts/` 也写不了），要交的写在最后一条消息里；可写那一轮照旧“这些是要求，不是沙箱”。
   - **页面。** 任务页按这一轮快照写“权限：只读：工具层 / 文件系统层”或“权限：可写”；职能页那句“权限目前只记录、尚未强制”换成实际的规则。

## 10. 第三档：操作档（已落地，账本版本 37）

读者：主人和实现者。状态：**已落地**（主人 2026-11-12 要求不等数据直接落地；账本版本 36 → 37）。本节取代 §2 的“只有这两个”、§6 的升档两步和 §7 表里“档位只有决策、执行两个”。

### 10.1 结论

**在执行档下面固定加一档“操作档”（`operate`），“验证”职能默认用它；没填操作档的登录用它自己的执行档内容顶上。** 档位仍是全局固定的名字，不做“档位有几个、叫什么由主人配”。

| 标识 | 页面上叫 | 用途 | 推荐内容 |
|---|---|---|---|
| `operate` | 操作档 | 照着做、跑出结果：跑测试、复现、按规则批量改、跑数据，交报告 | 最便宜够用的模型，低推理强度 |
| `execute` | 执行档 | 靠做完拿结果：写代码、写测试，交提交 | 便宜好用的模型，低到中的推理强度 |
| `decide` | 决策档 | 靠想清楚拿结果：分析、设计、审阅 | 更强的模型，中到高的推理强度 |

三档从下到上排序：操作 < 执行 < 决策。排序只用在两处：升档（10.3）和顶替（10.2）。

### 10.2 为什么这样分

- **问题。** 执行档同时承担“写代码”和“跑一遍、报结果”两种活。后者对错能机械核对，便宜模型就够；和写代码共用一份内容，要么写代码的模型配便宜了，要么跑测试的额度花贵了。
- **按活的类型分，不按难度分。** “这是跑测试还是写代码”派之前一眼能分清；“这段实现难不难”往往做到一半才知道。所以新档挂在职能上（验证 → 操作档），不给总控一个“判断难度”的口子。写代码里真正难的，照旧由两条规则兜住：高风险类别（认证、密钥、对外入口、账本迁移、并发）由总控按职能派分析或覆盖成决策档，执行档被审阅打回就升档。
- **不按模型系列分四档。** 档位要跨执行器通用，Codex、dsh 的模型阵容和 Claude 不一样；相邻两档差距小，挑错档的损失会盖过细分的收益。
- **为什么不做“档位集合可配”。** 讨论时说的“三档是推荐配置、不写死”，拆开看有三样：职能用哪档、总控用哪档、有几档叫什么。前两样今天已经是数据（职能页的默认档位、设置里的 `router.tier`）。第三样要付的代价是：每个登录配 N 份、升档和顶替要对付任意顺序、各执行器机器上的 profile 跟着变；而档位名是任务和登录之间的接口（§2），由主人改名等于改接口。没有人用得上这份灵活性之前不做。

### 10.3 规则

- **顶替只有一条：操作档没填，就用同一个登录的执行档内容。** 只往上顶一级，不往下（执行档没填不会拿操作档的便宜内容），决策档不顶替。只填了决策档的登录仍然只接决策档的活。这样主人什么都不改时，验证任务和今天一模一样地跑；想省额度，就给登录填一份操作档。
- **顶替的判断只在一处**：给定登录和档位，返回“用哪份内容、它是哪一档的”。挑登录（`service/pick.ts` 的 `hasTier`）、准备快照（`runner/snapshot.ts` 的 `tierValueOf`）都问它，不各自查字典。挑登录不因为“有真正的操作档”而优先：顺序照旧是项目登录清单的顺序和额度。
- **快照照实记。** Run 快照的 `tier` 仍是 `operate`，另记 `tier_from: "execute"`（只在顶替时有）；任务页写“操作档（这个登录没填，用的执行档内容）”。会话续接照旧按档位名比：同一个任务的两轮都是操作档就能续接，不论内容从哪来；内容变了按现有规则判断。
- **升档改成“往上一档”**（取代 §6 第 2、3 步）：打回且对得上当前产物时，被审那一轮是操作档 → 覆盖成执行档；是执行档 → 覆盖成决策档；已是决策档 → 照旧向主人提问。理由写“审阅打回，升到 X 档”，时间线 `task.escalate` 的 `from`/`to` 照实写。仍然不计数：档位有限且有序，“没有上一档”就是终止条件，最多自动重做两轮。升档之后总控不能改档位覆盖，这条不变。验证职能默认不要独立审阅，所以这条路只在主人给某个用操作档的职能打开“要独立审阅”时才走到。
- **只读不受影响。** 只读只看执行器有没有只读方式（§9 第 6 步），和档位无关；操作档的内容和别的档一样过 `checkTier`，顶替来的执行档内容按它自己的值检查。
- **总控。** `router.tier` 收三个值，推荐仍是决策档；选操作档时设置页提示“总控的活全是判断，不建议”，但不拒绝。

## 11. 派发偏好：每档一份全局顺序，总控按任务写优先，审阅尽量分散

读者：主人和实现者。状态：**主人已同意（2026-11-12），实现中**。本节取代 [accounts-machines-decoupled.md](accounts-machines-decoupled.md) 和 [project-sessions.md](project-sessions.md) 里“项目的允许登录是一张有顺序的清单、顺序就是偏好”的说法，以及设置项 `knowledge.logins` 的“按这个顺序”。

### 11.1 结论

**一个任务交给哪个登录，分三层定：主人的偏好打底，总控按任务调整，tycho 只守硬约束。**

| 层 | 谁定 | 在哪 | 管什么 |
|---|---|---|---|
| 每档一份顺序 | 主人 | 控制台账号页，整个 tycho 一份 | 同一档里先找谁 |
| 能用哪些登录 | 主人 | 项目页（知识任务是设置项 `knowledge.logins`） | 这个项目能不能用某个登录，**不再带顺序** |
| 优先名单 | 总控 | 建任务、改任务时带上，按任务记 | 这个任务先找谁，找不到就退回上面的顺序 |
| 硬约束 | tycho | 照旧 | 项目能用的登录、档位要填了、审阅换执行器、只读、额度、并发上限 |

### 11.2 为什么这样分

- **顺序放在全局，不放在项目。** 偏好背后是额度和成本，这是登录自己的事，和项目无关：Claude 额度紧，哪个项目里都紧。每个项目一份顺序，主人调一次偏好要改 N 处，漏一处就悄悄按旧顺序跑。和项目真正有关的只有“能不能用”（比如某个仓库只给某个账号权限），这一条留在项目页。以后真有项目要和全局反着排，再加项目级覆盖，现在不做。
- **按档位各一份。** 决策档和执行档的偏好常常相反（决策档先 Claude、执行档先 dsh），一份顺序表达不了，以前只好让某些登录不填某一档，这又让交叉审阅凑不齐执行器。
- **总控写的是“优先”，不是“钉死”。** 钉死的任务只等那一个登录，额度用完也不换。优先名单里的登录都用不了时退回全局顺序，不干等；真的只能某一个登录的，照旧钉住。
- **审阅尽量分散是 tycho 的默认，不靠总控记。** 同一份产物派几个审阅做交叉对抗，本来就该落到不同的执行器上；这是 tycho 知道的事（谁审过这份产物），放在 tycho。

### 11.3 规则

- **全局顺序。** 每个档位一个设置项 `dispatch.order.<档位>`（类型和 `knowledge.logins` 相同：一串登录，按 `TIERS` 生成，加档位不用改这里）。一个档位的顺序 = 设置里列出的、现在还在的登录，接着是没列出的，按“全部登录”原来的先后（先账号、后机器自己的登录，各按添加的先后）。留空就是今天“全部登录”的顺序。只有账本的一处（`loginOrder(tier)`）算它。
- **候选登录** = 有效登录池（`loginPool`，现在只是一组，不带顺序）里填了这一档、过得了审阅和只读判断的，按这一档的全局顺序排。`candidateLogins` 收这份顺序，不再按池子的顺序排。
- **分组挑。** 派发按顺序试几组候选，每组用现有的 `pickLogin`（额度快用完靠后、并发上限、`dispatch.frontLead` 分散都照旧），第一组挑得出就用它，挑不出（组里的都在歇息、跑满、没机器、登录被拒）就试下一组；最后一组是全部候选，它挑不出时任务等待，等待的原因照旧按全部候选写：
  1. 总控的优先名单里、也在候选里的登录，按名单的顺序；
  2. 审阅任务：没审过同一份产物的执行器的登录（同一份产物 = 绑定的被审任务和那一轮相同；审过 = 那些审阅任务建过 Run 的执行器）。这一组只在这样的执行器已经存在时才有：第一个审阅没有可分散的对象，按全部候选挑，`placed_by` 记 `order`；
  3. 全部候选。
  空组跳过。钉住的任务只有它钉的那一个，不分组。写过产物的执行器降级审阅（§4 ②）照旧在全部候选都审不了之后才走。
- **优先名单。** `create_task` / `update_task` 收可选的 `prefer: { login_ids, reason }`，`login_ids` 是一到几个登录（工具入口按当前名字解析成编号，和 `login_id` 一样），`reason` 必填。工具入口只拒收不在项目登录池里的登录；名单里没填这一档的登录不报错，派发时自然不在候选里（比如升档以后）。`update_task` 填 null 去掉名单。名单存在任务上（`task.prefer_json`），改它和改档位覆盖一样记进 `task.update` 的时间线，不改修订号。退回重做、升档都保留名单。
- **记下是哪一组挑中的。** `run.create` 的审计记 `placed_by`：`prefer`、`spread`（审阅分散那一组）或 `order`。任务页显示优先名单和理由；每一轮显示“按总控的优先 / 审阅分散 / 按顺序”。
- **总控看得到依据。** `list_logins` 每个登录多给：能接哪几档（按 §10.3 的顶替算：没填操作档的登录也报操作档，`tier_from` 写明它的内容来自执行档）、各档在全局顺序里的位置（顶替来的档位按它自己那一档的顺序算）、在跑几轮、并发上限、额度用到多少（有读数时）。总控的说明写清：一般不填 `prefer`；想按执行器分散或交叉、或者某类活更适合某个登录时才填；只能某个登录时才用 `login_id`。
- **不变的。** 档位由职能推出、审阅换执行器、只读、额度歇息、并发上限、`dispatch.frontLead`、钉住的语义都不变。哪个档位用哪个执行器，tycho 不写死，全由顺序和名单表达。

### 11.4 迁移

- **账本升一版**：任务加 `prefer_json`（可空）。项目的 `logins_json` 原样保留，只是顺序不再起作用；`knowledge.logins` 同样。全局顺序两个设置项默认为空。迁移不从各项目的清单里猜一份全局顺序：主人在账号页排一次（上线时的说明里写明）。留上一版 schema 的 fixture。
- **控制台**：账号页加“派发顺序”一节，每档一列，拖动或上下移；项目页的登录清单改成勾选，不再排序；任务页显示优先名单和每一轮是哪一组挑中的。
- **总控**：工具 schema 加 `prefer`，`list_logins` 多给上面那几项，提示词改一段。工具变了照规矩重启总控。

### 11.5 审阅的档位跟着被审的那一轮

主人 2026-11-12 认可（来自 token 排查：dsh 写的东西全被派给 Claude 决策档审，是额度烧得快的主因之一）。

- **规则。** 审阅任务的实际档位 = 覆盖 ?? **被审那一轮的档位** ?? 职能的默认档位。执行档写的由执行档审，决策档写的（本来就是或升档来的）由决策档审。交叉审阅换执行器照旧。
- **出处只有一处。** `bindReview` 生成绑定时，从被审那一轮的快照抄下 `tier`，存进 `review_of_json`；`TASK_SELECT` 推实际档位时用它，来源记“跟着被审的那一轮”（`TIER_SOURCE_TEXT` 加一项）。旧绑定没有 `tier`，照旧用职能的默认档位（审阅职能默认仍是决策档）。
- **高风险的照旧升到决策档审**：改到认证、密钥、对外入口、账本迁移、并发的，总控用现有的档位覆盖（带理由）把审阅定成决策档；这条写进总控的提示词。tycho 不从代码改动里猜风险类别。
- **打回和升档不变。** 执行档的审阅打回执行档的产物，照旧升到决策档重做；重做的产物再审时，绑定抄的就是决策档。
- **职能页**在审阅那一行写明“实际档位跟着被审的那一轮，默认档位只用在旧数据上”。

### 11.6 和别处的关系

- 本节同时改了两件事：审阅**用哪一档**（11.5）和同一档里**先找谁**（11.3），两件互不依赖。
