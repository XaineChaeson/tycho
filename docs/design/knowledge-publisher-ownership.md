# 谁能修改原生入口里的 Tycho 知识

同一份原生入口只能由一个已识别的知识发布集合维护。另一套服务可以报告占用，不能覆盖或撤下它。此记录确定修复边界；实现与原生验收结果分别记录。

2026-11-15 的隔离实验在 Claude、Codex、dsh 三个实际适配器目标上均复现：A 写入后，B 的空投影删除 A；B 的另一份知识覆盖 A，A 再检查又改回。741 与 754 的写入、检查实现相同。通用“Tycho 生成”标记不足以表达不同发布方。

## 决策

- 为全局知识发布集合生成一次持久的 `publisher` 标识，保存在服务私有数据域。主机本机和它的节点使用服务提供的同一个值。这个值表示发布集合，不冒充项目归属的服务身份，不启用旧服务的 ProjectHome authority，也不从 URL、路径或 Node 身份猜归属。
- 文件格式记录发布集合。只有同一发布集合能更新、撤下文件；另一个集合即使关闭自己的投影，也不删除它。旧文件缺少归属、格式未知或标识不可核实时保留并报告问题，不按相同正文或摘要接管。
- 归属核对与文件变更由同一入口完成，并在跨进程事务锁内串行。复用 Node 内置 SQLite 的系统锁，不建立第二份知识账本或 PID、TTL 租约。未知的协调文件不得被当成自己的重新初始化。默认关闭且没有投影时，不为协调创建原生配置目录。
- Node 协议升到 7。旧客户端通过既有、与协议版本无关的发布握手跟随升级；它们不能在新协议下提供固定知识检查结果。新检查器识别所有发布方的 Tycho 投影，旧格式也不能被当成不存在；未来未知的 Tycho 格式保留为未知。

SQLite 允许不同进程共享读事务，但同时只有一个写事务；本次仅借用这一互斥能力覆盖合作写方的文件操作。文件本身的完整替换仍由入口写方负责。协调文件要求文件系统提供正确的 SQLite 锁；所有活跃连接使用同一个最终路径，程序不会再次打开冷初始化的临时名。依据：[事务语义](https://www.sqlite.org/lang_transaction.html)、[文件锁与数据库别名边界](https://www.sqlite.org/lockingv3.html)。

协调文件固定为执行器 profile 根目录中的 `.tycho-entry-mutex.sqlite`，这是共享写方的协调约定。Claude 的规则以 `.md` 文件定义发现范围；当前实现仅在其 `rules/` 子树新增知识 Markdown，保留目录原有的其他文件，参见 [官方规则说明](https://code.claude.com/docs/en/memory#organize-rules-with-clauderules)。初始化中断留下的冷临时别名不再被打开，也不因这个残留把有效协调文件永久拒绝。初始化失败、持锁忙和发布身份不可核实都如实显示尚未写入；只有实际写入后无法确认加载时，才显示加载未确认。

## 迁移边界

只在文件第二行加归属挡不住旧写方。新首行格式能让旧写方保留文件，但 741 的旧检查器会把它误报为不存在。因此，共享同一原生配置目录的主机、节点必须全部升级到支持新格式的版本，才能启用这种投影。新格式本身不证明混版安全。

升级前先在原发布服务关闭外部投影并确认撤下，再升级共享目录的所有写方和检查方。来源不明的旧格式文件保留，等待主人明确迁移；自动升级不能偷偷删除它。Tycho 派发的知识快照不依赖这项外部投影开关。

保证只覆盖合作的新写方对生成文件的归属与并发维护。它不隔离原生执行器自己的 AGENTS.md、技能、记忆、MCP 配置或私人会话，也不承诺跨服务共享整套原生 profile 的语义隔离。
