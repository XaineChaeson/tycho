# 在使用中改进自己：tycho 的自我迭代

读者：主人和实现者。状态：**已确认，分步实现中**（2026-11-06 三方审计裁决后定稿）。回答一个问题：你在对话里说"这个页面不好用，改成这样"，tycho 怎么把它做成、你确认、上线；改坏了怎么退回去。动手顺序见 §7。

## 结论

**你的场景能做，但只有下面这一种做法成立。**

- **改动分两条路，按"要不要换版本"定**：不动账本的（配置、技能、总控的角色说明）当场或下一次用到就生效，插件要**装上并显式激活**；动核心的（服务逻辑、内置页面、账本、状态机）必须换版本。
- **不允许"没法预演"**：候选版本先拿账本副本在一次性目录里起一次，页面只读、写明是冻结副本，通过之后才切换真账本。
- **不允许"上线后自动恢复账本"**：自动回退只换程序，**保留当前账本**，且只对已经证明向后兼容的发布生效。不兼容的迁移不进自动发布，人工做，动手前先说清会丢什么。恢复账本是事故处理，不是版本切换的反操作。
- **第一步只改控制台展示这类不动账本的改动**，验收是"一次真实上线 + 一个**故意失败的候选包**能退回上一版"。

顺序（和 [nodes.md](nodes.md) §2 同一份）：

1. 你跑的是**安装版**，不是源码 clone：只有安装版有"上一版"可退（`tycho update` 对源码目录直接拒绝）。
2. **第一步用现有 SSH 路径**跑通闭环；然后节点各步；**删 SSH 放最后**。
3. 之后才是配置和提示词自助、预演、外部插件。

## 1. 你会怎么用：一次改动的全过程

以"总览页那句话不好用，改成这样"为例。

1. **你提。** 你在对话里或企业微信里说一句。总控把它变成一个任务：项目是 tycho，写清验收标准，按职能建（改代码是实现），派到干活的机器。你只说要求，不用指定文件、分支或命令。
2. **它做。** 任务开工时机器自己去拿代码：项目配的仓库由那台机器用自己的 git 登录 clone（文件夹来源就在那个文件夹里原地做），执行者就在这份代码里改、跑项目规定的测试、在它自己的一条分支上提交、推上去、开 PR，回执里报提交号和 PR；非代码的交付（比如发布包）放进这一轮的 `artifacts/`。代码怎么去、改完去哪，只有 [code-sources.md](code-sources.md) 一处说；本文原来那套主机打 bundle 随快照下发的说法已经删掉。
3. **主机取回。** 代码不回来：仓库来源由执行器在那台机器上推分支、开 PR，文件夹来源的改动本来就在那个文件夹里（[code-sources.md](code-sources.md) 一处说）。服务按回执声明的路径，用现有的读文件通道把**非代码产物**（比如发布包）取回主机、落盘并按登记编号登记，核对摘要。进主线是合那个 PR，tycho 不把代码并进主机上的检出；也不需要主机上装前端工具链。
4. **不满意就退回去。** 执行者交回的东西不对（比如最后一次测试之后文件又改过），你在任务页上**退回返工**，或者让总控调 `rework_task`：任务回队列，说明进下一轮输入，接着用同一个来源在机器上的那份检出和同一个会话做，不用另起一个任务。
5. **独立审阅。** 一个审阅职能的任务（决策档，派给没写过这份产物的执行器；别的执行器都审不了时由写过的开新会话来审并标出，见 roles-and-tiers.md §4 ②）按验收标准核对**最终 commit**、测试结果、包摘要和改动范围——不看作者的结论。审阅后代码再动，旧审阅作废。
6. **你确认。** 默认你要做一次明确的动作：在主机上运行

   ```text
   tycho update --from <已审阅的发布包>
   ```

   这条命令的执行就是批准，不再重复问一次。授权绑在这次这个包上：包变了，旧授权失效。
7. **上线。** 独立的升级进程换版本、起服务、跑健康检查；通过后你刷新页面就是新的。发布窗口里没有非终态 Run，总控当前回合已经结束。
8. **退。** 不满意就说"退回去"，或再运行一次 `tycho update --from <程序目录>/versions/<上一版>`（上一版目录默认留着，不用重新下载）。**退回只换程序，账本留着**；升级后写进去的东西都还在。只有不兼容的迁移才人工处理，那条路会先告诉你会丢什么。

第一步里，"你说一句"到"你一条命令上线"全部走现有机制，不新增对象、不做插件。

## 2. 分层：哪些改动不用换版本

"不用换版本"看的是**谁在什么时候读它**：

| 层 | 谁在读 | 什么时候生效 | 现状 |
|---|---|---|---|
| 配置项 | 各模块按需要 | 用到的那一刻 | 已有：控制台设置页；登记在 `service/settings.ts` 一处（键、类型、默认值、说明、要不要重启） |
| 技能 | 派发器 | 每次派发 | 已有：从[知识账本](knowledge-and-skills.md)选择适用的技能修订，随快照下发 |
| 总控的角色说明 | 总控进程 | 拉起总控时读（目标） | 今天在服务启动时读一次，改它要重启服务；第二步改成拉起总控时读 |
| 内置页面 | 浏览器 | 随发布包 | 只能换版本（服务只提供 `console/dist/` 里真实存在的文件） |
| 插件 | 服务进程／浏览器 | 装上、显式激活 | 第三阶段做（§5） |
| 核心：服务逻辑、账本结构、状态机、路由表、九条底线 | 服务进程 | 换版本 + 重启 | 只能换版本，插件碰不到 |

三条硬规矩：

- **不可替换**：账本、状态机、九条底线、对外监听上谁能看到哪些接口，不因为"能改自己"而放宽。
- **配置只有一处**，这句话在配置自助落地时要改成：**控制台和被授权的对话操作使用同一个配置服务和同一份账本数据**——不新增配置文件、环境变量入口或第二套校验规则。改这条约定时，代码、测试和 `AGENTS.md` 一起改。
- **总控的工具是拉起时定死的**：工具列表在启动时逐字比对，不符就停摆。所以"给总控加一个改配置的工具"要重启总控才生效，不能热加载。

## 3. tycho 改 tycho 的闭环

### 3.1 代码怎么去、产物怎么回来

**代码怎么去：** 项目里配代码来源（[code-sources.md](code-sources.md) 一处说；本节原来那套"主机打 bundle、随快照下发"的运行链已经删掉，不留第二条路）：一项是一个 Git 地址，或者某台机器上的一个文件夹，可以有多项、有顺序。选定的来源钉在任务上，任务以后的每一轮都用它。

- **仓库来源：** 派到项目允许的任意机器，那台机器用它**自己的** git 登录 `git clone` 到任务目录里按来源绑定身份命名的目录（`tasks/<任务>/<来源 id>-<短哈希>/`，bindingKey）；同一绑定的后续轮次接着用这一份，上一轮没提交的工作也在里面。fetch、提交、推分支、开 PR 都是执行器自带的 git、`gh`、`glab` 用那台机器自己的登录做的，tycho 不替它推；推不上去照实写进回执，不算这一轮失败。主机不碰任何仓库、不保存代码副本，地址里也不带秘密（`shared/remote.ts` 的 `machineRemote`）：机器有没有访问权限是那台机器的现场，clone 失败就把 git 的原话带回这一轮，这一轮没有开工。
- **文件夹来源：** 只派到点名的那台机器，执行者的工作目录就是那个文件夹本身；tycho 不往里写任何东西，也不替执行器建 worktree，几件活并行还是先后由总控安排（code-sources.md §4）。
- **只读的一轮**（审阅、分析、验证）用自己的一份检出来看代码，不碰任务保留的那份，也不动别人正在用的文件夹。

**同一个来源的第二轮起固定在第一轮那台机器上**（成果在它的任务目录里）：那台机器没了就停住并说明原因，由总控决定改派来源还是重来。文件夹来源只在那台机器上跑，离线就等。改派来源（总控的 `update_task`）会解除这条固定，仓库副本按来源的**绑定身份**分开保存（同一个来源编号改了地址也是新的一份），旧的那份归保留期清理。原来那些"主机打 bundle、包大小超过上限就不派发、基准提交在主机上没有了就不派发"的规则，随这条运行链一起删掉了。

**产物怎么回来：** 代码不回来。执行者在来源里改完、跑完测试、提交，仓库来源把那一条分支推上去、开一个 PR（文件夹来源的改动就在那个文件夹里），回执里写分支、提交和至多一项 PR 链接；提交是不是推上去了，由跑这一轮的机器在结束时用 `git ls-remote` 读那条分支的远端头、随报告报回，主机照这份报告绑定审阅（主机不问远端：持有仓库访问身份的是干活的机器）。**非代码的产物**（发布包、报告这些）执行者留在这一轮的 `artifacts/` 里，服务按回执里声明的路径，用现有的读文件通道取回主机落盘，报出摘要：每次取回先落在临时目录里校验，再一次改名成按登记编号命名、之后不再改写的目录 `<数据目录>/releases/<run>/<登记编号>/`，然后在账本里登记（[roles-and-tiers.md](roles-and-tiers.md) §9 第 3 步）。账本的登记是产品身份的唯一权威：页面、验收、审阅、上线和合 PR 都从这一轮当前的登记找文件，磁盘上没登记的目录一律看不见，取回半路失败或崩溃只留下一个没人认的目录（之后被清掉），上一份登记照旧可用；被替换下来的旧登记目录保留，正在读它的升级命令不会读到一半没了。**主机不依赖 GitHub 或 GitLab，也不需要主机上有前端工具链。** 发布包必须能追溯到已审阅的内容：审阅绑定的是来源 + 提交（仓库是推上去的那个提交，文件夹是机器读到的 HEAD）+ 登记文件的摘要集合，代码再动、包重打，旧审阅自然失效。

**进主线是把那个 PR 合进去，不是主机上的本机合并。** tycho 没有"把代码并进主机检出"这条运行链（仓库根 `AGENTS.md` 的"主线只有一条：合 PR"）：仓库来源的活由执行器推分支、开 PR，`gh pr merge --match-head-commit <被审提交>` 是唯一真正的把关；没有 PR 就没有可并的。要求任务已验收，判定只在账本 `requireLandable` 一处；主人在控制台和总控都一样。有 PR 的并入是一个"验证"职能的子任务：它只合审阅绑定的那个提交，服务自己不推送、不调代码托管的接口；它那一轮结算为待验收且回执里有一个提交时，才在父任务上落并入的结果（`task.integrate`）。工作目录来源的改动本来就在原地，没有要并的东西。

发布包必须能追溯到已审阅的内容：提交号 + 包摘要一起绑进这次发布。审阅之后代码若再动、包若重打，这次授权就作废，要重新走一遍。**"包打出来了"不能当发布验收**（`scripts/pack.ts` 会重新构建控制台，它不替代测试、审阅和干净工作区检查）。

### 3.2 谁审阅、谁批准

- **审阅是普通任务**，职能是“审阅”，建的时候指名被审的任务；其余由服务定（[roles-and-tiers.md](roles-and-tiers.md) §4、§9 第 3 步）：绑定被审那一轮报回的**来源 + 提交**（仓库是推上去的那个提交，机器读了远端这条分支的头；文件夹是机器读到的 HEAD）和这一轮登记的非代码文件（名字 / 摘要 / 大小）以及当时的验收标准；brief 只给被审任务的目标、验收标准、提交、改动范围，不给作者的报告、总结和会话，代码由审阅那一轮自己 clone 后检出那个提交，或在工作目录来源的文件夹里对着它看；有别的执行器能审时，写过这份产物的执行器不能来审；别的都审不了时由写过的执行器开新会话来审，并标“未换执行器”；连它也审不了才停下。结论是通过、打回、审不了三种之一。实现这类要独立审阅的任务，没有针对当前产物的“通过”就验收不了，上线入口也只放行被“通过”覆盖的那个包；打回时服务把执行档的产出退回重做并升到决策档，决策档再被打回就停下找你。只有一个执行器时由它开新会话来审并照实标出；连它也审不了时，出路是你在控制台“不经审阅验收”，时间线上留一笔。
- **批准是你的一次动作**：第一步就是你运行那条升级命令。总控、插件和自改的 Worker 都不能替你扩大这份授权。
- **以后可以配置成"审阅通过就直接上线"**（默认关），它只省掉你那一次动作，仍必须满足同一套审阅和检查要求，不省掉回退。

### 3.3 上线由一个独立进程做

负责升级和回退的进程，不能是正在被停止的那个服务，也不能是这次自改的 Worker。它继续用 `cli/` 这一套：版本目录、安装记录、`install.lock`、改写 `current` 这个提交点。`install.lock` 要覆盖整个升级尝试和回退，不能在切换后就释放、再另起一条没有锁的回退路径。

升级过程要持久记下旧版本、候选版本、包摘要和进行到哪一步，这样升级进程自己崩了也能识别出"有一次没完成的尝试"，而不是停在半路没人知道。

### 3.4 健康检查回答什么

不止问"是不是你"。候选版本至少要让检查回答：

1. 回答的是**预期的版本、程序目录和数据目录**（今天只轮询"服务在运行"，换个版本照样能答）；
2. 账本能打开，**恢复屏障已经完成**，没有降级；
3. 控制台的入口和它实际引用的资源能加载；
4. 这次发布涉及的核心接口能读；
5. 检查窗口内没有退出或反复崩溃。

**门牌、外部机器、没配置的通道出问题，不触发回退**——那是原有环境故障，不是候选版本变坏了。恢复清点超过等待时限也不触发回退，但不能报通过：保留新版在跑，记录 `verified: false`、`ok: false` 和 `pending` 中尚未完成的核对步骤，页面和命令都说“版本已在跑、核对没做完：恢复清点尚未完成”。每次刷新服务状态，包括清点等待期间、观察窗口内和最终判定前，都重新检查账本读取和降级；等待期间进入降级是失败，照常走回退。超时也不等于"新进程已经不在"：回退前必须确认候选服务和它的总控驱动者都停了；确认不了就保留现场，宁可不动，也不起第二份服务。

### 3.5 自动回退的边界

```text
已确认候选服务退出，且旧程序能够正确处理当前数据时，退回程序版本，保留当前账本。
```

- **只换程序，不恢复账本。** 自动回退不碰 `ledger.before-vN.db`：恢复它会抹掉新版已经收下的消息、已经提交的决定、已经派出但旧副本没有记录的 Run、已经发出去的通知——那些外部副作用回不来。
- **只对已经证明向后兼容的发布生效。** schema 数字相同不足以证明兼容：字段含义、状态含义、外部协议也要兼容。所以每个版本要带一条明确的"能退到哪一版、依据是什么"的结论，并由检查核对，不能由发布的人口头声明。
- **不兼容的迁移不进自动发布。** 人工做，动手前先说清会丢什么。
- 这条改写了 `AGENTS.md` 里"改写 `current` 是提交点，之后失败不回退"那一条（`cli/install.ts` 现在的行为和它的测试都固定了旧约定）：**代码、测试、文档要一起改**，改成"提交点之后只在已证明兼容的发布上换回程序，账本不动；不兼容就如实报告，等人工"。

### 3.6 上线时正在跑的对话和任务

- **机器上的任务不受影响。** 执行在远端机器上进行，服务重启不影响它；服务起来后按现有恢复流程逐项核实，不重做、不清空。旧 Run 继续用它自己快照绑定的执行器、协议和插件版本收尾，不能改用新配置解释旧结果。
- **总控正在说话时，第一步不做无停机上线的承诺。** 现在停服会打断当前回合。第一步要求在**回合结束后的发布窗口**执行升级；以后再加排空（停止领新消息、等当前回合和工具收尾、再停服），并且上线工具不能等自己所在的那次工具调用结束——否则自己等自己。异常中断的请求标为"待核实"，不自动重投。
- **升级者不能是这次自改的 Worker**，也不能是正在被停的服务；它是一条独立命令。

### 3.7 失败验收

第一步必须有一个**故意失败的候选包**：装上、起不来或健康检查不过、退回上一版、服务恢复可用、账本没被动过。回退前的这段路要专门测一次：新版启动后收下一条消息、提交一个决定、派出一轮 Run，然后触发健康失败——**回退后这三样必须都还在**。

另外这些输入也要能过（至少不误报成功、不起第二份服务）：错误版本仍能回答身份接口；候选恢复耗时超过检查窗口；总控不可用但页面正常；停止候选超时；升级进程自己崩在半路。

## 4. 预演：唯一成立的做法

裁决里两处顺序不一致：《顺序》一节把配置和提示词自助排在预演之前，《自我迭代》一节说"预演放第二步"。**这份定稿按《顺序》排**（§7 第三步：配置自助在前，预演在后），要调换只动这两节的位置。

**预演不是"再起一份生产服务"**，而是：

1. 迁移之前用 `VACUUM INTO` 复制账本（现有迁移路径已经在留 `ledger.before-vN.db`）；
2. 用 `restoreBackup` 把副本恢复进**一个一次性数据目录**——它自带的封存语义正是我们要的：置 `pause.user`、排队的任务和预约转 `held`、未处理的消息转 `unverified`、待发的通知放弃；
3. 用候选版本起一次（`tycho run --port <端口>` 只让这一次运行换端口）；
4. **不接通道、不派发、不清理总控**；
5. 页面**只读**，并写明"这是冻结副本，写进去的东西在切换时会被丢掉"——副本是快照，不是草稿纸。

必须有一条测试断言：预演期间**生产进程、远端文件、通道发送次数全部不变**。光证明"候选页面能打开"不算通过。

两个已经踩到的坑，写进实现要求：

- **副本里带着生产总控的进程标记。** 候选启动时的清理会按这个标记去清理**生产**的总控（`cleanup()` 找进程的依据来自账本，不来自候选的数据目录）。所以预演入口必须独立，不能执行生产进程清理。
- **不要用"经门牌的同一条路径加个子目录"来预览。** 页面仍在根路径上请求 `/api/...`，你点一下就可能打回生产服务；换端口挡不住，同源复用会话也挡不住来源校验。预览要用独立的来源和独立的认证；页面本来就是只读的（上一段第 5 条），不提供任何写操作。

说清预演能证明什么：**迁移、数据读取、页面展示**。它不等于"接管生产现场的演练"——副本里同时有活跃总控、运行中的 Run、待发 Outbox 和绝对目录配置，那些不能靠"副本加新端口"保证安全。

## 5. 插件（裁决里的"第三阶段"，队列最后）

需求已经成立——你自己就是第二个作者，"在使用中给自己加能力"不是假想需求——但排期服从第一次可用闭环：先闭环和节点，插件排在队列最后（裁决里叫"第三阶段"，§7）。

真做的时候：

- **不可变的版本目录**：`<数据目录>/plugins/<插件 id>/<版本>/`，`plugin.json` 声明类型、配置字段、入口和文件清单；启用状态、配置值、活动版本存账本。
- **显式激活，不做文件监视。** 加载只发生在三个时刻：服务启动、控制台里点"重新加载"、装上/启用这个插件。数据目录什么时候被谁改过要看得见，自动生效会让这件事不可预测；"编辑到一半"和"批准生效"不能混在一起。
- **先做两种类型**：`executor`、`channel`。控制台页面用 sandbox iframe（收紧 sandbox 权限、来源和消息接口），只加页面、不动内置页。
- **故障隔离用子进程**（插件可以在导入或启动里死循环、`process.exit()`、留下撤不掉的异步资源）。**但要如实说**：子进程只解决"坏插件不拖垮服务和消息入账"，同用户下的代码仍读得到这个用户能读的文件，同源的页面代码也拿得到你的会话权限——**同进程或同源的代码不是沙箱**。第一版只装信得过的插件。
- **活跃 Run 保留原绑定**：卸载一个还被运行中 Run 用着的执行器，要保留那个版本和它的解析能力，不能替换入口后让旧结果改由新代码解释。
- **注册可撤销**：撤销不完成就如实显示；部分注册失败就撤销本轮已经做成的部分。

## 6. UI 的位置

控制台、企业微信、以后的桌面端都是同一组接口的客户端。

**现在不做桌面应用。** 网站加 PWA 够用：能装到桌面、能收通知、手机和别的电脑都能用。桌面应用真正的价值不是界面而是分发（一个安装包带上主机、客户端和 Node），那在开源发布前才值得做，到时用薄壳套住同一个网页。

## 7. 分步实现

### 第一步：自迭代闭环（用现有 SSH 路径，今天就能做完）

只做一件事：**你说一句，它改，你一条命令上线，坏包能退回去。** 全程只改控制台展示这类不动账本的改动。

范围：

- tycho 仓库登记成一个项目（`create_project`），项目的代码来源指向这个仓库（仓库来源：干活的机器用它自己的 git 登录 clone；主机上已经有检出、想让它在原地改就用文件夹来源），配上能改代码的账号、机器和项目技能（技能是一组 md 文件，随时能改）；
- 任务目标里写清要改什么、交付方式（在来源里改、跑测试、提交、推分支、开 PR；非代码产物放这一轮的 `artifacts/`）和验收标准；
- 执行者在来源里改、跑测试、提交、推分支、开 PR；回执里报分支、提交和 PR，非代码产物留在 `artifacts/`；
- 主机按回执取回非代码产物、核对摘要并登记（§3.1）；进主线是把那个 PR 合进去（§3.1）；
- 另建一个审阅任务审被绑定的那个提交和登记的文件（§3.2，见 [roles-and-tiers.md](roles-and-tiers.md) §4）；
- 独立升级进程、健康检查、程序回退（§3.3–§3.5）；
- 发布窗口：没有非终态 Run，总控当前回合已结束（§3.6）；
- "只改页面"由发布文件差异和审阅核对，不能靠作者自称兼容；不能一直用 `0.0.0` 覆盖上一份可用的代码：打包时由提交数决定第三段，同一条主线上递增；两条分支撞号时由落地核对发布清单拦住，不当重装（见 phase1-design）。

不做：插件、通用迁移回滚、无停机切换、把审阅做成固定对象、预演。

**第一次真实闭环之后补的三处**（这三处是闭环本身缺的，不是新阶段）：

- `ready` 的任务可以**退回返工**（`rework_task`，任务页上也能点）：说明进下一轮的 `pending_inputs`，接着用同一个来源在机器上的那份检出、能续接的执行器接着上一轮的会话，修订不动；带 `expected_revision`，任务改过就拒。
- 任务页上给一个**并入主线**的入口：把审阅绑定的那个提交所在的 PR 合进去（一个“验证”职能的合入子任务，服务只给 gh/glab 一条按提交匹配的命令，自己不推送、不调代码托管的接口；没有 PR 就没有可并的）。要求任务已验收；主人点，或项目授权“并入主线”后总控也能做（project-sessions.md 文末“总控可以自己做的事”）。tycho 不把代码并进主机上的检出。
- 技能（`skills/<项目>/`）里把顺序写死：改完 → 跑全部检查 → 提交 → 打包 → 放 `artifacts/`，**提交之后不再动文件**；回执写最终提交号和"检查是在这个提交上跑的"；版本号不由执行者改，打包按提交数给。

**成功标志**（你要能看到的）：

- 你说一句，任务出现，任务页能看到执行者改了什么、跑了什么、结果如何；
- 一条命令的输出说清从哪个提交构建、升到哪个版本、健康检查结果；刷新页面看到新样子；
- **一个故意失败的候选包被退回，服务回到上一版，账本里的东西都还在**；
- 中间任何一步失败，命令说清现在用的是哪个版本、还需要你做什么。

### 第二步：配置和提示词自助

- 总控的角色说明改成"拉起总控时读"，改它只需重启总控；
- 把还写死在代码里的行为登记成配置项（期限、并发、开关、目录），控制台仍是唯一读写入口；
- 给总控加改配置、改技能的工具（受服务端校验；新增工具要重启总控才生效），在对话里说"把失联宽限期改成半小时"当场生效；
- **撤销是新操作**：校验当前修订，提交新的配置和审计，再执行外部重配；"配置已经保存"和"外部激活失败"分开显示；不去覆盖更晚的那次修改。

## 8. 仍不知道的，以及现在就补的实测

| 不知道的 | 怎么测 | 猜错了会怎样 |
|---|---|---|
| 执行机能不能拿到仓库、把改动交回来 | 在真实执行机器上端到端走一遍：机器用它自己的 git 登录 clone、改、跑测试、提交、推分支、开 PR，主机取回非代码产物 | 拿不到就走文件夹来源（主机上已经有检出、执行器在原文件夹里做）；这条决定第一步能不能兑现。（代码由机器自己 clone，所以“机器上有没有托管的凭据”不影响拿到代码，只影响执行器能不能自己推分支、开 PR，推不了照实报告；剩下的只有机器上的 git 版本和仓库的访问权限） |
| 打包耗时与位置 | 机器上跑控制台构建和打包，记时间和网络可达性 | 太慢就改成主机上构建（主机有 npm 和网络） |
| 真实发布耗时与检查窗口 | 在主人机器上量健康等待和恢复清点的时间 | 窗口太短会误判回退，太长会拖住上线 |
| 兼容范围 | 除了 schema 数字，还要验证写入行为和状态含义 | 判错的代价是"以为能退，实际退回去读不懂账本" |
| 跨平台回退 | Windows 文件占用、计划任务重启、升级进程崩溃 | 回退本身失败，只能人工 |
| 停服期间通道会不会重投消息 | 实测企业微信长连接断开期间的行为 | 决定"升级期间消息不丢"能不能写成承诺 |
| 总控回合与发布的交接 | 在"已提交账本写入、工具还没返回"时请求升级 | 不能让发布请求和当前回合互相等待，也不能自动重投消息 |
| 回退约定（现有约定） | 现有实现与测试固定了"提交点之后不回退" | 改成"只换程序"时要一起改代码、测试和 `AGENTS.md` |

## 附录：dsh 的实际机制（调研，2026-11-06）

调研对象是本机安装包 `0.2.2-rc.1`（构建 commit `c59d10af…`，ASAR 内存读取，未解包）和随包中文文档。**借三样**：一项能力由接口、实现、使用方一起设计；插件声明自己的配置项，界面按声明生成表单；注册可撤销、改配置不重启。核心不借。

有用的实测事实：

- **程序树是"空入口 + 一摞补丁"叠出来的**：`cordis.yml` 是永不被编辑的空基线，profile 的组合包 patch、profile patch、home patch、`--patch` 逐层叠加；一条 patch 按 id 替换某个条目的整个 config，不做深度合并（所以同一块配置没法叠加——这是它的代价，也是我们不学多层 patch 的原因之一）。
- **配置编辑是一条串行、可校验、可发现冲突的写路径**：拿文件锁 → 按 schema 校验完整候选配置 → 原子写 → 重新合成比对，若这个字段被更高层覆盖就报错而不是默默写进去。界面只允许改标了 volatile 的字段，读一律脱敏。**这三件事值得照抄**（我们这边落在账本事务和控制台的设置校验上）。
- **"装好了、保存了、运行了"分三件事报告**：包管理器退出码为零不等于能力可用；安装、保存选择、运行时激活分别有结果，可能是失败、被覆盖或需要重启。
- **热生效分四种**：volatile 字段就地更新、普通字段重启该插件、插件代码取决于模块图和 HMR、浏览器插件单独换 bundle 且组件状态可能重置。随包的 headless 组合默认关掉 HMR。
- **恢复手段分五层**：写前校验、写后比对回滚、桌面安全模式（起不来时禁掉全部插件、用户的 patch 不动）、`--from-default-profile` 重建 profile、安装失败把清单文件恢复原样。

**四处常见说法经核对不成立，不要照抄：**

| 说法 | 事实 |
|---|---|
| "dsh 没有任何不可替换的基础" | 说得过满：Loader、启动、包管理、恢复入口和几份策略名单都是基础 |
| "热更新失败会完整恢复旧插件" | 不成立：旧插件先被停止，新代码加载失败后旧代码不再运行 |
| "dump 命令不挂载插件，所以是无副作用查询" | 不成立：它会重写 profile 的 `cordis.yml`，schema dump 还会导入模块并执行 schema 构造代码 |
| "从默认模板重建等于回到上一个可用状态" | 不成立：它替换自定义 profile（含依赖和用户 patch），不保证恢复旧依赖，也不消除更高层的 patch |

这四条支持的是**"配置、安装、激活、恢复分别报告"**，不是"复制一整套 HMR 或自动回滚"。
